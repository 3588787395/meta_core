## 一、分项详细评审

### 1. 表驱动深度（30分 → 17分）

**做得对的地方：**
- 准确指出现有代码中"表驱动只做了一半"的问题——查表路由而非结构蕴含
- 对五个认知偏差的诊断基本准确，特别是"编译期一次性解析"的洞察
- 提出 EdgeOp 概念，向"可执行操作码"迈进了一步

**核心问题：**

1. **EdgeOp 仍是"打包的函数调用"，不是"结构蕴含逻辑"**  
   spec 中的 EdgeOp 包含 `trigger` / `filter` / `propagate` / `ttl` / `side_effects` 五个字段，每个字段都是一个"操作对象"。这本质上是把原来散落在 5 个函数里的调用关系打包到了一个数据结构里，但**逻辑仍然在代码里，不在表结构里**。真正的表驱动应该是：**边的类型决定了执行计划中的位置和 opcode，执行器是一个通用的虚拟机，不关心这条边是条件边还是无条件边**。

2. **配置表收敛是"合并同类项"，不是"提升抽象层级"**  
   把 90 张表收敛到 18 张表的思路是"功能相近的合并"——事件/信号/告警合并为 rules.json，TDX 适配表合并为 tdx_adapter.json。这是**物理合并**，不是**化学融合**。真正的表驱动提升应该是：**找到更底层的统一抽象，让一张表能承载原来 10 张表的语义**。比如，规则引擎的 ECA 模型是否能统一更多东西？

3. **运行时表的"一等公民"设计停留在命名层面**  
   说"运行时表要有固定 schema、可查询、可写入、有明确生命周期"，但设计里的 8 张运行时表还是普通的 dict，没有统一的访问接口、没有 schema 校验、没有生命周期管理。`_RUNTIME_TABLE_NAMES` 只是一个字符串集合的 frozenset，这不是"一等公民"，这是"给变量起了个表的名字"。

4. **对"表驱动的粒度"理解有偏差**  
   spec 说"好的表驱动设计应该用少量高度通用的表结构"，方向对了，但给出的 18 张表仍然是按功能领域划分的（内核表/运行时表/规则表/适配器表/分析表/IO表/元表），而不是按**结构模式**划分的。真正的表驱动极致是：**整个系统只有 3-5 种结构模式的表，所有业务语义都通过数据内容表达**。

### 2. 事件驱动纯度（20分 → 12分）

**做得对的地方：**
- "拓扑运行前确定"的核心洞察正确
- 脏标记传播 + 级联触发的方向正确
- 数据更新与计算解耦（latest_tick 独立维护）的思路正确

**核心问题：**

1. **"拓扑运行前确定"只确定了一半**  
   现有代码的 `CompiledSchedule` 已经编译了 `topo_order` / `edge_ctx` / `edge_timing` / `edge_filter_spec` 等，但 spec 的目标设计仍然停留在"编译成 EdgeOp 列表"的层面。**真正的拓扑运行前确定应该是：编译结果是一个线性的指令序列，运行期连"这条边该不该执行"的判断都不需要——指令自己带有守卫条件**。现在的设计里，运行期还要 `op.trigger.check(state)`，这说明"时机触发"的逻辑还在运行期动态决策。

2. **脏标记传播模型过于粗糙**  
   `propagate_dirty` 的设计是：节点脏了 → 遍历所有出边 → 时机检查 → 执行边 → 目标节点变了就标脏。这个模型有三个问题：
   - **粒度太粗**：脏标记是节点级的，不是边级的。一条边执行了但目标节点没变（比如条件边过滤后结果相同），下游边不应该触发，但现在的设计无法表达。
   - **缺少依赖分析**：边的执行除了依赖源节点股票，还依赖行情数据、时间、外部参数等。"节点脏 OR 数据脏"的判断太粗糙。
   - **级联顺序有问题**：按 topo_order 遍历节点，但一个节点可能有多条入边，应该等所有可能触发的入边都执行完再处理出边，而不是遇到一个脏节点就马上处理其出边。

3. **增量计算的"增量"定义不清晰**  
   什么是"增量"？是股票集合的变化？还是股票属性的变化？还是行情数据的变化？spec 里混用了这几种概念。`node_snapshots` 存的是 `frozenset(code)`，只能检测集合变化，检测不到单只股票属性的变化（比如价格变了但股票还在池子里）。对于条件评估来说，股票属性变化才是更常见的触发因素。

4. **事件驱动与规则引擎的关系混乱**  
   spec 说"事件驱动 + 增量计算"是核心原则，但又设计了统一的 ECA 规则引擎。这两者是什么关系？事件驱动的"事件"和规则引擎的"事件"是一回事吗？边触发算事件吗？节点变化算事件吗？tick.end 算事件吗？这些概念没有理清楚，导致架构里有两套"事件"系统。

### 3. 核心精简度（20分 → 11分）

**做得对的地方：**
- 指出现有三段式（pre_tick / flowsCore / post_tick）的问题
- 提出单循环设计的方向
- 认识到 pre_tick 的"数据注入"本质上是源节点更新

**核心问题：**

1. **1000 行目标缺乏可信路径**  
   从 3504 行（不是 spec 说的 3884 行，数据不准确）压缩到 1000 行，意味着要砍掉 71% 的代码。四阶段路线图预估的行数变化：
   - 阶段一：3884 → 2500（减少 1384 行）
   - 阶段二：2500 → 1600（减少 900 行）
   - 阶段三：1600 → 1200（减少 400 行）
   - 阶段四：1200 → 1000（减少 200 行）
   
   但这些数字是拍脑袋的，没有基于实际代码分析。比如"删除旧执行路径"减 800 行，实际旧路径代码有多少？"统一字段解析"减 200 行，现有字段解析代码有多少？没有证据支撑。

2. **核心循环看似简单，实则隐含大量复杂度**  
   spec 给出的 tick 函数只有 4 步，看起来很简洁：
   ```python
   update_latest_tick → mark_source_nodes_dirty → propagate_dirty → fire_rules
   ```
   但 `propagate_dirty` 里面调用 `op.execute(state)`，这个 `execute` 里包含了 filter + propagate + ttl + side_effects。`fire_rules` 里包含了事件/信号/告警/分析/持仓跟踪。**复杂度没有消失，只是被藏起来了**。核心循环的简洁是用"深层嵌套的函数调用"换来的，不是真正的精简。

3. **Engine 类的职责边界不清晰**  
   spec 说 engine.py 目标 1000 行，但 Compiler 放哪里？规则编译器放哪里？EdgeOp 的实现放哪里？如果都放在 engine.py 里，1000 行肯定不够。如果分出去，那"engine.py"的定义是什么？是只包含运行时循环，还是包含编译期？这个边界没有定义清楚，行数目标就没有意义。

4. **"核心方法 ≤ 20 个"的指标毫无意义**  
   方法数量是可以通过"大函数拆小函数"或"小函数合并成大函数"随意操纵的指标。真正重要的是**认知复杂度**和**职责内聚度**，不是方法计数。用方法数量作为精简度指标，说明对"精简"的理解还停留在表面。

### 4. 功能完整性（15分 → 9分）

**做得对的地方：**
- 五套规则系统（事件/信号/告警/高亮/持仓跟踪）的识别准确
- 四象限分类法（A/B/C/D 类表）的分析框架有价值
- 三种运行模式（live/replay/simulation）的统一思路正确

**核心问题：**

1. **向后兼容性几乎没有考虑**  
   现有系统有大量外部依赖：app.py 调用 engine 的接口、UI 层读取运行时表、XML 导入导出、持久化表结构。重构如果改变了 engine 的公共 API、运行时表的结构、配置表的格式，所有这些外部依赖都会断裂。spec 里只在风险部分提了一句"配置表合并导致兼容性问题"，然后说"提供配置迁移工具"。这远远不够。
   
   具体问题：
   - `node_stocks` 的结构变不变？现在每个股票 entry 是 dict，有 `code` / `entry_ts` / `entry_price` / `attrs`，未来呢？
   - 事件对象的格式变不变？`_emit_transfer_events` 生成的事件有哪些字段？
   - 公共方法 `run_pool` / `run_loop` / `run_mode` 的签名变不变？
   - `__getattr__` 代理的旧字段名还保留吗？保留多久？

2. **功能清单不完整，遗漏了很多边缘功能**  
   spec 主要关注核心循环和规则引擎，但很多边缘功能完全没提：
   - 拓扑校验（`_validate_pool_topology`）
   - 候选池刷新（`_check_refreshed_pool_data`）
   - 热加载 / 配置变更检测
   - 数据缓存与 TTL 失效
   - 分钟聚合器
   - 公式依赖排序（`_compute_formula_order`）
   - 能力注册与动态绑定（`_bind_capabilities`）
   - 降级链（fallback_chain）
   
   这些功能在重构后放在哪里？是核心引擎的一部分，还是移到外围服务？

3. **DZH / TDX 适配层的设计太粗糙**  
   说"收敛为 tdx_adapter.json / dzh_adapter.json"，但适配层的职责边界是什么？核心引擎知道 TDX/DZH 的存在吗？还是说适配层在核心引擎之外，做格式转换？如果核心引擎直接读 adapter 表，那"核心"就不纯了。如果适配层在外面，那数据流是怎样的？这些关键问题都没有回答。

4. **持久化层完全被忽略**  
   DESIGN0.md 里明确说了三种表：持久表（SQLite）/ 运行时表（内存 Dict）/ 配置表（JSON 文件）。但 spec 的重构设计里只讨论了配置表和运行时表，持久化层完全没提。重构后持久表的 schema 变不变？`stock_transfer_log` / `node_state` 这些表怎么和新的运行时表对应？事件/信号要不要持久化？这些都没有设计。

### 5. 可执行性（15分 → 7分）

**做得对的地方：**
- 四阶段划分（骨架 → 规则引擎 → 表收敛 → 极致精简）有逻辑
- 每阶段有行数目标和验证标准的意识
- 提到了风险与回退策略

**核心问题：**

1. **路线图是"任务清单"，不是"可执行计划"**  
   每个阶段列了 8-10 个任务，但任务之间的依赖关系是什么？哪些可以并行？哪些有前置条件？完全没有。比如阶段一的 1.4（迁移 _run_tick_event_driven）和 1.6（删除旧执行路径）之间有依赖，但 1.5（简化核心循环）和 1.7（统一字段解析）之间呢？不知道。

2. **验收标准太空洞**  
   "所有现有测试通过"——现有测试有哪些？覆盖了多少功能？行为等价性怎么验证？没有测试策略，"通过测试"就是一句空话。
   
   "事件驱动路径是唯一路径"——怎么证明？是代码里删除了旧路径的函数，还是只是不调用？
   
   "ExecutionPlan 是运行时的唯一输入"——怎么验证？运行期 grep 有没有读取配置表的代码？

3. **风险分析流于表面**  
   只列了 4 个风险：功能回归、兼容性、性能退化、学习成本。每个风险的缓解措施都是一句话。
   
   真正的风险远不止这些：
   - **架构腐化风险**：重构过程中，新旧两套代码并存，会不会越改越乱？
   - **性能风险**：事件驱动的增量计算在某些场景下可能比全量计算更慢（比如所有节点都脏的时候，脏标记传播的开销是额外的）
   - **调试难度增加**：编译期 + 运行期分离，出了问题是编译错了还是执行错了？更难定位
   - **团队共识风险**：新架构的学习曲线陡不陡？团队成员能不能达成一致理解？
   - **范围蔓延风险**：重构过程中不断发现"这个也顺便改了吧"，导致工期无限延长

4. **没有回退计划的细节**  
   "每阶段完成后跑全套测试，保留行为等价性测试"——行为等价性测试在哪里？怎么构建 oracle？如果阶段一完成后发现性能退化了 50%，怎么回退？回退到什么状态？需要多长时间回退？这些都没有。

5. **缺少资源评估**  
   四阶段重构需要多少人天？几个人做？优先级怎么排？和业务需求怎么平衡？这些实际问题完全没有考虑。架构设计不是画饼，是要落地的。

## 二、具体改进建议（15 条）

### 高严重度（必须解决，否则架构站不住脚）

#### 建议 1：明确 EdgeOp 的本质——是 opcode 列表，不是对象组合
- **问题描述**：当前 EdgeOp 设计是"触发器对象 + 过滤器对象 + 传播器对象"的组合，本质上是把函数调用打包成数据结构，逻辑仍在代码里。
- **严重程度**：🔴 高（决定了表驱动的深度）
- **改进方向**：
  - 把 EdgeOp 设计成**线性指令序列**（类似字节码），每条指令有 opcode 和操作数
  - 执行器是一个简单的循环：`for instr in op.instructions: execute_instr(instr, state)`
  - 条件边和无条件边的区别**只在于指令序列的不同**，执行器不区分边类型
  - 示例：无条件边 = [COPY_SRC, PROPAGATE, UPDATE_SNAPSHOT]；条件边 = [COPY_SRC, EVAL_FILTER, IF_PASS_PROPAGATE, UPDATE_SNAPSHOT]

#### 建议 2：重新定义"脏"的粒度——从节点级到边级 + 数据依赖
- **问题描述**：节点级脏标记太粗糙，无法表达"某条边的输入变了但其他边没变"的情况，导致不必要的重计算。
- **严重程度**：🔴 高（决定了事件驱动的效率）
- **改进方向**：
  - 脏标记从节点级改为**边级**：每条边有自己的 dirty flag
  - 边的脏 = 源节点变化 OR 依赖的行情字段变化 OR 依赖的参数变化
  - 编译期分析每条边的数据依赖（读了哪些行情字段、哪些配置参数）
  - 运行期只对真正"输入变了"的边做触发检查

#### 建议 3：理清"事件驱动的事件"和"规则引擎的事件"的关系
- **问题描述**：架构中有两套事件概念——事件驱动增量计算的"变更事件"和 ECA 规则引擎的"业务事件"，两者关系混乱。
- **严重程度**：🔴 高（概念不清会导致实现混乱）
- **改进方向**：
  - 明确区分两个层级：**底层的变更传播层**（脏标记、级联触发）和**上层的业务事件层**（ENTER/EXIT/告警等）
  - 变更传播层是机制，不是业务；业务事件层是策略，由规则引擎定义
  - 业务事件可以订阅变更传播层的事件（如 node.enter / node.exit），但两者不是一回事
  - 在文档中用明确的术语区分，不要都叫"事件"

#### 建议 4：定义清晰的向后兼容策略与迁移路径
- **问题描述**：spec 对向后兼容性几乎没有考虑，实际重构中这是最大的风险之一。
- **严重程度**：🔴 高（决定了重构能否安全落地）
- **改进方向**：
  - 列出所有公共 API（方法签名、参数、返回值），标记哪些变哪些不变
  - 列出所有运行时表的 schema，标记变更策略（保留旧字段/提供迁移脚本）
  - 设计**双轨运行期**：新旧两套引擎可以并行运行，对比结果，验证一致性
  - 明确 deprecation 策略：旧 API 保留几个版本？什么时候删除？

#### 建议 5：补全功能覆盖清单，明确哪些在核心内哪些在外围
- **问题描述**：spec 只关注核心循环和规则引擎，大量边缘功能（拓扑校验、热加载、数据缓存、分钟聚合器等）的归属不明确。
- **严重程度**：🔴 高（功能遗漏会导致架构不完整）
- **改进方向**：
  - 做一次完整的功能审计：列出 engine.py 中所有 120+ 方法，逐个判断重构后放在哪里
  - 明确核心引擎的边界：什么是核心必须有的，什么可以移到外围服务
  - 建立"核心 vs 外围"的判断标准：是否影响核心循环的正确性？是否可以通过插件机制扩展？

---

### 中严重度（重要，但不影响架构骨架）

#### 建议 6：给 1000 行目标提供代码级的证据支撑
- **问题描述**：1000 行目标缺乏依据，现有代码 3504 行（不是 3884 行），每一行砍掉的理由是什么？
- **严重程度**：🟡 中（目标不具体会导致无法衡量进度）
- **改进方向**：
  - 对 engine.py 做一次逐函数分析，标记每个函数重构后：删除 / 合并 / 迁移 / 保留
  - 做一个行数预估表：旧函数 X 行 → 新设计 Y 行，理由是什么
  - 明确 Compiler 代码、EdgeOp 代码、规则引擎代码分别放在哪些文件，各约多少行

#### 建议 7：设计统一的运行时表访问接口
- **问题描述**：运行时表的"一等公民"设计停留在命名层面，没有统一的访问接口和生命周期管理。
- **严重程度**：🟡 中（影响可维护性和一致性）
- **改进方向**：
  - 设计 `RuntimeState` 类，封装所有运行时表的访问
  - 提供统一的 API：`state.get(table, key)` / `state.set(table, key, value)` / `state.query(table, predicate)`
  - 每张表有明确的 schema 定义，读写时做校验（至少在 debug 模式下）
  - 表的生命周期（初始化 / 重置 / 持久化 / 销毁）有明确的钩子

#### 建议 8：细化脏标记传播的算法设计
- **问题描述**：propagate_dirty 的算法太粗糙，没有考虑多入边汇聚、边执行顺序、部分变更等情况。
- **严重程度**：🟡 中（影响事件驱动的正确性和效率）
- **改进方向**：
  - 明确传播算法：是 BFS 还是 DFS？还是按拓扑层级的 level-synchronous？

  - 设计"变更集"概念：不仅标记"脏不脏"，还标记"什么变了"（哪些股票新增/删除/属性变更）

#### 建议 9：明确规则引擎的执行模型——pull 还是 push？
- **问题描述**：ECA 规则引擎的执行模型不清晰。是定时轮询检查条件（pull），还是事件触发时检查（push）？
- **严重程度**：🟡 中（影响性能和实现复杂度）
- **改进方向**：
  - 明确规则的触发方式：事件触发型（事件发生时检查条件） vs 轮询型（定时检查条件）
  - 对于事件触发型，规则在编译期就订阅到具体的事件类型上，运行时事件发生时直接调用订阅者
  - 对于轮询型（如 tick.end 的分析规则），明确触发时机和频率
  - 不要设计成"所有规则每次 tick 都检查一遍"，那样性能太差

#### 建议 10：设计编译期的分层架构
- **问题描述**：Compiler 只是一个黑盒，输入 pool_config 输出 ExecutionPlan，内部结构不清晰。
- **严重程度**：🟡 中（影响可维护性和可扩展性）
- **改进方向**：
  - 编译期分阶段：解析 → 验证 → 中间表示（IR）→ 优化 → 代码生成（ExecutionPlan）
  - 每个阶段有明确的输入输出和职责
  - 优化阶段可以做：死代码消除（从未触发的边）、常量折叠（编译期能算的就算好）、指令重排（优化执行顺序）
  - 设计中间表示（IR），让优化阶段可以在 IR 上做变换

## 三、设计中最深刻的洞见（3 条）

### 洞见 1："逻辑隐含于表结构，差异显示于表内容"——对表驱动本质的把握
这是整个 spec 最有价值的一句话。它点出了表驱动的精髓：**不是用表来选择执行哪个函数，而是用表的结构本身来定义执行逻辑**。现有代码的问题确实是"表驱动只做了一半"——把 if/else 换成了查表调用 handler，但 handler 里还是硬编码的逻辑。如果这个洞见能真正贯彻到设计中，整个架构的质量会上一个台阶。

但遗憾的是，spec 自己的设计也没有完全做到这一点。EdgeOp 还是"对象组合"而非"结构蕴含"。这说明提出这个洞见的人自己也还在探索中。

### 洞见 2："拓扑运行前确定"——编译期/运行期分离的核心认知
"股票池的拓扑结构在运行期间不会改变"——这个观察虽然简单，但它是整个事件驱动架构的基石。基于这个观察，才能把所有静态计算（拓扑排序、边类型判断、触发规则解析、过滤规则编译）都移到编译期，运行期只做纯执行。

现有代码的 `CompiledSchedule` 已经在往这个方向走了，spec 把它提升为第一原则，是正确的。如果能再进一步——把"时机触发"也编译成执行计划的一部分（而不是运行期每次检查），那才是真正的"运行前确定"。

### 洞见 3："五套规则系统本质上都是 ECA"——统一抽象的穿透力
事件、信号、告警、高亮、副作用，这五套系统看起来各有各的触发机制和处理逻辑，但 spec 看穿了它们的共同本质：**"当X发生时，如果Y条件满足，就执行Z动作"**。这个统一抽象非常有价值，如果能真正实现，代码量的减少会是实质性的，不只是物理合并。

更重要的是，统一规则引擎意味着新增业务规则不需要改 Python 代码，只需要加 JSON 配置——这才真正符合"新增功能 = 加 JSON 条目，零行 engine.py 改动"的表驱动目标。

## 四、设计中最肤浅的理解（3 条）

### 肤浅 1：把"表驱动"理解为"配置表合并同类项"
spec 花了很大篇幅讲"从 90 张表收敛到 18 张表"，但收敛的方式是"功能相近的合并"——事件/信号/告警合并为 rules.json，TDX 适配表合并为 tdx_adapter.json。这是**物理合并**，不是**化学融合**。

真正的表驱动提升应该是**抽象层级的提升**：找到更底层的结构模式，让一张表能承载原来 10 张表的语义。比如，如果所有的表都遵循"键-值-时间戳"的三元组模式，那整个系统可能只需要 3-5 种结构模式的表。

90 张表到 18 张表的收敛，更多的是"整理文件目录"，而不是"提升表驱动深度"。用这个作为表驱动的成果，说明对表驱动的理解还比较浅。

### 肤浅 2：核心循环的"精简"是把复杂度藏起来了
spec 展示的 tick 函数只有 4 步，看起来非常简洁：
```
update_latest_tick → mark_source_nodes_dirty → propagate_dirty → fire_rules
```

但这是典型的"冰山错觉"——水面上的部分很小，水面下藏着巨大的体积。`propagate_dirty` 里的 `op.execute()` 包含了 filter + propagate + ttl + side_effects，`fire_rules` 里包含了 5 套规则系统的所有逻辑。

**复杂度没有消失，只是被移动和隐藏了。** 真正的精简应该是**减少需要理解的概念数量**，而不是把多个概念打包成一个黑盒然后说"看，只有一个概念"。

如果算上 Compiler、EdgeOp 体系、规则引擎的代码，总代码量可能并没有减少多少，只是从 engine.py 分散到了更多文件里。

### 肤浅 3：对"增量计算"的理解停留在"脏标记 + 跳过"
spec 对增量计算的设计是：节点脏了就处理，不脏就跳过。这是增量计算最基础的形式，叫**保守增量计算**——只要输入可能变了就重算，不管输出到底变没变。

真正的增量计算应该是**精确增量计算**：
- 知道输入的**具体变化**是什么（哪几只股票新增、哪几只删除、哪几只的哪个属性变了）
- 能根据输入变化**直接计算输出变化**（不需要重算整个集合）
- 变更的传播是**变更集的传播**，不是"脏标记"的传播

当然，精确增量计算实现复杂度高很多，不一定非要一步到位。但 spec 把"脏标记跳过"当成了事件驱动增量计算的全部，说明对这个领域的理解还比较初级。

## 六、总结评语

这份 spec 的**方向感是对的**——表驱动要深化、事件驱动要提纯、核心要精简、规则要统一。这些都是正确的架构演进方向。

但**深度严重不足**。很多设计停留在"给现有代码起个新名字"或"把多个函数打包成一个对象"的层面，没有触及真正的架构提升。比如：
- EdgeOp 不是"结构蕴含逻辑"，只是"把函数调用写成数据结构"
- 18 张表不是"提升抽象层级"，只是"合并同类项"
- 核心循环的精简不是"减少复杂度"，只是"隐藏复杂度"

**给作者的建议**：
1. 少谈"目标"（1000 行、18 张表），多谈"机制"（怎么做到、为什么这样设计）
2. 少做"分类整理"（四象限、七层表），多做"抽象提升"（找到统一的结构模式）
3. 先把概念理清楚，再画架构图。概念不清的图，再好看也是空中楼阁

**总体评价**：
这是一份"有想法但没吃透"的设计文档。作者有很好的直觉，能嗅到现有架构的问题，但对表驱动、事件驱动、增量计算这些核心概念的理解还不够深入，导致设计浮于表面。建议下一轮迭代先做概念澄清和功能审计，把基础打牢了再往上建。
