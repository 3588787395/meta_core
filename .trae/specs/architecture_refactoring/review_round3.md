## 二、分项详细评审

### 1. 表驱动深度（22/30）

#### 1.1 EdgeVM 通用化：形似神不似（7/12）

**声称的突破**：从20+领域opcode → 12个通用opcode + 领域库函数

**严厉检查**：

**（1）opcode确实通用了，但VM模型不通用**

12个opcode（LOAD/STORE/PUSH/POP/ADD/SUB/JMP/JZ/JNZ/CALL/RET/NOP）从命名上看是通用的。但**VM的内存模型直接与三元组存储硬绑定**：

```
地址格式：
  e:<entity>:<attr>  → 直接映射到 RuntimeState.get(entity, attr)
  g:<key>            → 直接映射到 RuntimeState.get_meta(key)
```

这不是通用VM的设计。通用VM（如JVM、Lua VM、Python VM）有**通用的内存模型**：线性堆、栈帧、全局变量区。而EdgeVM的LOAD/STORE**直接绕过通用内存，操作领域状态**。

**结论**：EdgeVM知道"实体-属性-值"这个特定存储模型，它不是通用VM，是"绑定了EAV存储模型的专用解释器"。

**（2）"VM不知道股票池"——正确但无意义**

文档反复强调"VM不知道股票池"。技术上没错，但VM知道"EAV三元组"、知道"节点属性"、知道"全局元数据"——这些都是本系统的领域概念。

这就像说"CPU不知道银行业务，只知道0和1"——正确，但没有架构意义。真正的通用VM应该能跑任何领域的程序，而不只是"换一套库函数就能跑"。

**（3）ADD/SUB 两个算术指令就够了？**

文档里说有ADD和SUB，但表3.2.1里只列了ADD、SUB，没有MUL、DIV。示例代码里也只实现了ADD和SUB。如果真要做通用VM，最基本的算术指令集应该完整吧？

当然，可以说"乘法用库函数实现"——但如果连基本算术都要靠库函数，那VM的"通用性"体现在哪里？

**（4）库函数注册机制简陋**

当前设计是 `lib_fns[fn_id] = fn`，函数通过 `fn(self.state, *args)` 直接访问整个state。这意味着：
- 库函数可以随意读写任何状态，没有权限隔离
- 库函数和VM紧耦合（必须接收state作为第一个参数）
- 无法做沙箱、无法做权限控制

真正的VM扩展机制应该是通过VM提供的API来访问状态，而不是直接把state塞给库函数。

#### 1.2 配置表化学融合：分类≠融合（7/10）

**声称的突破**：从18张表 → 4种结构模式（化学融合）

**严厉检查**：

**（1）这是"分类学"，不是"化学融合"**

把18张表按结构归入4类（字典/规则/关系/枚举），这叫**分类**，不叫**融合**。

化学融合的定义应该是：**用一个统一的元模型（meta-model）来描述所有配置，不同配置之间的差异只在数据内容，不在结构模式**。

现在的状态是：4种模式，每种模式有自己的结构、自己的操作接口、自己的schema。这和"18张表分成4组"没有本质区别。

**（2）规则表ECA结构的牵强附会**

文档声称"时机、过滤、TTL、高亮、告警——本质上全都是ECA规则的不同形式"。让我们逐一检验：

| 配置类型 | when（事件） | if（条件） | then（动作） | 牵强程度 |
|---------|-------------|-----------|-------------|---------|
| 业务规则 | node.enter等 | 业务条件 | 发信号/告警 | 合理 |
| 时机规则 | "时间到达" | 在交易时间内？ | 允许边执行 | ⚠️ 牵强 |
| 过滤规则 | "边执行时" | 价格/量/公式 | 保留/移除股票 | ⚠️ 非常牵强 |
| TTL规则 | "tick" | 入池时间 > TTL？ | 移除股票 | ❌ 硬凑 |

问题：
- **时机规则**：时间是持续流逝的，不是"事件"。"时间到达"是一个连续过程，不是离散事件。
- **过滤规则**："边执行时"作为事件？那函数调用也算事件了？照这个逻辑，任何函数都是ECA——when=被调用, if=参数满足, then=返回结果。这是对ECA概念的滥用。
- **TTL规则**："tick"作为事件？那系统里所有周期性操作都是ECA规则了。

**结论**：为了凑"4种模式"而把差异巨大的东西硬塞进ECA框架，是削足适履。

**（3）关系表和字典表的界限模糊**

edges.json 被归为"关系表"（src-dst-attrs），但它同时也可以看作是"以edge_id为key的字典表"。

同样，node_type_hierarchy.json 是关系表，但如果用字典表表示（子类型为key，父类型为值）也完全可以。

这说明：4种模式之间的界限不是清晰的，很多表可以归入多种模式。这不是"化学融合"应有的状态——化学融合应该有清晰、正交的元模型。

**（4）为什么是4种？不是3种或5种？**

文档说"4种模式不是拍脑袋的，是从18张表中归纳出来的"。但归纳法的问题是：如果你归纳的样本本身就有偏差，归纳结果也会有偏差。

- 为什么没有"列表/序列表"模式？（比如交易时段列表、节假日列表）
- 为什么没有"树/层级表"模式？（比如板块层级、行业分类）
- 为什么没有"状态机表"模式？

答案是：因为当前18张表里这些模式不明显。但"化学融合"应该面向未来，而不是只归纳过去。

#### 1.3 运行时表统一：EAV是手段不是目的（8/8）

**声称的突破**：从8张表8种结构 → 统一三元组模型

**严厉检查**：

这一项是本轮**最扎实**的改进。EAV三元组模型确实统一了运行时状态的访问接口。

**仍然存在的疑虑**：

**（1）行情数据用EAV是反模式**

`latest_tick` 拆成每个字段一个三元组：
```
("stock:600001", "close", 12.34)
("stock:600001", "volume", 10000)
("stock:600001", "open", 12.00)
...
```

查询一只股票的5个字段需要5次get操作。而原来的结构体只需要1次。

在行情数据高频访问的场景下，这个性能损失可能很大。文档只轻描淡写地说"单值查询性能略低"，但实际影响需要量化评估。

**（2）value仍然可以是任意复杂类型**

EAV模型的"纯度"取决于value是否是原子值。当前设计中，value可以是list、dict、set等任意复杂类型：
- `("node:src_1", "stocks", [StockEntry(...), ...])` — value是列表
- `("cs:edge:e1", "added", frozenset({...}))` — value是集合

这本质上是"两层字典 + 复杂值"，不是纯EAV。纯EAV应该是：
```
("node:src_1:stock:600001", "entry_ts", 12345.0)
("node:src_1:stock:600001", "entry_price", 10.5)
...
```

当然，纯EAV性能更差。我同意当前的折中方案是合理的，但不要把它包装成"极致的EAV三元组模型"——它是"以实体为粒度的KV存储"。

**（3）便捷API层说明什么？**

RuntimeState对外提供了 `get_node_stocks`、`get_tick_field`、`get_edge_state` 等便捷API。

这说明什么？说明**使用者还是需要按"表"的思维来访问数据**，三元组模型只是内部实现细节。如果三元组模型真的那么自然，为什么还需要一层"表式访问"的包装？

**评分说明**：这一项给满分（8/8），因为EAV确实统一了底层存储，而且文档也坦诚了性能trade-off。扣分项在EdgeVM和配置表那边。

### 2. 事件驱动纯度（16/20）

#### 2.1 变更集语义：有进步但自相矛盾（6/8）

**亮点**：
- 变更集的形式化定义（四元组 + 不变性约束）做得不错
- union/compose/intersect/diff四个基本运算都有定义
- 定理6.1和6.2（应用一致性、合并交换律结合律）正确

**严重问题**：

**（1）OR汇聚语义自己推翻了自己**

第6.2.2节用了很大篇幅定义union运算，然后举了个例子，然后——**自己发现union是错的**。

```
啊！这里有差异！说明简单的 union 不对。
...
正确的 OR 汇聚变更集计算方式：
  1. 计算节点的当前状态 S_new = 所有入边作用后的结果
  2. 计算节点的上次状态 S_old
  3. cs_node = (S_new \ S_old, S_old \ S_new, {}, v)
```

那前面定义的union运算有什么用？文档说"union是近似"——近似的数学定义还叫形式化吗？

**结论**：变更集代数的核心运算（汇聚）没有正确的代数定义，最后还是靠"全量计算 + 差集对比"。这不是增量，这是"算完了再告诉你哪些变了"。

**（2）定理6.4是正确的废话**

> **定理6.4（增量计算的正确性）**：在以下假设下，增量计算的结果与全量计算的结果完全一致：
> 1. 每条边的函数 f 是确定的
> 2. 变更集的应用是正确的
> 3. 传播顺序符合拓扑顺序

这就像说"如果你按正确的顺序做正确的事，结果就是正确的"——当然正确，但没有信息量。

真正需要证明的是：**变更集的增量维持是正确的**。即：给定输入变更集cs_in，函数f的增量版本输出的cs_out，与"先应用cs_in再全量计算f再做差"的结果一致。

这个才是增量计算正确性的核心。而文档完全没有证明这个。

**（3）modified字段的模糊地位**

变更集四元组有added、removed、modified三个集合。但：
- apply函数只用到added和removed（modified不影响成员关系）
- union/compose/intersect运算中modified的处理很简单
- modified到底是"属性变更但仍在集合中"还是"任何属性变更"？

文档说"modified不影响集合成员关系，只影响属性"——那modified是给谁用的？是给增量filter用的？如果是，那它的语义应该和filter的增量算法绑定定义，而不是孤立地定义在变更集里。

#### 2.2 精确增量：有filter增量，其他都没落地（5/7）

**亮点**：
- set.filter的增量算法有具体伪代码，逻辑清晰
- 增量/全量降级策略有提及
- 粒度层级（节点级→边级→集合级→属性级→指令级）的划分合理

**严重问题**：

**（1）EdgeVM如何支持增量？完全没说**

这是最核心的问题。文档花了大量篇幅定义EdgeVM的指令集、语义、示例，但**所有示例都是全量模式**。

增量模式下，一条边的指令序列应该是什么样的？
- 变更集如何传入指令序列？
- 是作为额外参数传给CALL？
- 还是有专门的增量指令？
- 指令序列如何判断该走全量还是增量？
- 如果中间某一步不支持增量，如何降级？

文档说"函数有两种模式：全量模式和增量模式"，但**EdgeVM的CALL指令如何区分两种模式**？是靠参数数量？还是靠不同的fn_id？还是有专门的CALL_INCREMENTAL指令？

**结论**：精确增量和EdgeVM是脱节的。增量只在库函数层面设计了，没有融入VM执行模型。

**（2）除了filter，其他操作的增量都没设计**

文档的表格里列了7个集合操作的增量支持情况：

| 操作 | 支持增量？ |
|------|-----------|
| set.copy | 不需要 |
| set.filter | ✅ 支持 |
| set.intersect | ✅ 支持（然后说"比较复杂，先用全量模式"） |
| set.union | ✅ 支持（没有具体算法） |
| set.diff | ✅ 支持（没有具体算法） |
| set.move | ✅ 支持（没有具体算法） |
| set.changes_since | 生成变更集 |

实际上，**只有filter有具体的增量算法**。其他三个打了勾的，要么"复杂所以先用全量"，要么只有名字没有实现。

**（3）变更集沿边传播机制缺失**

增量计算的核心是"变更集沿着边传播"。但文档里：
- 传播算法（第6.4节）里的 `execute_edge_program` 接收 `input_change_set`，但如何使用？
- 节点的变更集如何传递给出边？
- 多条入边的变更集如何合并后传给下一层？

这些关键机制都没有详细设计。

**（4）降级策略只有一句话**

"如果变更集太大（超过阈值），自动降级到全量模式"——阈值是多少？怎么判断变更集大小？按元素数量？按比例？降级后下一次如何恢复增量？

都没有说。

#### 2.3 数据依赖：覆盖面全，但深度不足（5/5）

这一项做得不错。五个维度（数据/集合/状态/参数/时间）的划分合理，DataDeps数据结构清晰，脏标记判定逻辑完整。

**小瑕疵**：
- D5时间依赖是"每次tick都检查"——等于没有优化。更精确的做法应该是计算"下次时间相关变化发生的时刻"，到那时才触发。
- D3状态依赖的脏标记机制太弱（只有"state_externally_modified"一个标志），没有细粒度的状态字段级脏标记。

但整体来说，五维依赖是本轮最扎实的改进之一。

### 3. 核心精简度（14/20）

#### 3.1 概念数量：明减暗增（5/10）

**声称**：从~15个核心概念 → ~8个核心概念

**列出的8个概念**：
1. EdgeVM
2. RuntimeState
3. ChangeSet
4. Propagator
5. ExecutionPlan
6. Library Functions
7. Data Dependencies
8. Tick Cycle

**严厉检查**：

**（1）这8个概念不在同一个抽象层级**

- Tick Cycle：这是最基础的运行模式，不算架构概念
- Library Functions：是EdgeVM的扩展机制，不是独立概念
- Data Dependencies：是编译期分析结果，依附于ExecutionPlan

如果剔除这些，真正独立的核心概念是5个：EdgeVM、RuntimeState、ChangeSet、Propagator、ExecutionPlan。

**（2）但编译期增加了大量概念**

编译期五阶段：Parser、Validator、IRGen、Optimizer、CodeGen——这就是5个新概念。

加上：
- EdgeIR（中间表示）
- SSA风格（如果真的做的话）
- 4种配置表模式
- 5种依赖类型
- 9个ADR...

**结论**：从"147个方法堆在一个文件里"变成"分层架构 + 众多概念"。engine.py的概念少了，但**整个系统的概念数反而增多了**。

当然，概念增多不一定是坏事——分层架构本来就需要更多概念。但**不要声称"核心概念从15个减到8个"，这是误导**。正确的说法是"核心运行时概念精简了，但编译期和整体架构概念增多了，这是分层的代价"。

#### 3.2 认知复杂度：学习曲线陡增（4/6）

旧架构：新人读3884行的engine.py，虽然长但是平铺直叙，顺着读就能懂。

新架构：新人需要理解：
- 编译期/运行期分离
- EdgeVM栈式虚拟机模型
- 三元组状态模型
- 变更集代数
- 层级同步BFS传播
- ECA规则引擎
- 五维依赖分析
- 4种配置模式

**认知复杂度显著升高**。

当然，长期来看，统一模型的维护成本更低。但短期内，团队的学习成本是真实存在的。

文档对此没有足够的坦诚。

#### 3.3 代码量：engine.py瘦了，但系统胖了（5/4？不，5/4超了，应该是5/4不对，重算）

让我重新评估：engine.py从3884行降到~700行，这是事实。

但新增的代码：
- compiler/: ~770行
- rules.py: ~350行
- table_engine.py: ~600行（重构后）
- runtime_state.py: ~250行
- adapters/: ~500行
- persistence/: ~250行
- services/: ~600行
- utils/: ~350行
- 其他模块: ~600行

**核心相关代码总量**：700+770+350+600+250 = 2670行（还只是核心部分）

加上外围模块，总代码量可能超过5000行，比原来的3884行还多。

当然，这是"代码从一个文件分散到多个模块"，不是"代码量变多"——原来的代码也有这些功能，只是混在一起。

但**"精简"的说法需要澄清**：是engine.py精简了，不是整个系统精简了。整个系统因为分层和模块化，代码量可能还会略有增加（因为接口、抽象、错误处理都变多了）。

### 4. 功能完整性（13/15）

#### 4.1 持久化层：骨架完整，细节不足（5/6）

**亮点**：
- 6张持久表都有设计
- 冷启动恢复流程清晰
- 运行时统一/持久化分表的决策合理（ADR-007）

**不足**：
- 没有持久化选型（SQLite? LevelDB? JSON文件?）
- 没有事务保证（一个tick内的多次修改如何原子化？）
- 增量恢复策略粗糙（恢复后第一个tick走全量）
- 没有持久化的性能影响评估（每tick写盘的开销如何？）

#### 4.2 适配层：有骨架，缺血肉（4/5）

**亮点**：
- 核心引擎与平台解耦的方向正确
- 三个接口（数据输入、配置翻译、输出格式化）划分合理
- 编译期做大部分转换的思路正确

**不足**：
- 文档自己承认"适配层详细设计"是不足的
- TDX特有逻辑的处理表太简单，没有具体的转换规则
- 没有提到平台特有API的适配（如TDX的tq_adapter具体怎么注入）
- 适配层的错误处理、异常传播都没有设计

#### 4.3 边缘功能覆盖：审计细致，外围设计粗（4/4）

功能审计表做得很细致，147个方法逐一分类，去向明确。这是文档的亮点之一。

外围服务（services/、data/、analytics/等）只有目录结构，没有详细设计。但这些属于"外围"，不在核心架构范围内，可以后续补充。

### 5. 可执行性（13/15）

#### 5.1 任务拆解：细致但偏乐观（5/6）

**亮点**：
- 六阶段划分合理
- 每个阶段都有任务清单、依赖图、关键路径
- 任务粒度适中

**问题**：
- 人天估算偏乐观。65-80人天完成这么大的重构，而且保证正确性，难度很大。
  - 阶段一：10-12人天（骨架+原型+双轨+API兼容）——偏紧
  - 阶段三：15-18人天（编译器+配置融合+迁移工具）——偏紧
  - 阶段四：12-15人天（精确增量+持久化）——偏紧
- 没有考虑测试、Code Review、文档编写的时间
- 没有风险缓冲时间
- 没有人力配置说明（几个人做？全职还是兼职？）

#### 5.2 验收标准：有量化但可操作性待加强（4/5）

每个阶段都有量化验收标准，这是进步。

问题：
- 很多验收标准用了"✅"标记，容易让人误以为已经完成
- "跑通5个测试池配置"——哪5个？复杂度如何？没有定义
- "双轨shadow模式连续运行1000个tick"——用什么数据？真实行情还是模拟数据？
- "性能提升≥5倍"——在什么场景下？测试方法是什么？

#### 5.3 风险应对：全面但偏泛（4/4）

9个风险点，每个都有影响/概率/缓解措施，覆盖全面。

缓解措施大多是正确的方向，但比较泛。比如"严格的模块边界 + 每阶段结束后清理 + code review + ADR约束"——这些都是正确的废话，谁都知道要做，但具体怎么做？

不过风险分析做到这个程度已经不错了，不苛求。

## 三、10条具体改进建议

### 建议1（P0）：明确EdgeVM的定位——是"领域专用VM"，不要硬撑"通用VM"

**问题**：当前EdgeVM的内存模型与EAV三元组紧耦合，不是真正的通用VM。硬叫"通用VM"只会带来混淆。

**建议**：
- 改叫"MetaVM"或"PoolVM"，明确它是为本系统定制的虚拟机
- 如果真的想做通用VM，设计通用内存模型（线性地址空间 + 栈帧），EAV状态通过库函数访问，而不是通过LOAD/STORE直接操作
- 两者选其一，不要含糊

### 建议2（P0）：闭环"增量 + VM"的设计

**问题**：精确增量和EdgeVM是脱节的。增量只在库函数层面，没有融入VM执行模型。

**建议**：
- 设计增量模式下的指令序列结构
- 明确CALL指令如何传递变更集、如何返回变更集
- 设计全量/增量模式的切换机制（指令级？函数级？边级？）
- 给出一个完整的"增量模式边执行"示例（从输入变更集到输出变更集）

### 建议3（P0）：修正变更集代数——要么证明union正确，要么删除

**问题**：OR汇聚的union运算被自己举例证伪了。形式化定义不能有"近似正确"的东西。

**建议**：
- 方案A：放弃"变更集代数"的提法，承认汇聚时需要全量计算 + 差集对比。变更集只用于"标记哪些变了"，不用于"代数运算"。
- 方案B：找到正确的汇聚运算（可能不是简单的union，需要考虑边的执行顺序和相互作用），并证明其正确性。
- 无论选哪个，都要删掉那个"自己发现错误"的例子，或者把它放在"常见误区"里。

### 建议4（P1）：配置表"化学融合"走到底——设计统一的配置元模型

**问题**：4种模式是分类，不是融合。

**建议**：
- 设计一个**统一的配置元模型**（Config Meta-Model），用它来描述所有配置
- 4种模式可以作为元模型的"特化"或"视图"，但底层是统一的
- 例如：所有配置都可以表示为"实体-关系-属性"图，字典表是单实体无关系，关系表是两实体有关系，规则表是带条件的关系...
- 如果做不到统一，就坦诚地说"我们把配置分成4类"，不要叫"化学融合"

### 建议5（P1）：重新审视"规则表ECA"的适用边界

**问题**：把时机、过滤、TTL都硬塞进ECA框架，是削足适履。

**建议**：
- 业务规则（事件/信号/告警）：保留ECA结构，合理
- 时机规则：单独一类（时间调度类），不要硬凑ECA
- 过滤规则：作为"边的属性"或"库函数参数"，不是规则
- TTL规则：作为"集合操作的参数"，不是规则
- 规则表只存真正的"业务事件-条件-动作"规则

### 建议6（P1）：补充行情数据的性能评估

**问题**：EAV模型对行情数据的性能影响被低估了。

**建议**：
- 做一个基准测试：用EAV存1000只股票的20个行情字段，对比结构体存储的读写性能
- 如果性能差距超过30%，考虑优化方案：
  - 方案A：行情数据单独用结构体存储，不纳入三元组
  - 方案B：引入列存格式（按字段存，而不是按股票存）
  - 方案C：增加缓存层（整只股票的字段缓存）
- 在架构文档中明确性能trade-off

### 建议7（P1）：补充完整的增量操作算法

**问题**：只有filter有增量算法，其他操作要么"复杂所以先用全量"，要么没有实现。

**建议**：
- 至少给出set.union和set.diff的增量算法（这两个应该不难）
- set.intersect如果真的复杂，明确写"v0.4不支持，走全量降级路径"，不要打勾然后说"先用全量"
- 每个增量算法都要有：输入输出定义、伪代码、正确性说明、复杂度分析

### 建议8（P2）：澄清"核心概念数"的计算方式

**问题**：声称从15个减到8个，但实际系统概念数增多了。

**建议**：
- 明确区分"核心运行时概念"和"整体架构概念"
- 核心运行时概念：EdgeVM、RuntimeState、ChangeSet、Propagator（4个，比之前少）
- 整体架构概念：加上编译期5阶段、规则引擎、依赖分析、配置模式...（比之前多）
- 坦诚说明："运行时概念精简了，但整体架构因为分层，概念增多了，这是正常的trade-off"

### 建议9（P2）：补充持久化选型和事务设计

**问题**：持久化层只有表结构，没有选型和事务保证。

**建议**：
- 明确持久化存储选型（SQLite? LevelDB? 自定义二进制格式?）
- 设计事务机制：一个tick内的所有状态修改如何原子化持久化？
- 设计WAL（预写日志）或类似机制，确保崩溃后能恢复
- 增加持久化性能评估（写入延迟、吞吐量、存储空间）

### 建议10（P2）：增加人天估算的可信度

**问题**：65-80人天的估算偏乐观，且没有依据。

**建议**：
- 每个任务给出更细的拆解（至少到半天粒度）
- 增加测试时间（至少占总工作量的30%）
- 增加风险缓冲（至少20%）
- 明确人力配置（几个人、什么角色、是否全职）
- 给出"乐观/中性/悲观"三种估算

## 四、3条最深刻洞见 vs 3条最肤浅理解

### 最深刻的3条洞见

**洞见1：表驱动的三层次统一——配置、运行时、执行层**

> "三个层次都统一了，才是真正的'表驱动架构'。每一层都遵循'结构统一，语义在数据'的原则。"

这条洞见是对的。表驱动不是某一层的事，而是整个架构的方法论。配置层统一模式、运行时统一状态模型、执行层统一指令集——三层都做到了，架构的一致性才高。

**洞见2：增量计算的本质是变更集代数**

> "增量计算不是'跳过不脏的边'这么简单，它的数学基础是变更集代数。"

方向是对的。虽然当前的变更集代数还不成熟（union被自己证伪了），但**找到正确的数学基础是关键的第一步**。很多增量系统做不好，就是因为没有清晰的变更集语义，全靠 ad-hoc 的逻辑堆。

**洞见3：化学融合的关键是找到"原子模式"**

> "物理合并是'把相似的放一起'，化学融合是'找到共同的底层结构'。"

这个判断非常准确。物理合并和化学融合的本质区别，就是"是否找到了共同的元模型"。虽然当前4种模式还没做到真正的化学融合，但这个方向是对的。

---

### 最肤浅的3条理解

**肤浅1："VM不知道股票池" = VM通用**

VM知道EAV三元组、知道节点属性、知道全局元数据——这些都是本系统的领域概念。"不知道股票池名称"不等于"通用"。

真正的通用VM是：你给它一套指令和内存，它能跑任何计算，不需要知道"实体"、"属性"这些概念。当前EdgeVM的LOAD/STORE直接操作EAV，说明VM和领域模型是紧耦合的。

**肤浅2：4种模式 = 化学融合**

分类≠融合。把18张表分成4类，叫"物理合并的升级版"，不叫"化学融合"。

化学融合应该是：**用一个统一的元模型描述所有配置，不同配置只是元模型的不同实例化**。4种模式应该是元模型的4种"视图"或"特化"，而不是4种并列的结构。

**肤浅3：核心概念从15个减到8个**

这是典型的"选择性计数"。只数运行时概念，不数编译期概念；只数核心模块，不数外围模块。

实际情况是：engine.py里的概念少了，但整个系统的概念多了（编译期5阶段、规则引擎、依赖分析、配置模式...）。这是分层架构的正常代价，坦诚承认就好，不用硬说"概念减少了"。

## 五、下一轮（v0.5）P0重点

### P0-1：闭环增量 + VM 的设计

- 设计增量模式下的EdgeVM执行模型
- 明确变更集如何在指令序列中传递
- 给出完整的增量边执行示例
- 设计全量/增量降级和恢复机制

**为什么是P0**：这是本轮声称的"核心突破"之一，但实际上是最大的缺口。增量和VM不闭环，精确增量就是空中楼阁。

### P0-2：明确EdgeVM定位，不要硬撑"通用"

- 要么承认是领域专用VM，改名
- 要么真的做通用内存模型，EAV通过库函数访问
- 二选一，不要含糊

**为什么是P0**："通用VM"是本轮的头号声称，但名不副实。继续硬撑会误导后续设计，也影响架构文档的可信度。

### P0-3：修正变更集代数，去除自相矛盾

- 删除被自己证伪的union运算，或者修正它
- 明确变更集的定位：是"代数运算的对象"还是"变化标记"
- 如果是前者，补全正确性证明；如果是后者，删掉"代数"的提法

**为什么是P0**：形式化定义不能有"近似正确"的东西。要么不形式化，要形式化就必须正确。当前文档里"自己举例证明union不对"的段落，严重损害了变更集部分的可信度。

### P0-4：性能基线实测

- 对EAV三元组模型做性能基准测试
- 对增量filter做性能基准测试
- 对EdgeVM的解释开销做基准测试
- 用实测数据替代"预估"和"略低"

**为什么是P0**：性能是架构决策的重要依据。当前所有性能判断都是"估计"、"略低"、"应该更快"，没有实测数据。没有实测，性能trade-off就是拍脑袋。

## 六、总结评语

v0.4相比v0.3，**确实有进步**——持久化层补全了、依赖分析完整了、变更集有形式化尝试了、功能审计做得很细。这些都是实打实的改进，+5分是合理的。

但**本轮声称的"8大核心突破"水分较大**：

| 声称的突破 | 实际成色 |
|-----------|---------|
| EdgeVM通用化 | 50% — opcode通用了，但内存模型还是领域绑定的 |
| 配置表化学融合 | 30% — 是分类不是融合，ECA硬凑痕迹明显 |
| 运行时表统一 | 90% — EAV确实统一了，虽然性能有隐忧 |
| 变更集语义 | 60% — 有形式化，但核心运算被自己证伪 |
| 精确增量 | 40% — 只有filter有算法，和VM完全脱节 |
| 数据依赖 | 85% — 五维覆盖全面，深度尚可 |
| 持久化层 | 75% — 骨架完整，细节待补 |
| ADR从3到9 | 100% — 数量和质量都有提升 |

**整体判断**：架构方向是对的（表驱动、编译期/运行期分离、增量计算），但每一步都走得不够彻底，喜欢用"高级词汇"包装"半成品"。

**给架构师的建议**：
- 少一点"突破"、"革命"、"极致"，多一点"我们做到了什么、还没做到什么"
- 形式化要么不做，要做就做对——不能有"近似正确"的定理
- 性能不能靠估计，要实测——哪怕是原型级别的实测
- 坦诚面对架构的trade-off——没有只有收益没有代价的架构决策

**评级**：B-。方向正确，功底有，但浮夸之风需要收敛。下一轮如果能把P0的几个问题解决，有望冲B+。
