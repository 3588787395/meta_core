## 二、分项详细评审

### 2.1 行为洞察深度（22/30 分）

**做得好的：**

1. **双时间模型的洞察是准确的**（+5 分）
   - 数据时间 vs 系统时间的区分抓住了实时系统的核心痛点
   - 时间触发用数据时间、超时心跳用系统时间的判断基本正确
   - 行情延迟场景下的行为分析有实际意义

2. **交易日历作为基础设施的定位是对的**（+3 分）
   - 从简单时段配置升级为完整交易日历，方向正确
   - 意识到"判断交易时间首先要判断交易日"，这是关键洞察

3. **正交边界的分析方法有价值**（+4 分）
   - "改一个维度不影响其他维度"的判断方法是正确的
   - name 拆分为唯一标识和显示名，这个洞察是深刻的
   - position 归 UI 的判断也是准确的

**不足之处：**

1. **L2 组合的洞察停留在表面**（-3 分）
   - 只看到了"三层组合"的形式，没有深入思考组合模型的适用边界
   - 排名类 filter 为什么算子层可以没有？这个问题没有解释清楚
   - 阈值可以是另一个指标吗？（比如 MACD 金叉 = DIFF 上穿 DEA）这个本质问题被回避了

2. **数据时间的粒度洞察不足**（-2 分）
   - tick 的时间戳和 K 线的时间戳是不同性质的东西
   - 事件时间（tick 级）和周期时间（bar 级）的区别没有讲
   - 未完成 K 线的"当前时间"怎么定义？没有深入

3. **乱序处理的策略过于粗糙**（-2 分）
   - "等 3 秒"是拍脑袋的，没有依据
   - 股票池对实时性要求不高？这个假设不成立——取决于具体策略
   - 超过窗口直接丢弃？这不是保守策略，是懒惰策略

4. **TTL 用系统时间的洞察有缺陷**（-1 分）
   - 行情中断几小时，系统时间在走，股票会因为 TTL 全部被踢出去
   - 等行情恢复时，池子空了，这合理吗？
   - 没有区分"自然时间 TTL"和"交易时间 TTL"

### 2.2 表驱动深度（16/25 分）

**核心审查：L2 组合表驱动真的落地了吗？**

**结论：部分落地，但有明显夸大。真正的 L2 只在"用已有组件组合出新 filter 配置"这个层面成立。**

**落地的部分（+10 分）：**

1. **formula_table + operator_table + combine_table 三层结构基本合理**
   - 指标计算、比较判断、组合运算的三层划分有逻辑依据
   - 每层查表调用的模式是清晰的
   - 执行伪代码写得比较详细，可以看出流程

2. **组合逻辑的通用性在限定范围内成立**
   - 如果指标、算子、组合方式都已存在，组合出新的 filter 配置确实不用写代码
   - 比如"MA5 > 10 且 成交量 > 1000万"这种标准 filter，确实是纯配置

**没落地的部分 / 夸大的部分（-9 分）：**

1. **"改表不改代码"的说法严重夸大**（-4 分）
   - 文档自己也承认：加新算子要写代码（L1），加新组合方式要写代码（L1）
   - 加新指标，如果公式引擎不支持的函数也要写代码（L1）
   - 真正"不改代码"的只是：用**已有**的指标、算子、组合方式，组合出一个新的 filter **实例配置**
   - 这叫"配置驱动"，不是"表驱动 L2 组合"
   - L2 的定义应该是"组合逻辑本身是表驱动的，加新的组合模式不用改代码"，但现在加新的组合方式还是要写 handler

2. **排名类 filter 打破了三层模型**（-2 分）
   - 例子 2（涨幅前 10）说"算子：无（直接用指标值排名）"
   - 三层模型在排名类场景下退化为两层
   - 文档没有明确说明这种退化情况，三层模型的普适性存疑
   - operator_id 可以为空吗？为空时怎么处理？没有定义

3. **阈值可以是另一个指标吗？**（-2 分）
   - 例子 3（MACD 金叉）里说 threshold = DEA 值（另一个指标）
   - 但 operator_table 的定义里，参数是"阈值"，隐含是固定值
   - 如果阈值可以是另一个指标，那比较层的输入就不是"指标值 + 固定阈值"，而是"两个指标值比较"
   - 这需要更复杂的处理：比较之前要先算两个指标
   - 文档完全没有讨论这个本质问题，例子和表结构是矛盾的

4. **filter_config 的归属不清**（-1 分）
   - filter_config 是 edge 实例的配置，还是类型配置？
   - 如果是实例配置，那"改表不改代码"就不成立——改的是实例数据，不是配置表
   - 配置表（formula_table / operator_table / combine_table）是类型级的
   - filter_config 是实例级的，两者不在一个层次上

### 2.3 架构诚实度（12/20 分）

**问题：这一轮的架构诚实度反而比上一轮下降了。**

**不诚实的表现：**

1. **标题党严重**（-3 分）
   - 反复强调"真正的改表不改代码"，但实际上大量场景还是要写代码
   - "L2 组合表驱动真正落地"——落地的是配置化，不是 L2 组合
   - 文档正文里其实承认了加算子/加组合方式要写代码，但标题和总结里选择性忽略

2. **propagate 合并到 combine 是概念偷换**（-2 分）
   - propagate 是"传播行为"（股票怎么从一个节点传到另一个节点）
   - combine 是"多条件组合运算"（多个 filter 条件怎么组合）
   - 这两个概念在语义上完全不同
   - 强行合并 = 为了减少表的数量而牺牲概念清晰度
   - 文档说"propagate 也是一种组合方式"——这是牵强的

3. **三态逻辑的宣传过度**（-2 分）
   - 三态逻辑（True/False/None）确实有用
   - 但文档里反复强调"三态逻辑贯穿始终"，实际上 None 的处理就是"遇到 None 就返回 None"
   - 三态逻辑的难点在于组合运算的语义（比如 AND 运算遇到 None 怎么算），文档没有深入讨论
   - 只是说"support_ternary: true"，但具体怎么支持？没有定义

4. **"正交"用得太滥**（-1 分）
   - 什么都叫"正交"，节点配置正交、算子配置正交、时间配置正交
   - 节点配置和算子配置和时间配置之间是什么关系？它们是"正交"的吗？
   - 正交的意思是"两个变量独立变化"，但这三类表显然是相互依赖的
   - 滥用术语 = 降低可信度

**诚实的部分（+6 分）：**

1. 承认了加新算子/加新组合方式要写代码（虽然放在角落里）
2. 承认了公式引擎不支持的函数要写代码
3. v1.13 → v1.14 的变更摘要表做得比较诚实，哪些变了哪些没变一目了然

### 2.4 架构清晰度（12/15 分）

**做得好的：**

1. **双时间模型的概念非常清晰**（+4 分）
   - 数据时间 vs 系统时间的对照表做得很好
   - 每个场景用什么时间、为什么，讲得很清楚
   - 简单记忆法则（和市场相关用数据时间，和系统相关用系统时间）很实用

2. **正交边界的梳理有进步**（+3 分）
   - trigger_mode 归 edge_behavior_table，判断正确
   - name 拆分为 display_name 和唯一标识，思路清晰
   - position 归 UI，判断准确
   - 每张表"管什么/不管什么"的表格形式很直观

3. **配置表分类层级图清晰**（+2 分）
   - 节点配置 / 算子配置 / 时间配置三大类的划分是合理的
   - 每类包含哪些表，一目了然

**还不够清晰的：**

1. **实例级配置 vs 类型级配置的边界不清**（-1 分）
   - ui_table 里既有类型级的（display_name / color / icon），又有实例级的（position）

2. **节点行为和边行为的边界模糊**（-1 分）

3. **时间模型的层级关系表达不够精确**（-1 分）

## 四、12 条具体改进建议

### 🔴 P0 级建议（必须改）

**1. 把"改表不改代码"的口号改成更诚实的表述**
   - 当前说法有误导性，容易让读者以为加任何新东西都不用写代码
   - 建议改成："用已有指标、算子、组合方式组合出新 filter = 纯配置，不用写代码"
   - 明确区分 L1（加新组件要写代码）和 L2（组合已有组件不用写代码）
   - 架构诚实度比宣传效果重要

**2. 明确 filter_config 的归属：实例级还是类型级？**
   - 如果是实例级（每条边有自己的过滤条件），那它不属于"配置表"，属于"实例数据"
   - 配置表（formula_table / operator_table / combine_table）是类型级的，定义了"有哪些可用的组件"
   - filter_config 是实例级的，定义了"这个具体的边用哪些组件怎么组合"
   - 两者不在一个层次上，不要混为一谈

**3. 解决"阈值可以是另一个指标"的问题**
   - MACD 金叉（DIFF 上穿 DEA）这种场景，阈值是另一个指标，不是固定值
   - 这是真实存在的需求，不能回避
   - 两种方案：
     - 方案 A：operator 的参数可以是"固定值"或"另一个指标的引用"，比较层先判断参数类型，再做处理
     - 方案 B：把"两个指标的关系"也做成一种 formula，比如 `DIFF_CROSS_ABOVE_DEA` 是一个公式，输出 bool
   - 选哪个方案，要说清楚理由

**4. 把 combine 和 propagate 拆开来**
   - combine = 多条件组合运算（and/or/top_n 等），输出是一个布尔集合/排名列表
   - propagate = 传播行为（怎么把 filter 结果传到下一个节点），比如：全部传入、只传新增的、增量合并等
   - 这是两个不同的维度，应该是两张表，不要强行合并
   - 概念清晰度 > 表的数量少

### 🟡 P1 级建议（应该改）

**5. 排名类 filter 要明确说明三层模型的退化情况**
   - 排名类（top_n / bottom_n）没有 operator，直接用指标值排名
   - 这是合理的，但要明确说：不是所有 filter 都有完整的三层
   - operator_id 可以为空吗？为空时比较层怎么处理？
   - 定义清楚规则，不要让读者自己猜

**6. 区分"事件时间（tick 级）"和"周期时间（bar 级）"**
   - 数据时间不止一种：tick 的时间戳是事件时间，K 线的时间戳是周期时间
   - 未完成 K 线的"当前时间"怎么定义？是最新 tick 的时间吗？
   - 周期确认用的是哪个时间？是 bar 的结束时间吗？
   - 粒度再细一层，避免后续混淆

**7. TTL 要区分"自然时间 TTL"和"交易时间 TTL"**
   - 有些场景用自然时间（比如"入池 24 小时自动移出"）
   - 有些场景用交易时间（比如"入池 5 个交易日后移出"）
   - 行情中断时，自然时间 TTL 会把股票都踢光，这可能不是想要的行为
   - 提供两种 TTL 计算方式，让用户选

**8. 乱序处理策略要有依据，不能拍脑袋**
   - "等 3 秒"的依据是什么？为什么不是 1 秒或 10 秒？
   - 应该说："延迟窗口的大小取决于行情源的延迟分布，建议根据实际监控数据调整，默认值 3 秒"
   - 超过窗口的数据怎么处理？直接丢弃太粗暴了
   - 至少要分级别：窗口内的正常处理，窗口外的告警并记录，要不要处理由策略决定

**9. 交易日历要说明数据来源和更新机制**
   - holidays 列表谁来维护？怎么更新？
   - A 股节假日每年都不一样，不能硬编码
   - 建议：支持从外部数据源（比如交易所官网）自动更新
   - 至少要说明更新流程

### 🟢 P2 级建议（可以改）

**10. 性能优化：holidays 应该用 Set 存储**
   - 伪代码里 `if date in holidays`，holidays 是 List，每次判断是 O(n)
   - 用 Set 存储，O(1) 查询
   - 虽然节假日数量不多，性能影响不大，但这是基本规范

**11. 路线图的优先级要区分开**
   - 四个阶段全是 P0，等于没有优先级
   - 建议：阶段一（L2 组合）和阶段二（双时间 + 交易日历）是 P0，阶段三（正交边界）是 P1，阶段四（测试验证）是 P0 但跟着前面的走
   - 每个阶段要有明确的交付物和验收标准

**12. 补充具体的验收测试用例**
   - 怎么验证"L2 组合真的落地了"？至少要有：
     - 用已有组件组合出一个新 filter，不用写代码，验证功能正确
     - 加一个新算子，需要写代码，验证注册后可以用
   - 怎么验证"双时间模型正确"？至少要有：
     - 行情延迟场景下，时间触发的时机正确
     - 超时检测在非交易时段不触发
   - 没有验收标准 = 无法验证是否真的落地了

## 五、3 条最深刻洞见

### 洞见 1：双时间模型的区分是实时交易系统的基石
> **"时间触发用数据时间，超时心跳用系统时间"——这个判断抓住了实时系统的核心矛盾。**

为什么深刻：
- 很多实盘 bug 都源于数据时间和系统时间的混淆
- 这个区分不是股票池特有的，是所有实时数据处理系统的通用问题
- 文档用通俗的例子（行情延迟 5 秒）把这个问题讲清楚了，非常好

但还可以更深：
- 数据时间不止一种粒度（tick 级 / bar 级）
- 系统时间也有精度和同步问题（分布式场景下）
- 双时间模型的本质是"因果时间"和"观测时间"的分离

### 洞见 2：交易日历是所有时间计算的基础设施
> **"判断交易时间首先要判断交易日"——这个看似显然的结论，很多系统直到出了 bug 才意识到。**

为什么深刻：
- 很多系统一开始只有"时段配置"，忽略了"交易日"的概念
- 等到节假日出问题了，才来补交易日历
- v1.14 主动把交易日历作为基础设施来建设，这个方向是对的

但还可以更深：
- 交易日历不只是"判断某一天是不是交易日"，它还定义了"时间的度量衡"
- 比如"5 个交易日后"，这是一种基于交易日历的时间计算
- 多市场场景下，不同市场的交易日历不同，时间计算会更复杂

### 洞见 3：name 拆分为唯一标识和显示名，抓住了"身份 vs 表现"的本质
> **"唯一标识是给系统用的，不能改；显示名是给人看的，可以改，可以多语言"——这个区分是架构成熟的标志。**

为什么深刻：
- 很多系统前期图省事，用 name 同时做唯一标识和显示名
- 等到要改名字、要做多语言、要做数据迁移的时候，就痛苦了
- 提前把这个边界划清，避免了后续的大量返工

但还可以更广：
- 不只是 name，很多属性都有"身份"和"表现"的区分
- 比如 color：是节点类型的固有属性（身份的一部分），还是 UI 表现？
- 如果不同用户可以自定义节点颜色，那 color 就是实例级 UI 属性，不是类型属性

---

## 六、3 条最肤浅理解

### 肤浅 1："L2 组合表驱动真正落地"——落地的是配置化，不是 L2
> **"加新 filter 不改代码"的前提是"指标、算子、组合方式都已经存在"，这叫配置化，不叫 L2 组合。**

为什么肤浅：
- L2 的定义应该是"组合逻辑本身是表驱动的，加新的组合范式不用改代码"
- 但现在加新的组合方式（比如加一个"至少满足 N 个"的组合逻辑）还是要写 handler
- 真正的 L2 应该是：组合方式本身也可以用更基础的算子组合出来
- 现在的三层模型，组合层还是 L1（每个组合方式一个 handler）

更诚实的说法：
- "filter 的配置化：用已有组件组合出新 filter，不用写代码"
- "L2 组合是未来方向，目前先做到 L1.5"

### 肤浅 2："propagate 合并到 combine"——为了表少而牺牲概念清晰度
> **"propagate 也是一种组合方式"——这是牵强的，组合运算和传播行为是完全不同的维度。**

为什么肤浅：
- combine 回答的是"多个条件怎么得出一个结果"（逻辑运算）
- propagate 回答的是"结果怎么传到下一个节点"（数据流动）
- 这两个问题的性质完全不同，强行合并 = 概念混淆
- 表的数量少不等于架构好，概念清晰才是真的好

正确的做法：
- combine_table：定义多条件组合方式（and/or/top_n 等）
- propagate_table：定义传播行为（全量/增量/去重 等）
- 两张表，各司其职，正交清晰

### 肤浅 3："股票池对实时性要求不是特别高"——这是假设，不是事实
> **乱序处理用"等 3 秒"的简化策略，理由是"股票池对实时性要求不是特别高"——这个假设太危险了。**

为什么肤浅：
- 股票池的实时性要求取决于具体策略，不能一概而论
- 有些策略就是要抢开盘前几分钟的机会，延迟 3 秒可能就错过了
- 架构设计不能建立在"对实时性要求不高"的假设上
- 正确的做法是：提供不同级别的实时性选项，让用户根据策略选择

更合理的策略：
- 提供"低延迟模式"（不等待乱序，来一个处理一个）和"高一致性模式"（等待窗口，乱序数据都到齐再处理）
- 窗口大小可配置
- 让用户根据策略的实时性要求和对乱序的容忍度来选择

## 八、总结

v1.14 是一个**有进步但宣传过度**的版本。

**进步在于：**
- 双时间模型的概念澄清做得很好，抓住了实时系统的核心痛点
- 正交边界的梳理有实质性进展，name 拆分、position 归位等判断准确
- 交易日历作为基础设施的定位是正确的

**不足在于：**
- "L2 组合表驱动真正落地"的说法严重夸大，实际上只是配置化
- 架构诚实度反而下降，有为了宣传而牺牲概念清晰度的倾向
- 很多边界问题（类型/实例、combine/propagate、数据时间粒度）还没有理清楚

**给架构师的一句话：**
> 落地比概念重要，诚实比完美重要。宁可说"L1.5 配置化，我们正在向 L2 努力"，也不要说"L2 已经落地了"。牛皮吹多了，真的落地了也没人信。
