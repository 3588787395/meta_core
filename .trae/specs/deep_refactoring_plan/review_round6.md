## 二、分项详细评审

### 1. 行为洞察深度（24/30）

#### 做得对的地方（+24）

- **纠正"日线一天只算一次"的回测思维——这是真进步**。实盘中最新一根K线（无论什么周期）都是未完成的，每个 tick 都可能变化。这个认知升级是 v1.6.1 最有价值的部分，把"缓存粒度"的讨论从回测语境拉回了实盘语境。（+8）
- **纯函数性质的洞察是对的**：指标是纯函数，输入数据不变 → 输出结果不变。这个根本性质抓得准，所有缓存优化都建立在这个基础上。（+5）
- **职责分离的方向是对的**：指标缓存是公式引擎内部的事，股票池引擎不操心。这个边界划分是架构层面的进步，比 v1.5 混在一起要清晰得多。（+5）
- **K线数据层独立是对的**：股票池引擎不直接操作K线数据，通过公式引擎获取指标值。这个分层让各层职责更单一。（+3）
- **filter三层 + 传播是边的步骤——这个定型是对的**。v1.5 还在纠结传播是不是 filter 第四层，v1.6/v1.6.1 明确了：filter 只有三层（指标→比较→集合运算），传播是边的执行步骤之一。这个概念清晰度提升了。（+3）

#### 扣分项（-6）

- **矫枉过正：从"按周期分"的极端走到"全局一个"的另一个极端**。v1.5 摸到了正确方向——不同指标的缓存有效期可以不同；v1.6 用版本号机制把这个方向落地了（虽然是周期级的，粒度还可以更细）；v1.6.1 直接跳到了另一个极端："一个全局水位线就够了"。这是从"过度设计"跳到"设计不足"，两头都不对。
  - 为什么不对？因为全局水位线意味着：股票A来了一个 tick，股票B（数据根本没变）的所有指标也要被认为"可能变了"。虽然通过 dirty_nodes 可以把范围限制在"有股票数据变化的节点"，但节点里其他没变化的股票还是会被全量重算。
  - 正确的粒度应该是什么？不是"周期级"，也不是"全局级"，而是**"股票级"**——哪只股票的数据变了，那只股票的指标需要重算，其他股票的数据没变，指标结果也不会变。（-3）

- **`data_dirty` 和 `dirty_nodes` 职责重叠，逻辑混乱**。文档里说"三要素：时间条件 AND (节点脏 OR 数据脏)"，但实际上：
  - tick 来了 → 该股票所在节点加入 `dirty_nodes`（节点脏）
  - TTL 过期 → 节点加入 `dirty_nodes`（节点脏）
  - 传播变化 → 目标节点加入 `dirty_nodes`（节点脏）
  
  也就是说，**所有"数据变了"的情况都会导致节点脏**。那 `data_dirty` 这个全局标记还有什么独立存在的价值？文档里的伪代码更说明了问题：
  
  ```python
  if not data_dirty:
      pass  # 数据没变，所有计算结果都不会变，跳过
      # （除非节点状态变了，所以还要检查节点脏）
  ```
  
  这算什么逻辑？`data_dirty=False` 的时候是 `pass`，不是 `return False`。那这个判断等于没写。`data_dirty` 完全是个冗余概念，和 `dirty_nodes` 职责重叠了。（-2）

- **缺少 `dirty_stocks` 细粒度跟踪，节点脏了只能全量重算**。节点脏了，但节点里可能只有1只股票的数据变了，其他99只都没变。现在的设计是：节点脏 → 对节点里所有股票重算指标。这是对"数据不变则结果不变"这个洞察的浪费——你明明知道其他99只股票的数据没变，为什么还要重算它们的指标？因为你没跟踪"具体哪只股票脏了"，只跟踪了"哪个节点脏了"。（-1）

### 2. 表驱动深度（20/25）

#### 做得对的地方（+20）

- **公式注册表（formula_registry）是真进步**。从 v1.5 没有公式注册表，到 v1.6/v1.6.1 有了完整的公式元数据注册，这是表驱动思维的重要体现。公式有什么参数、输出什么类型、依赖什么周期——这些信息从硬编码变成了表数据。（+6）
- **比较算子正交化方向正确**。指标和比较算子是两个正交维度，笛卡尔积组合出各种 filter。这个设计比 v1.5 混在一起要好得多，扩展性更强。（+5）
- **编译期指标去重的表驱动落地了**。`edge_indicator_refs` 通过 ID 引用指标，不是复制配置。引用而非复制，是表驱动的核心思想。（+4）
- **filter 三层的表结构分层清晰**。`edge_indicator_refs` / `edge_compare_spec` / `edge_set_op_spec`，每层一张表，职责单一。（+3）
- **传播模式、时间触发的表驱动延续得好**。这几块 v1.3 就有基础，v1.6.1 保持住了。（+2）

#### 扣分项（-5）

- **表驱动只停留在"配置表"层面，未深入到"逻辑表"**。现在的表驱动是："配置什么指标、什么比较算子、什么传播模式"这些是表驱动的，但**核心执行逻辑还是硬编码的**——filter 必须是三层，必须按"指标→比较→集合运算"的顺序执行，边必须按"gate→filter→propagate→event→mark_dirty"的步骤执行。这些执行流程不是表驱动的，是代码写死的。
  - 真·表驱动是什么样的？边的执行步骤本身也应该是可配置的表——比如有的边可以跳过比较层，有的边可以直接 propagate，有的边可以只算指标不传播。这些差异应该在表内容里，而不是代码里的 if-else。（-3）

- **集合运算层的表驱动表达能力太弱**。只有 `logic/rank/set_op` 三种类型，嵌套组合怎么表示？`(A AND B) OR (C AND NOT D)` 这种多层逻辑能表达吗？文档里没说清楚。集合运算层是 filter 灵活性的关键，现在的表结构太简单了。（-2）

### 3. 事件驱动纯度（13/20）

#### 做得对的地方（+13）

- **TTL 过期队列仍是真事件驱动**。最小堆，过期才处理，不是每 tick 遍历。这块一直做得不错。（+4）
- **节点脏驱动比边队列更自然**。数据更新 → 节点脏 → 遍历出边，这个因果链是清晰的。节点是状态的容器，状态变了容器就脏，这个抽象是对的。（+4）
- **无条件边立即传播**。状态变化立即触发，不是等下一轮。（+3）
- **事件即时发射**。每条边执行完立即发事件，不是攒到 tick 结束。（+2）

#### 扣分项（-7）

- **本质还是"每 tick 批量处理"的微批模式，不是真事件驱动**。从 v1.3 到现在，核心循环一直是"等数据更新 → 处理所有脏节点 → 等下一次更新"。这不是事件驱动，这是**微批处理**——把一段时间内的变化攒起来，批量处理。
  - 真·事件驱动是什么样的？事件来了就处理，事件之间是独立的。比如股票A来了个 tick，就只处理股票A相关的计算，不需要等"其他股票的 tick 都到了"再一起处理。
  - 现在的模型更像"tick 级微批"，每个 tick 是一个批次，批次内批量处理所有变化。（-3）

- **全局水位线让数据变化粒度更粗了，离事件驱动更远**。v1.5 至少还是股票级的（stock_dirty），v1.6 是周期级的（period_version），v1.6.1 退化成全局级的（data_dirty）。粒度越来越粗，离"哪只股票变了处理哪只"的事件驱动理想越来越远。（-2）

- **时间触发还是轮询检查**。每条边的时间触发条件（starttype + cxtype）是在边执行时检查的，不是"时间到了触发事件"。还是轮询模式。（-1）

- **缺少事件日志/事件溯源**。所有状态变化都是直接修改内存表，没有事件日志。出了问题无法回放，也无法追溯。（-1）

### 4. 架构清晰度（12/15）

#### 做得对的地方（+12）

- **三层职责分离更清晰了**。数据层 → 公式引擎层 → 股票池引擎层，每层职责单一，边界明确。比 v1.5 混在一起要好得多。（+4）
- **核心运行时表从 7 张减到 5 张，确实瘦身了**。去掉了 `period_version` 和 `kline_cache`（移到其他层），核心概念更少了。这次是真瘦身，不是 v1.5 那种"删2加4"的假瘦身。（+3）
- **filter 三层结构定型了**。指标层→比较层→集合运算层，每层职责清晰，输入输出明确。传播是边的步骤不是 filter 层，这个定位也清晰了。（+3）
- **编译期 vs 运行时严格分离**。CompiledPool 的概念一直很清晰，运行前一次性编译，运行时只读。这个坚持得不错。（+2）

#### 扣分项（-3）

- **`data_dirty` 是冗余概念，降低了清晰度**。如前所述，`data_dirty` 和 `dirty_nodes` 职责重叠，伪代码逻辑有 bug（data_dirty=False 时是 pass 不是 return）。一个职责不清的概念放在核心运行时表里，只会增加理解成本。（-2）

- **"5张核心表"的计数有点讨巧**。`latest_tick` 算一张，`data_dirty` 算一张（但它只是个 bool 值或者时间戳，真的算"表"吗？），`node_stocks` 算一张，`dirty_nodes` 算一张，`ttl_expiry_queue` 算一张。
  - 严格来说，`data_dirty` 只是一个全局变量，不是"表"。如果 bool 值也算"表"，那是不是所有全局状态都能算一张表？
  - v1.5 还知道把 `edge_last_data_ts` 踢出去凑数字，v1.6.1 直接把 `data_dirty` 这个标量值算成"一张表"了。数字游戏，没意思。（-1）

## 三、"纠正错误"真实性验证

架构师声称 v1.6.1 纠正了四个根本性错误。让我们逐条验证：

### 纠正1：去掉了"周期级脏标记/版本号"的过度设计，回归单一全局水位线

**结论：半真半假。去掉过度设计是真的，但"回归单一全局水位线"是矫枉过正，从一个极端走到另一个极端。**

- ✅ **去掉 `period_version` 是对的**——v1.6 的周期级版本号确实粒度不对（同周期所有指标共享一个版本号，但实际上不同指标的计算频率和依赖可以不同）。
- ❌ **但"全局单一水位线"也不对**——粒度太粗了。股票A的 tick 来了，股票B的数据没变，为什么要认为股票B的指标"可能变了"？
- ✅ **正确的粒度是"股票级"**——哪只股票的数据变了，那只股票的指标需要重算。这才是对"数据不变则结果不变"这个洞察的正确应用。
- ⚠️ **所以 v1.6.1 是：去掉了一个错误的设计（周期级版本号），换上了另一个不够好的设计（全局水位线）。** 不是"纠正错误"，是"换了一个错误"。

### 纠正2：明确了"日线一天只算一次"是回测思维，实盘中是错的

**结论：完全正确。这是 v1.6.1 最扎实的认知升级。**

- ✅ **这个纠正非常关键**。实盘中最新一根K线是未完成的，每个 tick 都可能变化。能从回测思维切换到实盘思维，这是认知上的真进步。
- ✅ **这个纠正也解释了为什么"周期级缓存"在实盘场景下意义不大**——因为所有周期的最新值都在随 tick 变化，缓存命中率没那么高。
- ⚠️ **但注意：这个结论只适用于"最新值"**。历史K线（已完成的）的指标值确实是不变的，可以缓存。文档里也提到了这一点（历史值缓存是公式引擎内部的事），这是对的。

### 纠正3：指标缓存是公式引擎内部的事，不是股票池引擎的事

**结论：完全正确。职责分离的方向是对的。**

- ✅ **股票池引擎不应该关心指标怎么缓存、怎么增量计算**。股票池引擎只需要"给我这只股票这个指标的值"，至于公式引擎是从缓存读还是实时算、是增量算还是全量算，股票池引擎不需要知道。
- ✅ **这个边界划分让两层可以独立演进**。公式引擎可以换缓存策略、可以加增量计算优化，都不影响股票池引擎。
- ⚠️ **但注意：问题只是"移动"了，不是"消失"了**。指标缓存的问题（缓存粒度、失效机制、增量计算）依然存在，只是从股票池引擎移到了公式引擎里。不要以为移走了就不用想了——公式引擎里还是要解决这些问题，只是职责更清晰了。

### 纠正4：保留了正确的设计：filter三层、指标去重、公式注册表、比较算子正交化等

**结论：完全正确。这些 v1.6 的正确成果都保住了。**

- ✅ **filter 三层结构**（指标→比较→集合运算）是对的，传播是边的步骤不是 filter 层，这个定位也对。
- ✅ **编译期指标去重**是对的，相同（公式+参数+周期）的指标全局只算一次。
- ✅ **公式注册表**是对的，公式元数据从硬编码变成表数据。
- ✅ **比较算子正交化**是对的，指标和比较是两个正交维度，笛卡尔积组合。

## 四、16条具体改进建议

### 改进1：把全局水位线改成股票级水位线（P0）

**问题：** 全局 `data_dirty` 粒度太粗。股票A的 tick 来了，股票B（数据没变）的指标也会被认为"可能变了"。虽然通过 `dirty_nodes` 限制了节点范围，但节点内其他股票还是会被全量重算。

**建议：**
- 增加 `dirty_stocks: Set[code]`，跟踪本轮 tick 中哪些股票的数据发生了变化。
- tick 来了 → `dirty_stocks.add(code)` + 该股票所在节点加入 `dirty_nodes`。
- 边执行时，指标计算只针对 `dirty_stocks ∩ source_codes` 的股票，其他股票的数据没变，指标结果也不会变，直接用上一轮的值（或者让公式引擎自己处理缓存）。
- 这样才是对"数据不变则结果不变"这个洞察的正确应用——哪只股票数据变了，才重算哪只。

**为什么是P0：** 这是核心性能问题，也是认知正确性问题。全局水位线是对"数据不变则结果不变"的半吊子应用——你知道"数据不变结果不变"，但你不知道"具体哪只股票数据变了"，所以只能全量重算。

### 改进2：删除冗余的 `data_dirty` 概念（P0）

**问题：** `data_dirty` 和 `dirty_nodes` 职责重叠。所有"数据变了"的情况都会导致节点脏，`data_dirty` 没有独立存在的价值。伪代码里 `data_dirty=False` 时是 `pass` 不是 `return`，更说明这个判断是多余的。

**建议：**
- 直接删除 `data_dirty` 这个全局标记。
- 边触发检查的三要素简化为：时间条件 AND 源节点脏。
- "数据变了"这个信息已经通过"哪些股票在 `dirty_stocks` 里"和"节点是否在 `dirty_nodes` 里"体现了，不需要额外的全局标记。
- 核心运行时表从 5 张变成 4 张（latest_tick, node_stocks, dirty_nodes, ttl_expiry_queue），更干净。

**为什么是P0：** 冗余概念会增加理解成本，而且伪代码已经暴露出逻辑混乱的问题（data_dirty=False 时 pass）。早点删掉，早点清爽。

### 改进3：明确公式引擎的接口契约（P0）

**问题：** 文档说"指标缓存是公式引擎内部的事"，但公式引擎的接口是什么？股票池引擎怎么调用？公式引擎怎么知道数据变了？这些都没说清楚。

**建议：**
- 定义公式引擎的核心接口：
  ```python
  class FormulaEngine:
      def calculate(self, code: str, formula: str, period: str, args: dict) -> Any: ...
      def calculate_batch(self, codes: List[str], formula: str, period: str, args: dict) -> Dict[str, Any]: ...
      def on_tick(self, code: str, bar: dict) -> None:  # 通知数据更新
  ```
- 明确公式引擎的内部职责：K线缓存、指标缓存、增量计算、历史值复用。
- 明确股票池引擎和公式引擎的交互方式：股票池引擎只调用 `calculate`，不直接读K线、不读缓存。
- 最好画一张时序图，展示一次 tick 从数据层到公式引擎到股票池引擎的完整流程。

**为什么是P0：** 职责分离不能只停留在概念上，必须落实到接口。接口不定义清楚，分层就是空的。

### 改进4：集合运算层表达能力升级——树形结构（P1）

**问题：** 现在的集合运算层只有 `logic/rank/set_op` 三种类型，无法表达复杂的嵌套组合。比如 `(A AND B) OR (C AND NOT D)` 这种多层逻辑组合，现在的表结构能表达吗？文档里没说清楚。

**建议：**
- 集合运算层规格设计成树形结构，每个节点有 `type` 和 `children`，可以任意嵌套。
- 支持的节点类型：`and` / `or` / `not` / `condition_ref` / `rank` / `set_op`。
- 例如：
  ```json
  {
    "type": "or",
    "children": [
      {
        "type": "and",
        "children": [
          {"type": "condition_ref", "ref": 0},
          {"type": "condition_ref", "ref": 1}
        ]
      },
      {
        "type": "and",
        "children": [
          {"type": "condition_ref", "ref": 2},
          {
            "type": "not",
            "children": [{"type": "condition_ref", "ref": 3}]
          }
        ]
      }
    ]
  }
  ```
- 这样集合运算层才有真正的表达能力，才能应对复杂的选股逻辑。
- 顺便定义 JSON Schema，为前后端共享打下基础。

**为什么是P1：** 集合运算层是 filter 灵活性的关键。现在的表结构太简单，表达能力不足。

### 改进5：比较算子真正正交化——拆成三个维度（P1）

**问题：** 文档说"比较算子正交化"，但现在的 `comparison_operators` 还是按"效果"分类（scalar_compare / cross / inflection / rank），不是按"本质维度"分类。本质维度应该是：① 比较范围（independent/global）② 比较对象（scalar/series/cross_section）③ 比较操作（gt/lt/cross/rank/...）。

**建议：**
- 比较算子拆成三个正交维度的注册表：
  - `scope_registry`：比较范围——independent（单股独立）/ global（全局截面）
  - `target_registry`：比较对象——scalar（单值）/ series（时间序列）/ cross_section（截面集合）
  - `operator_registry`：具体操作——gt / lt / eq / cross_above / cross_below / turn_up / turn_down / rank_top / rank_bottom / ...
- 三个维度的笛卡尔积覆盖所有比较类型。
- 每个维度有自己的注册表，扩展新的比较方式只要加一个 operator，不用改整体结构。
- filter 配置就是"选 scope + 选 target + 选 operator + 参数"。

**为什么是P1：** 正交化是表驱动的核心。现在的"正交化"还不够彻底，还是按效果分类，不是按维度分类。

### 改进6：时间触发改造成"定时事件"（P1）

**问题：** 时间触发条件是边执行时检查的，还是轮询模式。

**建议：**
- 用时间堆（和 TTL 队列类似）管理每条边的下次触发时间。
- 时间到了触发事件，不是每次边执行都检查一遍。
- 时间触发和数据触发是平等的两个事件源，都进入事件循环。
- 这样才是真事件驱动，不是"边执行时顺便检查一下时间"。

**为什么是P1：** 时间触发是三大触发源之一（数据触发、时间触发、状态触发），现在只有数据触发和状态触发是"事件感"的，时间触发还是轮询。

### 改进7：前后端一体重新启动，从共享规格开始（P1）

**问题：** v1.6.1 完全没推进前后端一体，开倒车。但公式注册表和比较算子集已经是标准化的 JSON 了，这是天然的前后端共享基础。

**建议：**
- 既然公式注册表、比较算子集、filter 三层规格都是 JSON，那就把这些 JSON Schema 定义出来，前后端共用。
- 前端根据规格渲染配置界面，后端根据规格执行计算。
- 先从最简单的开始：
  1. 定义 `formula_registry` 的 JSON Schema
  2. 定义 `comparison_operators` 的 JSON Schema
  3. 定义 `edge_filter_spec` 的 JSON Schema（三层结构）
- 前端和后端都用同一份 Schema 做验证和渲染。
- 先把这一块做起来，比空谈"前后端一体"有用得多。

**为什么是P1：** 基础已经有了（标准化的 JSON 规格），不利用起来太浪费了。而且前后端一致性是股票池系统的核心痛点之一。

### 改进8：增加 `dirty_stocks`，实现节点内增量计算（P1）

**问题：** 节点脏了，但节点里可能只有1只股票的数据变了，其他股票都没变。现在的设计是全量重算节点里所有股票的指标，浪费了"数据不变则结果不变"的洞察。

**建议：**
- 增加 `dirty_stocks: Set[code]`，跟踪本轮哪些股票的数据发生了变化。
- 边执行时：
  - 指标计算层：只对 `dirty_stocks ∩ source_codes` 的股票调用公式引擎，其他股票的数据没变，指标结果也不会变。
  - 比较层（独立型）：只重算 `dirty_stocks` 中股票的比较结果，其他股票的比较结果可以复用。
  - 集合运算层：排名型需要全量，但逻辑组合型可以做短路优化。
- 这样节点脏了不一定要全量重算，可以增量计算。

**为什么是P1：** 这是"数据不变则结果不变"这个洞察的正确落地方式。现在只用到了"节点级"的增量，还可以做到"股票级"的增量。

### 改进9：明确指标类型系统，统一值类型（P2）

**问题：** 指标值的类型（标量/向量/多输出/时间序列）没有统一的类型系统，比较层不知道输入是什么类型。

**建议：**
- 定义指标值类型系统：`Scalar` / `Vector` / `Dict[str, Scalar]` / `Dict[str, Vector]`。
- 每个公式在公式注册表里声明自己的输出类型。
- 每个比较算子声明自己需要的输入类型。
- 类型不匹配在编译期就报错，不是运行时崩。

**为什么是P2：** 类型系统是健壮性的基础。现在靠约定和文档，容易出错。

### 改进10：增加事件日志，支持回放和追溯（P2）

**问题：** 所有状态变化都是直接改内存，没有日志，出了问题查不到。

**建议：**
- 所有状态变化（股票入池/出池、数据更新）都记录事件日志。
- 事件日志可以回放，重现任意时刻的状态。
- 这不仅是调试工具，也是正确性验证的基础。

**为什么是P2：** 调试和运维需要，但不是核心功能，可以往后放。

### 改进11：增加指标缓存淘汰策略（P2）

**问题：** 只说了缓存（在公式引擎里），没说缓存怎么淘汰。股票数量多了缓存会爆炸。

**建议：**
- 按节点引用计数：股票不在任何节点里了，它的指标缓存可以清掉。
- LRU 策略：最近最少使用的指标缓存先淘汰。
- 内存上限：达到上限自动淘汰。
- 这些都要设计，不能只说"有缓存"。
- 注意：这是公式引擎内部的事，不需要股票池引擎关心，但架构设计时要考虑到。

**为什么是P2：** 性能优化，可以往后放。但架构设计时要留好位置。

### 改进12：边执行步骤也表驱动化（P2）

**问题：** 现在边的执行步骤（gate→filter→propagate→event→mark_dirty）是硬编码的，不是表驱动的。

**建议：**
- 定义"边执行步骤表"，每条边有哪些步骤是可配置的。
- 步骤类型：`gate` / `indicator` / `compare` / `set_op` / `propagate` / `event` / `mark_dirty`。
- 比如无条件边可以跳过 gate、indicator、compare、set_op，直接 propagate。
- 这样不同类型的边，执行流程的差异在表内容里，不是代码里的 if-else。

**为什么是P2：** 这是表驱动的深化，但不是当务之急。先把核心功能做对，再谈更深度的表驱动。

### 改进13：明确"最新值"和"历史值"的边界（P2）

**问题：** 文档说"历史K线的指标值可以缓存"，但最新一根K线的指标值每个 tick 都在变。那公式引擎怎么区分"历史值"和"最新值"？缓存策略有什么不同？

**建议：**
- 明确区分：历史K线（已完成，值不变）和最新K线（未完成，每个 tick 都可能变）。
- 历史值：可以长期缓存，不会失效。
- 最新值：每个 tick 都需要重算（或者增量更新）。
- 公式引擎的缓存策略要体现这个差异。

**为什么是P2：** 这是公式引擎内部的细节，但对性能影响很大。

### 改进14：增加错误处理和容错机制（P2）

**问题：** 文档里完全没提错误处理。公式引擎计算失败了怎么办？数据异常怎么办？节点状态不一致怎么办？

**建议：**
- 定义错误类型：数据错误、公式错误、配置错误。
- 定义错误处理策略：跳过该股票、标记为错误状态、告警。
- 定义降级策略：公式引擎不可用时，用缓存值还是直接报错？

**为什么是P2：** 健壮性需要，但不是核心功能。

### 改进15：考虑持久化和恢复机制（P3）

**问题：** 所有状态都在内存里，进程重启就全没了。

**建议：**
- 考虑节点状态的持久化（比如定期快照）。
- 考虑事件日志的持久化，支持从事件日志恢复状态。
- 考虑公式引擎缓存的持久化，重启后不用重新预热。

**为什么是P3：** 生产环境需要，但现在是架构设计阶段，可以往后放。

### 改进16：考虑并发安全（P3）

**问题：** 文档里的设计都是单线程的。如果以后要做多线程或者分布式，现在的设计能支持吗？

**建议：**
- 明确哪些数据结构是线程安全的，哪些不是。
- 考虑事件队列的并发消费。
- 考虑节点状态的并发修改。
- 不用现在就实现，但架构设计时要留好口子。

**为什么是P3：** 远期需求，架构设计时留点空间就行。

## 五、3条最深刻洞见

### 洞见1：纠正"日线一天只算一次"——把讨论从回测语境拉回实盘语境

"实盘中最新一根K线是未完成的，每个tick都在变"——这个认知升级是 v1.6.1 最有价值的部分。之前所有版本（包括 v1.5）的缓存设计，都隐含了"日线一天只算一次"的回测假设。v1.6.1 把这层窗户纸捅破了，把整个讨论拉回了实盘语境。这不是小修小补，这是**前提假设的修正**——前提错了，后面所有的推导都是错的。能把前提纠正过来，这个价值怎么强调都不过分。

更重要的是，这个纠正还带来了一个推论：**所有周期的最新值都在随 tick 变化，所以"按周期分级缓存"在实盘场景下的收益没有想象中那么大**。这个推论直接动摇了 v1.5/v1.6 周期分级缓存的基础。虽然 v1.6.1 给出的解决方案（全局水位线）不对，但它提出的问题是对的——这比给出一个正确答案但问错问题要有价值得多。

### 洞见2：指标缓存是公式引擎内部的事——职责分离的正确姿势

"股票池引擎不管指标怎么缓存，只调用公式引擎"——这个边界划分是架构层面的真进步。之前的版本（v1.3-v1.6）都把指标缓存放在股票池引擎里，导致股票池引擎既要管筛选逻辑，又要管缓存策略，职责混乱。v1.6.1 明确了：**缓存是计算的优化，不是业务逻辑的一部分**。业务逻辑（股票池引擎）只关心"给我结果"，不关心"结果是怎么算出来的、有没有缓存"。

这个边界划分的好处是：两层可以独立演进。公式引擎可以换缓存策略、加增量计算、甚至换成分布式计算，都不影响股票池引擎的代码。反过来，股票池引擎改筛选逻辑、加新的 filter 类型，也不影响公式引擎。这才是真正的架构解耦。

### 洞见3：数据不变则结果不变——但你得知道"具体什么没变"

"指标是纯函数，数据不变则结果不变"——这个根本性质抓得非常准。所有缓存优化、增量计算，都建立在这个基础上。但是，**知道这个性质还不够，你还得知道"具体哪部分数据没变"**。

- 如果你只知道"全局数据可能变了"（全局水位线），那你只能全量重算——等于白知道这个性质。
- 如果你知道"这只股票的数据变了"（股票级水位线），那你只需要重算这只股票的指标——增量计算。
- 如果你知道"这个指标的输入数据变了"（指标级水位线），那你只需要重算这个指标——更细粒度的增量。

粒度越细，缓存命中率越高，增量计算的收益越大。v1.6.1 的问题在于：它认识到了"数据不变则结果不变"，但它的水位线粒度太粗（全局级），导致这个洞察的价值没有充分发挥出来。从"全局级"到"股票级"再到"指标级"，这是一条清晰的优化路径。

## 六、3条最肤浅理解

### 肤浅1："一个全局水位线就够了"——矫枉过正，从一个极端走到另一个极端

"去掉周期级版本号，回归单一全局水位线"——这个说法太极端了。v1.5/v1.6 的周期级缓存确实有问题（同周期所有指标共享一个版本号，粒度不对），但解决方案不是"干脆不要分级了，全局一个就够了"。这就像发现"按楼层分垃圾桶"不合理，就干脆"整个小区一个垃圾桶"——不是进步，是退步。

正确的做法是什么？不是"周期级"，也不是"全局级"，而是**"股票级"**——哪只股票的数据变了，那只股票的指标需要重算。这个粒度既避免了周期级的复杂（9个周期、版本号对比），又避免了全局级的浪费（一只股票变了全市场重算）。v1.6.1 连中间的"股票级"选项都没考虑，直接跳到最粗的"全局级"，这是思考不深入的表现。

### 肤浅2："核心运行时表5张"——把 bool 值也算作"表"，数字游戏

"核心运行时表从7张减到5张"——听起来很厉害，但仔细一看：`data_dirty` 也算一张"表"？它不就是一个 bool 值或者时间戳吗？如果一个全局变量都能算"一张表"，那是不是所有全局状态都能拆出来单独算一张？

v1.5 的时候评审就指出过"概念瘦身是假的，删2加4"，v1.6.1 又玩起了数字游戏。架构设计要诚实，是几个概念就是几个概念。`data_dirty` 这种和 `dirty_nodes` 职责重叠的冗余概念，不仅不应该算作"一张表"，反而应该被删掉。删掉之后核心运行时表是 4 张（latest_tick, node_stocks, dirty_nodes, ttl_expiry_queue），更少，也更干净。

### 肤浅3："公式引擎内部做缓存"——问题只是移动了，不是消失了

"指标缓存是公式引擎内部的事，股票池引擎不操心"——这个职责分离是对的，但不要以为把问题移到公式引擎里，问题就不存在了。缓存粒度怎么选？失效机制是什么？增量计算怎么做？历史值和最新值怎么区分？缓存淘汰策略是什么？这些问题一个都没少，只是从股票池引擎的问题变成了公式引擎的问题。

v1.6.1 的文档里，公式引擎就是个黑箱——"股票池引擎调用它就行，内部怎么优化不用管"。但架构设计不能这样。你可以不关心实现细节，但你得知道"这个层能不能解决这些问题"。如果公式引擎内部还是用全局水位线，那缓存效率一样很低。职责分离是为了更好地解决问题，不是为了把问题藏起来。

## 七、下一轮P0重点（v1.7 必须解决的三个问题）

### P0-1：股票级水位线 + 删除冗余 data_dirty

**为什么是P0：** 全局水位线粒度太粗，是对"数据不变则结果不变"的半吊子应用。`data_dirty` 是冗余概念，增加理解成本还导致逻辑混乱。这两个问题都是核心认知问题，必须先解决。

**具体要求：**
- 增加 `dirty_stocks: Set[code]`，跟踪本轮哪些股票的数据发生了变化。
- 删除 `data_dirty` 全局标记。
- 边触发检查的三要素简化为：时间条件 AND 源节点脏。
- 边执行时，指标计算只针对 `dirty_stocks ∩ source_codes` 的股票（节点内增量）。
- 核心运行时表从 5 张变成 4 张（latest_tick, node_stocks, dirty_nodes, ttl_expiry_queue）。
- 写一个简单的测试用例验证：节点里有两只股票，只有一只来了 tick，确认另一只股票的指标没有被重算。

### P0-2：公式引擎接口契约 + 时序图

**为什么是P0：** 职责分离不能只停留在概念上，必须落实到接口。接口不定义清楚，三层架构就是空的。公式引擎是中间层，它的接口定义直接决定了上下两层能不能解耦。

**具体要求：**
- 定义公式引擎的核心接口（calculate / calculate_batch / on_tick）。
- 明确公式引擎的内部职责（K线缓存、指标缓存、增量计算）。
- 明确股票池引擎和公式引擎的交互方式。
- 画一张完整的时序图，展示一次 tick 从数据层到公式引擎到股票池引擎的完整流程。
- 明确"最新值"和"历史值"的缓存策略差异。

### P0-3：前后端共享规格启动——定义 JSON Schema

**为什么是P0：** 公式注册表和比较算子集已经是标准化的 JSON 了，这是天然的前后端共享基础。放着这么好的基础不用，太浪费了。而且前后端一致性是股票池系统的核心痛点之一（前端预览和后端计算不一致），必须尽早开始解决。

**具体要求：**
- 定义 `formula_registry` 的 JSON Schema。
- 定义 `comparison_operators` 的 JSON Schema。
- 定义 `edge_filter_spec` 的 JSON Schema（三层结构）。
- 这些 Schema 前后端共用，前端用它渲染配置界面，后端用它验证和执行。
- 先做一个最小可行的 demo：前端根据 Schema 渲染一个简单的 MA > 10 的 filter 配置，后端根据同一个 Schema 解析并执行。
