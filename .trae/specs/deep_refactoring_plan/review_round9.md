## 二、核心假设验证：并发模型真的合理吗？

### 2.1 单线程事件循环在Python里性能够吗？

**结论：不够。文档严重低估了Python单线程的性能瓶颈。**

文档说"单线程事件循环：所有计算在一个线程，没有竞态条件"，这话只对了一半——没有竞态条件是真的，但性能代价被完全忽略了。

**Python单线程的问题：**

| 场景 | 单线程表现 | 影响 |
|------|-----------|------|
| 5000只股票 × 100个指标的全量计算 | 可能需要 500ms~2s | 整个事件循环被阻塞，定时器事件全部延迟 |
| 排名型filter（1000只股票排序） | O(n log n)，每次都要全量重排 | 每来一个tick就排一次，排一次阻塞一次 |
| 控制事件（stop/pause） | 必须等当前计算完成才能响应 | 停止按钮点了没反应，用户体验差 |

**更严重的是：文档自相矛盾。**

- 第1.4节说"定时器事件精确触发（到点就处理）"
- 但单线程事件循环里，如果正在处理一个大数据批次，定时器事件只能在队列里等着
- 这就不是"精确触发"，而是"尽量触发"

**实盘场景是什么样的？**

```
真实行情节奏：
  - 9:30~10:00：行情活跃，每秒几十上百个tick
  - 10:00~14:30：行情平稳，每秒几个tick
  - 14:30~15:00：行情活跃，每秒几十上百个tick

如果是单线程：
  - 行情活跃时，CPU一直在算指标，定时器事件（如14:30触发）可能延迟几百毫秒
  - 对于选股来说，几百毫秒可能不重要，但对于"精确时间触发"这个承诺，是失信的
```

**Python环境下的正确做法应该是：**
- 事件循环负责IO和调度（单线程，没问题）
- CPU密集型计算（指标计算、排名）交给worker线程/进程池
- 或者用 asyncio + 协程，把计算任务拆成小片段

文档完全没有讨论这个问题，好像"单线程"就是银弹。这是对并发模型的肤浅理解。

### 2.2 批次化会不会增加延迟？

**结论：会。而且文档没有讨论这个tradeoff。**

文档说"攒个 100ms~1s 的批次，延迟可接受，性能大幅提升"。这个说法太随意了。

**批次大小的tradeoff：**

| 批次大小 | 延迟 | 性能提升 | 适用场景 |
|---------|------|---------|---------|
| 10ms | 几乎实时 | 几乎没有提升 | 高频交易 |
| 100ms | 可感知 | 显著提升 | 大多数选股场景 |
| 1s | 明显延迟 | 大幅提升 | 分钟级以上的策略 |

**问题在于：**
1. 文档没有说明批次大小是可配置的还是固定的
2. 文档没有讨论不同场景下的最佳批次大小
3. 文档把"批次化"从"性能优化"升级成了"架构核心概念"，这是本末倒置

**批次化本来应该是一个透明的性能优化——** 用户可以选择开或关，调大调小，不影响核心架构。但在 v1.9 里，batch_state 是核心运行时表，dirty_stocks 是批次级的，node_data_dirty 也是批次结束时清空。**批次已经渗透到了架构的每个角落。**

这意味着：如果未来想改成逐事件处理（不攒批），整个架构都要改。这是坏设计。

### 2.3 版本屏障的实现方式有bug

**文档说"计算阶段只读不写数据（除了状态表）"，但状态表本身不就是数据吗？**

```
批次处理流程的问题：

  阶段 1：数据更新阶段
    - 更新 latest_tick ✅
    - 收集 dirty_stocks ✅
    - 更新 node_data_dirty ✅

  阶段 2：计算阶段
    - 处理 TTL 过期 → 会修改 node_stocks、node_stock_change ❌
    - 按拓扑序处理脏节点 → 会修改 edge_compare_results、edge_filter_results、node_stocks... ❌
    - 发射事件 → 会修改事件队列 ❌

  阶段 3：批次结束
    - 清理脏标记 ✅
```

**问题：计算阶段也在写数据（状态表），而且是级联写。**

如果节点A的计算结果更新了 node_stocks[A]，然后节点B（依赖A）在同一个批次里读到了更新后的 node_stocks[A]，那节点B的计算就是基于"新版本"的数据，而节点A是基于"旧版本"的数据——版本不一致。

**文档的版本屏障只覆盖了 latest_tick，没有覆盖状态表的级联更新。**

正确的版本屏障应该是：
- 要么：整个计算阶段完全只读，所有写入都收集起来，批次结束时统一提交（类似数据库事务）
- 要么：明确说明"级联传播在同一个批次内是可见的，版本屏障只保证输入数据（latest_tick）的一致性"

文档没有说清楚，给人的感觉是"整个计算都是基于一致快照"，但实际上只有输入数据是一致的，中间状态是级联可见的。

## 三、核心假设验证：事件驱动是真的吗？

### 3.1 事件循环和轮询的区别是什么？

**先明确概念：**

| 模式 | 特征 | 触发方式 |
|------|------|---------|
| **轮询 (Polling)** | 定期检查"有没有新数据"，有就处理 | 时间驱动检查 |
| **事件驱动 (Event-Driven)** | 每个变化都是一个独立事件，事件来了就处理 | 变化驱动处理 |
| **微批处理 (Micro-batching)** | 攒一批数据再处理，介于轮询和事件驱动之间 | 时间+数量双触发 |

**v1.9 到底是什么？**

让我们看数据事件的处理方式：
- tick 来了 → 放进数据队列 → 攒够一批（时间或数量）→ 作为一个 tick_batch 事件处理

**这是微批处理，不是事件驱动。**

真正的事件驱动应该是：每个 tick 都是一个独立事件，逐事件处理。攒批是性能优化，不应该改变事件的语义。

**文档偷换了概念：**
- 把"微批处理"包装成"事件驱动"
- 把"批次"说成"版本屏障"
- 把"攒批处理的数据"说成"数据事件"

**更严重的问题：事件粒度不统一。**

| 事件类型 | 粒度 |
|---------|------|
| 数据事件 | 一批 tick（多个数据点） |
| 定时器事件 | 单个定时器触发（一个时间点） |
| 控制事件 | 单个控制命令（一个命令） |

数据事件是批量的，定时器和控制事件是单个的。事件粒度不统一，导致事件循环的处理逻辑很别扭——一会儿处理一个，一会儿处理一批。

### 3.2 时间驱动独立化是真进步，但还不够

**时间驱动从"数据更新时顺便检查"变成"独立定时器事件源"，这是真进步，值得肯定。**

但还有两个问题：

**问题1：定时器事件和数据事件的优先级矛盾。**

文档说优先级是：控制 > 定时器 > 数据。

但实际场景中：
- 如果正在处理一个大数据批次（100ms），定时器事件到点了，只能等
- 等批次处理完，定时器已经延迟了 100ms
- 这和 v1.8 的"顺便检查"有什么本质区别？只不过 v1.8 是数据更新时检查，v1.9 是数据批次结束时检查

**问题2：定时器事件处理逻辑有缺陷。**

看伪代码 `handle_edge_timer_event`（第8.5节）：
- 定时器触发 → 直接用 edge_filter_results 的缓存做 propagate
- 没有重新计算 filter
- 那如果数据变了但还没处理（在数据队列里攒着），定时器用的是旧数据的结果

**这就有问题了：**
- 数据事件和定时器事件是两个独立的事件源
- 如果定时器事件在数据事件之前被处理，用的就是旧数据
- 这不是"基于最新数据的时间触发"，而是"基于上一批数据的时间触发"

正确的做法应该是：定时器事件触发时，先确保所有已到达的数据都被处理了，再执行时间触发的逻辑。或者说，数据事件的攒批时间应该远小于定时器的精度，保证定时器触发时数据已经是最新的。

文档没有讨论这个问题。

## 四、node_stock_change 结构化审查

### 4.1 方向正确：从 bool 到 entered/exited 是质变

**这个改进是本轮最大的亮点，给4分的提升主要来自这里。**

从 `node_stock_change[nid]: bool` 到 `node_stock_change[nid]: {entered: Set, exited: Set}`，这不是简单的数据结构升级，而是认知升级：
- 旧版：只知道"变了"
- 新版：知道"怎么变的"（哪些进来了，哪些出去了）

只有知道"怎么变的"，才能做到真正的增量处理：
- 入池的股票：初始化指标、比较结果、TTL
- 出池的股票：清理所有相关状态
- 没变的股票：完全不碰

这是增量计算的基础。方向完全正确。

### 4.2 伪代码中的增量处理有bug

**看 process_edge 的伪代码（第8.4节），比较层对 entered 的处理有问题：**

```python
# 伪代码第8.4节，第二层：比较判断
for code in entered:
    if code in indicator_values.get(indicator_ids[0], {}):
        result = do_compare(indicator_values, code, compare_spec)
        edge_compare_results[eid][code] = result
    else:
        # 数据不足，标记为 None
        edge_compare_results[eid][code] = None
```

**Bug 1：只检查了第一个指标。**

`indicator_values.get(indicator_ids[0], {})` —— 只看了第一个指标有没有值。但一条边可能引用多个指标（比如 "MA5 > MA10" 引用了两个）。如果第一个指标有值但第二个没有，还是会进入比较，然后 do_compare 里可能报错或者返回错误结果。

正确的做法应该是：检查所有需要的指标是否都有有效值，只要有一个没有，就标记为 None。

**Bug 2：data_dirty 的部分没有处理数据不足的情况。**

```python
# 数据变了的：更新比较结果
for code in data_dirty:
    if code in source_codes:
        result = do_compare(indicator_values, code, compare_spec)
        edge_compare_results[eid][code] = result
```

data_dirty 的股票，如果数据不足（比如新股，K线不够），应该返回 None，而不是让 do_compare 自己处理。伪代码里没有这个判断，默认 data_dirty 的股票数据都是充足的。

**Bug 3：排名型 filter 完全浪费了 entered/exited 结构化。**

文档明确说排名型"只要有变化就全量重排"。这意味着：
- entered/exited 的结构化对排名型没有价值
- 排名型还是全量重算，和 v1.8 一样

那对于排名型占多数的场景，node_stock_change 的改进就白做了。

**当然，排名型确实难做增量**——因为排名是相对的，一只股票的指标变了，可能影响所有股票的排名。但文档应该主动讨论这个问题：
- 排名型增量到底可不可能？
- 有没有近似算法？（比如只重新计算变化股票的排名，其他不动）
- 如果确实做不到，那应该明确说明"排名型filter不支持增量，必须全量重排"，而不是默认读者知道。

### 4.3 三态化是进步，但传播规则不完整

**edge_compare_results 从二态变成三态（True/False/None），这是进步。**

文档也给出了三态逻辑运算规则（AND/OR/NOT），这很好。

**但还不够：**

| 缺失的传播规则 | 说明 |
|--------------|------|
| **集合运算中的 None 怎么处理？** | 独立型 filter 里，None 的股票是算"不通过"还是"待定"？文档没说。 |
| **排名型中的 None 怎么处理？** | 数据不足的股票，是排最后还是排除？文档没说。 |
| **propagate 时 None 怎么处理？** | 目标节点里，None 的股票算在池子里还是不算？文档没说。 |

**更根本的问题：三态应该在哪一层结束？**

- 比较层是三态（True/False/None）
- 集合运算层应该是几态？如果是二态（通过/不通过），那 None 在哪一层被转换成 False 或排除？
- node_stocks 里的股票，是"明确通过"的，还是"可能通过的（包含None）"？

文档没有说清楚这个状态机的转换路径。

### 5.1 从6个到11个：数量上去了，质量呢？

**先列一下11个接口：**

**数量翻倍了，但有些问题：**

**问题1：eval_indicator 和 eval_indicators 功能重叠。**

- eval_indicator：单只股票单指标
- eval_indicators：批量多股票多指标

eval_indicator 完全是 eval_indicators 的特例——传一个 formula_id、一个 code，就是单只单指标。保留两个接口只是为了"方便"，但增加了接口表面积，也增加了维护成本。

**正确的做法：只保留批量接口，单只的只是批量的特例。** 或者连特例都不用提供，用户自己传单个元素的列表就行。

**问题2：on_data_updated 和 on_period_tick 的关系模糊。**

文档说：
- on_data_updated：任何 tick 数据更新都调用（高频）
- on_period_tick：只有当某周期K线确认时才调用（低频）

**但周期K线确认不也是一种数据更新吗？** 而且 on_period_tick 也传 dirty_codes，和 on_data_updated 一样。

两者的本质区别是什么？
- 是"数据类型"不同（tick vs bar）？
- 还是"更新频率"不同（高频 vs 低频）？
- 还是"计算时机"不同（实时计算 vs K线确认后计算）？

如果是"计算时机"不同，那应该是公式引擎内部的策略——有些公式只在K线确认后才重算，有些每个tick都重算。这不需要两个接口，公式引擎自己根据公式的配置来决定就行。

**问题3：register_formula 的返回值不明确。**

文档说 register_formula 返回 formula_id，但：
- formula_id 是调用方传的（formula_def 里有 id 字段），还是公式引擎生成的？
- 如果 formula_def 里没有 id 字段，怎么办？
- 如果重复注册同一个公式，返回同一个 id 还是新的 id？
- 如果公式语法错误，返回什么？抛出异常还是返回错误码？

这些边界条件都没说。

**问题4：start/stop 是空的。**

start 的描述是"预热缓存（可选）、启动后台线程、注册定时器"——但这些都是"可选"的，那 start 到底做什么？

**start/stop 更像是生命周期的仪式感，没有实际的契约。**

### 5.3 公式引擎和股票池引擎的边界

**文档说公式引擎是"黑盒，股票池引擎不直接访问"内部表，这是对的。**

但有一个边界问题：**公式引擎知道节点的概念吗？**

从接口来看，公式引擎只知道 formula_id、code、period，不知道 node。这是对的——公式引擎是通用的，不应该知道股票池的节点概念。

**但有一个问题：node_data_dirty 是按节点存的，而通知公式引擎用的是 dirty_stocks（全局的）。** 

这意味着：
- 股票池引擎知道"哪些节点包含哪些股票"（code_nodes 映射）
- 公式引擎不知道节点，只知道股票
- 所以通知公式引擎时，只能传全局的 dirty_stocks，公式引擎失效所有相关公式的缓存

**但如果某只股票只在节点A里，不在节点B里，而公式X只被节点B的边引用——那这只股票的数据更新了，公式X的缓存需要失效吗？**

从正确性来说，不需要——因为节点B永远不会用这只股票的公式X结果。但从实现来说，公式引擎不知道节点，所以只能全部失效。

这是一个性能优化点，但不是架构问题。文档可以提一句。

## 六、表驱动深度审查

### 6.1 状态表的语义更丰富了，但逻辑还是硬编码的

**先说好的：状态表的语义确实更丰富了。**

| 表 | v1.8 | v1.9 | 进步 |
|----|------|------|------|
| node_stock_change | bool | {entered: Set, exited: Set} | 从"有没有变"到"怎么变的" |
| edge_compare_results | bool（二态） | True/False/None（三态） | 从"二选一"到"三态语义" |
| edge_filter_results | Set[code] | Set 或 List[code] | 从"无序集合"到"有序/无序" |

这些都是进步——表的内容更丰富了，能表达更复杂的状态。

**但表驱动的核心不是"表的内容丰富"，而是"逻辑在表里"。**

让我们检查一下，哪些逻辑在表里，哪些逻辑在代码里：

| 逻辑 | 在哪里？ | 表驱动吗？ |
|------|---------|-----------|
| 指标计算逻辑 | 公式引擎内部（公式字符串是数据） | ✅ 部分是 |
| 比较算子逻辑 | comparison_operators 表 | ✅ 是 |
| 集合运算逻辑 | 硬编码（AND/OR/NOT/排名） | ❌ 不是 |
| 事件类型 | 硬编码（tick_batch/edge_timer/start/...） | ❌ 不是 |
| 事件处理逻辑 | 硬编码（if-else 分支） | ❌ 不是 |
| 事件优先级 | 硬编码（控制 > 定时器 > 数据） | ❌ 不是 |
| 定时器类型 | 硬编码（once/interval/period/calendar） | ❌ 不是 |
| 批次大小 | 配置参数（算表驱动吗？） | ⚠️ 半是 |
| TTL 逻辑 | 硬编码（入池设时间，过期就移除） | ❌ 不是 |

**真正表驱动的只有：公式、比较算子。** 这两个从 v1.0 开始就是表驱动的，v1.9 没有新增。

**集合运算、事件类型、定时器类型、处理逻辑——全是硬编码的。**

文档说"表驱动"是设计原则，但实际上表驱动只覆盖了很小一部分。大部分逻辑还是写死在代码里的。

### 6.2 事件类型为什么不能表驱动？

**举个例子，事件类型完全可以表驱动：**

```python
# 事件类型表（表驱动）
event_types = {
    "tick_batch": {
        "priority": 3,
        "handler": "handle_tick_batch",
        "batching": True,
    },
    "edge_timer": {
        "priority": 2,
        "handler": "handle_edge_timer",
        "batching": False,
    },
    "start": {
        "priority": 1,
        "handler": "handle_start",
        "batching": False,
    },
    ...
}
```

这样，加新的事件类型只需要加一条记录，不需要改事件循环的代码。

**但文档的事件循环是这样的：**

```python
if event.type == "control":
    ...  # 硬编码
elif event.type == "edge_timer":
    ...  # 硬编码
elif event.type == "tick_batch":
    ...  # 硬编码
```

这不是表驱动，这是"用字典当枚举"。

### 6.3 表驱动的真正价值

**表驱动不是"用表存数据"——那叫数据结构。**

表驱动的真正价值是：
1. **逻辑可变**：改配置就能改逻辑，不需要改代码
2. **可扩展性**：加新类型不需要改核心代码
3. **可配置性**：不同实例可以有不同配置
4. **可验证性**：表的内容可以校验、可以导出、可以可视化

用这个标准来看，v1.9 的表驱动深度还是太浅了。

## 七、架构清晰度审查

### 7.1 三层状态表更清晰了，但"批次"概念把水搅浑了

**三层状态表（指标→比较→集合）的分层是清晰的，而且越来越清晰。**

但 v1.9 引入了"批次"的概念，而且这个概念渗透到了架构的每个角落：

| 地方 | 批次相关 |
|------|---------|
| batch_state 表 | 批次版本号、批次时间戳 |
| dirty_stocks | 本批次的脏股票 |
| node_data_dirty | 批次结束时清空 |
| 事件循环 | 数据事件是 tick_batch（一批） |
| 计算流程 | 批次开始→计算→批次结束 |

**批次本来应该是一个"性能优化手段"，现在变成了架构的一等公民。**

这带来的问题：
1. **概念变多了**：要理解系统，需要同时理解"事件循环"和"批次"两个概念，而且它们的关系很微妙
2. **架构耦合了批次大小**：如果未来想改成逐事件处理，整个架构都要改
3. **版本屏障的概念被滥用**：批次=版本屏障，但其实每个事件都可以有自己的版本号

**更清晰的架构应该是：**
- 核心模型：事件驱动（每个事件一个版本号）
- 性能优化：攒批处理（把多个小事件合并成一个大事件，透明的优化层）
- 用户看到的：还是事件驱动的模型，攒批是底层优化

现在的架构是反过来的——批次是核心，事件是包装。

### 7.2 概念数量：9张表 + 3类事件 + 4种定时器 + 11个接口

**让我们数一下 v1.9 的核心概念：**

| 类别 | 数量 | 说明 |
|------|------|------|
| 核心运行时表 | 9 张 | batch_state + 8张旧表 |
| 编译期表 | 7 张 | formula_registry、comparison_operators、edge_* 等 |
| 公式引擎接口 | 11 个 | 从6个增加到11个 |
| 事件大类 | 3 类 | 数据、定时器、控制 |
| 具体事件类型 | 10+ 种 | tick_batch、period_bar_confirm、edge_timer、ttl_check、start、pause、resume、stop、config_reload、stock_entered、stock_exited |
| 定时器类型 | 4 种 | once、interval、period、calendar |

**概念是不是太多了？**

当然，功能多了概念自然会多。但问题是：**有没有可以合并、可以简化的？**

举几个例子：
- eval_indicator 和 eval_indicators 能不能合并？
- on_data_updated 和 on_period_tick 能不能合并？
- 数据事件的两种（tick_batch、period_bar_confirm）能不能合并成一种？
- stock_entered/stock_exited 算不算"事件"？它们是内部产生的，还是对外的通知？

文档追求"概念丰富"，但好的架构追求"概念最少"。

### 7.3 边界问题：事件循环和批次计算引擎的关系

**文档的架构图是这样的：**

```
事件循环 → 事件分发器 → 数据事件处理器 → 批次计算引擎
```

**但批次计算引擎不就是数据事件的处理器吗？** 为什么要分成两层？

而且：
- 定时器事件的处理走不走批次计算引擎？看起来不走，定时器事件有自己的处理逻辑
- 控制事件的处理走不走批次计算引擎？也不走
- 只有数据事件走批次计算引擎

**那批次计算引擎其实就是"数据事件处理器"，没必要单独拎出来作为一层。**

文档的分层有点过度设计了——为了显得"架构层次多"，硬拆了很多层。实际上，事件循环 + 事件处理器（每种事件一个处理器）就够了。

## 十、3条最深刻洞见 + 3条最肤浅理解

### 最深刻的3个洞见

**洞见1：node_stock_change 结构化（entered/exited 双集合）**

从 bool 到 entered/exited，这不是简单的数据结构升级，而是认知升级——从"知道变了"到"知道怎么变了"。只有知道变化的具体内容，才能做到真正的增量处理（入池初始化、出池清理）。这是增量计算的基石，方向完全正确。

**洞见2：时间驱动独立化为独立事件源**

把时间触发从"数据更新时顺便检查"剥离出来，变成独立的定时器事件源，这是从"伪事件驱动"到"真事件驱动"的关键一步。时间和数据是两个独立的变化维度，必须解耦。这个方向是对的。

**洞见3：比较层三态化（True/False/None）**

从二态到三态，表面上只是多了一个值，实际上是对"数据不确定性"的正视。真实世界里，不是所有股票都有足够的数据来判断条件满足与否。三态化让状态的语义更准确，也为后续的逻辑传播（None 的传播规则）打下基础。

### 最肤浅的3个理解

**肤浅1："单线程事件循环就能解决并发一致性"**

这是对并发模型的肤浅理解。单线程确实能避免竞态条件，但代价是 CPU 密集型计算会阻塞整个事件循环，导致定时器事件延迟、控制事件无法响应。Python 的 GIL 使得多线程也无法利用多核。文档只谈了单线程的好处，完全回避了性能代价和应对方案，好像单线程是银弹。

**肤浅2：把"微批处理"包装成"事件驱动"**

事件驱动的本质是"每个变化都是独立事件，逐事件处理"。攒批处理是微批处理，是批处理的变种。文档把 tick_batch 叫"数据事件"，然后说自己是事件驱动架构——这是偷换概念。批次化是性能优化，不应该上升到架构核心，更不应该改变事件的语义。

**肤浅3："批次化 = 版本屏障"**

批次化和版本屏障是两个不同的概念。批次化是性能优化（合并多个事件减少 overhead），版本屏障是一致性保证（计算基于一致的快照）。文档把它们绑在一起，好像批次化天然就有版本屏障。实际上，版本屏障可以在单事件粒度上实现（每个事件一个版本号），批次化只是把多个事件合并成一个版本。把两个概念混为一谈，是对一致性模型的肤浅理解。
