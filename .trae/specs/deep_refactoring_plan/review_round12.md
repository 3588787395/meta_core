## 二、逐维详细评审

### 2.1 行为洞察深度（22/30）

**进步点：**
- 从"事件驱动包装"到"诚实承认轮询"——这是态度的根本转变，值得肯定
- 有代码验证意识（engine.py:3711-3718、engine.py:2066-2093），不是空口说白话
- 区分了"计算时间"和"延迟"——这是重要的认知突破
- 识别出"变了才算，不变跳过"的增量计算模式

**核心问题：**

1. **对股票池业务本质理解浅**
   - 股票池的核心是什么？是"选股条件的组合与演进"，还是"数据流的计算图"？
   - 文档偏向后者（计算图视角），但前者（业务视角）可能更本质
   - 没有回答"为什么需要节点和边"这个根本问题——用纯配置式的条件组合不行吗？

2. **对实盘复杂度几乎无感**
   - 停牌、复牌、新股上市、退市、涨跌停、集合竞价、连续竞价、盘前盘后、节假日……
   - 这些实盘场景下，架构如何应对？完全没提
   - 比如：停牌股票数据不更新，dirty_stocks 里没有，那指标值是用旧的还是设为 None？
   - 比如：新股上市第一天，历史数据不足，指标怎么算？三态怎么处理？

3. **对"时间维度"理解严重不足**
   - 股票计算的核心复杂度之一是多周期（1分钟、5分钟、15分钟、日线、周线……）
   - 不同周期的 K 线数据如何同步？指标如何跨周期引用？
   - 周期边界的数据一致性如何保证？（比如 10:30 的 5 分钟 K 线什么时候算"完成"？）
   - 文档里完全没有讨论这些，说明对股票计算的本质理解还很浅

4. **公式引擎黑盒态度**
   - 文档明确写"公式引擎内部表（黑盒）"——但性能瓶颈就在公式引擎
   - 不理解公式引擎的内部机制，性能估算就是空中楼阁
   - 指标缓存的粒度是什么？是按股票缓存还是按公式缓存？缓存失效策略是什么？
   - 这些问题不搞清楚，"指标层占85%"的结论就是拍脑袋

5. **没有错误处理和容错概念**
   - 实盘系统，错误处理是核心功能，不是边角料
   - 数据缺失怎么办？公式计算出错怎么办？网络中断怎么办？
   - 部分股票数据更新失败，是整轮跳过还是部分处理？
   - 完全没有讨论，说明还停留在"理想情况"的思考层面

### 2.2 表驱动深度（14/25）

**进步点：**
- 从"状态表"到"行为表"——方向完全正确，这是 v1.12 最大的亮点
- 4张行为表的设计有一定道理
- 有伪代码示例，不是光说不练
- 识别出"用表存数据 ≠ 表驱动"——这个认知很重要

**核心问题（严厉批评）：**

#### 问题1："加新节点类型不改代码"是**虚假承诺**

文档声称"加新节点类型 = 加一行，不改引擎代码"，但仔细看就知道是假的：

```python
# 文档里的"表驱动"代码
type_def = node_type_table[node_type]
handler_name = type_def['out_edge_handler']
handler = handler_registry[handler_name]
handler(nid, node, node_changes[nid])
```

这只是"把 if-else 分发改成查表分发"，**不是真正的表驱动**。

为什么？因为：
- 加新节点类型，还是要写新的 handler 函数
- handler 函数里的逻辑还是代码，不是配置
- 引擎代码确实不用改，但**业务代码还是要写**
- 这叫"策略模式"或"注册表模式"，不叫"表驱动"

**真正的表驱动是什么？**
- 通过配置组合现有的行为原子，就能产生新的节点类型
- 连 handler 的逻辑都是由表数据组合出来的
- 加新类型 = 加配置行 + 组合已有原子，不需要写新函数

**当前的水平：** 只是"分发方式表驱动"，不是"行为逻辑表驱动"。

#### 问题2：行为表数量**远远不够**

只有 4 张行为表，但系统里的行为维度远不止 4 个。至少还缺：

| 缺失的行为表 | 作用 | 为什么重要 |
|------------|------|----------|
| **时间条件表** | 定义不同的定时策略（按时间点、按周期、按事件） | 边的触发时机是重要行为维度，现在散落在 edge_timer_specs 里 |
| **TTL 策略表** | 定义不同的 TTL 策略（固定时长、滑动窗口、收盘清零、交易时间累计） | TTL 是股票池的核心功能，现在只有堆队列，没有策略抽象 |
| **指标计算策略表** | 定义不同的计算策略（全量/增量、缓存策略、预计算策略） | 性能优化的核心，现在是黑盒 |
| **数据结构表** | 定义节点用什么数据结构存股票（Set、List、OrderedList、Heap、Dict） | 不同节点需要不同的数据结构，现在隐含在代码里 |
| **事件发射策略表** | 定义事件如何发射（立即/批量/延迟、去重策略、顺序保证） | 事件是对外接口，策略很重要 |
| **后处理策略表** | 定义后处理行为（排名、分组、聚合、预警） | 后处理是独立维度，不应混在节点里 |

#### 问题3：行为表颗粒度和正交性差

`node_type_table` 把多个正交维度混在一张表里：
- init_handler（初始化策略）
- in_edge_handler（入边处理策略）
- out_edge_handler（出边处理策略）
- allowed_roles（角色）
- has_stocks（数据结构特征）

这些维度是**正交**的，应该分开：
- 节点类型 = 数据结构类型 × 初始化策略 × 入边策略 × 出边策略 × 角色约束

混在一起的后果：
- 组合爆炸：如果有 5 种初始化策略 × 5 种入边策略 × 5 种出边策略，难道要定义 125 种节点类型？
- 复用困难：两种节点类型只是初始化不同，其他都一样，也要重复定义？

#### 问题4：没有 Schema 和校验机制

- 行为表的结构定义在哪里？
- 配置错了怎么办？比如 node_type_table 里引用了一个不存在的 handler_name
- 有没有启动时校验？有没有配置版本管理？
- 没有 Schema 的表驱动是危险的——错了才发现，而且可能是运行时才炸

#### 问题5：行为表和状态表的映射关系不清晰

- 每种行为操作哪些状态表？
- 有没有约束？比如"只有 propagate 行为能修改 node_stocks"
- 会不会出现"行为A操作了表X，行为B也操作表X，产生冲突"？
- 没有明确的读写权限边界，表再多也是乱的

### 2.3 事件/轮询模型准确性（17/20）

**进步点（巨大）：**
- 诚实承认是轮询模型，不是事件驱动——这是认知的巨大飞跃
- 正确指出"延迟 = tick_interval"，还有时间线示例
- 区分了"计算时间"和"延迟"——很多人搞不清这个
- 有代码验证，不是空口狡辩

**问题：**

1. **"脏驱动计算"仍有包装嫌疑**
   - 本质就是"增量计算"（Incremental Computing），这是计算机科学里的标准术语
   - 为什么要叫"脏驱动"？因为听起来更像是一种架构模式？
   - 文档把"脏驱动"和"轮询"并列，作为架构的两个支柱，但"脏驱动"的分量远远不够
   - "轮询数据 + 增量计算 + 拓扑传播"才是准确的描述，"脏驱动"只是实现细节

2. **对轮询模型的理解不完整**
   - 只说了"延迟 = tick_interval"，但轮询模型的内涵远不止这个
   - 轮询频率如何选择？是固定频率还是自适应？
   - 数据更新频率和轮询频率不匹配怎么办？（比如数据源 3 秒才更一次，轮询 1 秒就是浪费）
   - 忙时（交易时段）和闲时（非交易时段）的轮询策略要不要不一样？
   - 轮询失败怎么办？数据源超时怎么办？重试还是跳过？

3. **简单否定事件驱动，但没有讨论"轮询之上如何模拟事件语义"**
   - 业务层可能还是需要"事件"这个概念（价格突破、成交量异动、入池出池）
   - 入池/出池通知，本质上就是事件，但文档没有把它纳入统一的事件模型
   - 正确的说法应该是："数据获取层是轮询，但业务层可以有事件语义，事件是通过对比轮询结果产生的"
   - 简单地说"不是事件驱动"，容易把洗澡水和孩子一起倒掉

4. **没有讨论混合数据模式**
   - 实盘系统中，可能既有轮询的数据（行情快照），也有推送的数据（成交回报、订单状态）
   - 架构如何统一处理这两种数据来源？
   - 推送来的数据，是直接进入 dirty_stocks，还是等下一轮轮询？
   - 完全没提，说明对实盘数据来源的多样性理解不足

### 2.4 架构清晰度（10/15）

**进步点：**
- 脏标记体系收敛，从 3 套变 2 套，概念更清晰
- 有表清单，每张表有类型、读时机、写时机、说明
- 有分层性能模型，虽然估算还比较糙

**问题：**

1. **概念还是太多**
   - 7 张状态表 + 4 张行为表 + 公式引擎内部表 + 编译期表 = 十几张表
   - 很多表的边界模糊，比如：
     - `edge_compare_results`（三态比较结果）和 `edge_filter_results`（过滤结果）能不能合并？
     - "三态"（True/False/None）是不是必要的？能不能用"不在集合里 = None"来表达？
   - 概念越多，认知负担越重，出错概率越高

2. **分层边界模糊**
   - 文档里有"五层性能模型"（数据层/指标层/比较层/集合运算层/传播层）
   - 但"边执行层"又是"三层 filter"（指标计算/比较判断/集合运算）
   - 这两种分层是什么关系？是一个东西的两种说法吗？
   - "后处理层"（PK排名、分析角度、看盘面板、预警）到底算不算架构核心？
   - 分层不清晰，读者会困惑"到底有几层"

3. **核心抽象缺失**
   - 没有定义"节点"的本质：节点 = 股票集合 + 状态 + 行为？
   - 没有定义"边"的本质：边 = 条件 + 传播？
   - 没有定义"传播"的本质：传播 = 集合变换 + 状态更新 + 事件发射？
   - 都是在描述"有什么"（机制），没有抽象出"是什么"（本质）
   - 没有核心抽象，架构就像散沙，概念只会越来越多

4. **没有"不变量"和"约束"的概念**
   - 架构设计中，"什么是不变的"比"什么是变的"更重要
   - 比如："拓扑序不变"、"节点股票只由 propagate 修改"、"dirty_stocks 只在 tick 开始时更新"
   - 这些不变量和约束，是架构正确性的保证
   - 文档里完全没有讨论，说明架构设计还停留在"功能罗列"的层面

**问题：**

## 三、12条具体改进建议

### 建议1：用"增量计算"替代"脏驱动计算"（P0）
- 问题："脏驱动"是非标准术语，有包装嫌疑
- 建议：统一使用计算机科学标准术语"增量计算"（Incremental Computing）
- 理由：准确、专业、不包装，业内人一看就懂
- 影响：全文替换，不影响架构实质

### 建议2：拆穿"加新类型不改代码"的虚假承诺，诚实定义表驱动的层级（P0）
- 问题：当前只是"分发表驱动"，却声称"行为表驱动"
- 建议：明确定义表驱动的三个层级：
  - **L1：分发表驱动**（当前水平）—— if-else 改查表，handler 还是写代码
  - **L2：组合表驱动**（目标水平）—— 行为由原子操作组合而成，配置决定组合方式
  - **L3：声明式表驱动**（理想水平）—— 纯声明式配置，引擎解释执行
- 理由：诚实比包装重要，明确当前水平，才能知道前进方向

### 建议3：拆分 node_type_table，恢复正交性（P0）
- 问题：多个正交维度混在一张表里，导致组合爆炸
- 建议：拆成多张独立的行为表：
  - `init_strategy_table`（初始化策略）
  - `in_edge_strategy_table`（入边处理策略）
  - `out_edge_strategy_table`（出边处理策略）
  - `data_structure_table`（数据结构类型）
  - 节点类型 = 这些策略的组合引用
- 理由：正交设计是可扩展性的基础

### 建议4：补充时间维度的架构设计（P0）
- 问题：完全没有讨论多周期、时间同步等核心问题
- 建议：增加专门的"时间模型"章节，讨论：
  - 多周期 K 线的同步机制
  - 周期边界的数据一致性保证
  - 交易时间 vs 自然时间的处理
  - 历史数据回放的时间模型
- 理由：时间是股票计算的核心维度，回避不了

### 建议5：补充实盘边界场景的处理设计（P1）
- 问题：完全没有讨论停牌、复牌、新股、退市等实盘场景
- 建议：增加"边界场景处理"章节，至少覆盖：
  - 停牌股票的处理（数据不更新时指标怎么算）
  - 新股上市的处理（历史数据不足时怎么办）
  - 涨跌停的处理（价格不动时算不算变化）
  - 数据缺失的容错策略
- 理由：实盘系统的价值就在于处理边界场景，理想情况谁都会做

### 建议6：把公式引擎从"黑盒"变成"灰盒"，明确接口契约（P1）
- 问题：公式引擎是黑盒，但性能瓶颈就在这里
- 建议：至少明确以下接口契约：
  - 指标缓存的粒度和失效策略
  - 增量计算的支持程度
  - 错误处理和返回值约定
  - 性能基准（每个典型指标的耗时范围）
- 理由：架构不能建立在黑盒之上，接口契约是架构的一部分

### 建议7：合并 edge_compare_results 和 edge_filter_results（P1）
- 问题：两张表功能重叠，概念冗余
- 建议：考虑合并，或者明确分工：
  - 方案A：合并为一张表，用"不在集合中 = 不通过"替代 False
  - 方案B：明确 edge_compare_results 只存 True/None，False 的直接删掉
- 理由：概念越少越好，表越少越好，7张状态表还是偏多

### 建议8：定义架构不变量和约束（P1）
- 问题：没有明确什么是"不能变的"
- 建议：增加"架构约束"章节，明确：
  - 数据流向约束（只能从源到目标，不能反向）
  - 状态修改约束（只有 propagate 能修改 node_stocks）
  - 时序约束（必须按拓扑序处理）
  - 一致性约束（同一 tick 内看到的是一致的快照）
- 理由：不变量是架构正确性的骨架，没有骨架就是一堆肉

### 建议9：补充前后端一体设计（P1）
- 问题：完全没提前后端
- 建议：至少增加"前端配置模型"章节，讨论：
  - 前端配置的数据结构（和后端行为表如何对应）
  - 配置的可视化编辑方案（节点类型下拉框、参数表单等）
  - 前后端配置的一致性保证
  - 前端展示数据的接口设计
- 理由：前后端一体不是锦上添花，是可用性的基础

### 建议10：补充行为表的 Schema 和校验机制（P2）
- 问题：没有 Schema，配置错了运行时才炸
- 建议：
  - 为每张行为表定义 JSON Schema
  - 启动时校验所有行为表配置的合法性
  - 引用完整性检查（handler 是否存在、参数是否匹配）
  - 配置版本管理
- 理由：表驱动越多，校验越重要，否则配置错误就是灾难

### 建议11：性能估算要给出"误差范围"和"测量方法"（P2）
- 问题：估算数字看起来很精确，但都是拍脑袋
- 建议：
  - 每个估算值都给出置信区间（比如 55ms ± 20ms）
  - 明确估算的假设前提（什么 CPU、什么 Python 版本、什么数据量）
  - 给出验证方法（怎么测量每层的实际耗时）
  - 不要用"~55ms"这种看起来很精确的写法，改成"约 50-100ms"更诚实
- 理由：估算的价值不在于精确，而在于诚实和可验证

### 建议12：补充错误处理和容错设计（P2）
- 问题：完全没有错误处理
- 建议：增加"容错设计"章节，讨论：
  - 数据部分失败的处理策略（部分更新 vs 全轮跳过）
  - 公式计算错误的处理（返回 None 还是抛出异常）
  - 超时处理（轮询超时、计算超时）
  - 降级策略（指标算不出来时用什么替代）
- 理由：实盘系统，容错是核心功能，不是边角料

## 四、3条最深刻洞见

### 洞见1：诚实化是架构设计的第一原则
- v1.12 最大的价值不是技术改进，而是态度转变
- 从"包装成事件驱动"到"承认是轮询"，这是质的飞跃
- 很多架构设计的失败，不是技术不行，而是从一开始就不诚实——为了听起来高级而包装概念
- 诚实比正确更重要——错了可以改，但包装会把所有人都带偏
- **建议：把"诚实不包装"写进架构设计原则的第一条**

### 洞见2：表驱动的核心是"组合"，不是"分发"
- 很多人对表驱动的理解停留在"用表替代 if-else"——这只是最浅的一层
- 真正的表驱动是：**定义一组原子行为，然后用表数据来组合这些原子行为，产生新的功能**
- 关键字是"组合"——不是每个新功能写一个新 handler，而是用已有原子拼出来
- 当前的 node_type_table 只是"分发表驱动"（L1），离"组合表驱动"（L2）还有很远
- **建议：不要满足于 L1，往 L2 努力，那才是表驱动的真正价值**

### 洞见3：股票计算的核心复杂度在"时间"，不在"计算"
- 文档花了很多笔墨讨论性能优化、向量化计算，但这些都不是最难的
- 股票计算真正难的是**时间维度**：
  - 多周期 K 线的同步
  - 周期边界的一致性
  - 历史数据的回放和验证
  - 交易时间 vs 自然时间
  - 未来函数的规避
- 这些问题不解决，性能再快也没用——算出来的结果可能是错的
- **建议：下一轮重点研究时间模型，这才是股票系统的技术深水区**

## 五、3条最肤浅理解

### 肤浅1："加新节点类型不改代码"的虚假承诺
- 这是 v1.12 最唬人但也最经不起推敲的说法
- 仔细一看，只是把 if-else 改成了查表，handler 还是要写代码
- 这种说法要么是自己没搞懂表驱动的本质，要么是故意包装
- **严厉批评：架构文档不能有这种虚假宣传，是什么水平就说什么水平**

### 肤浅2：对实盘复杂度的无感
- 文档里的股票池，像是一个"理想实验室"里的东西
- 没有停牌、没有新股、没有数据缺失、没有错误、没有边界情况
- 但实盘不是实验室，90% 的 bug 都出在边界情况
- 架构设计不考虑边界场景，就像建房子不考虑地震——平时没事，一震就塌
- **警告：这样的设计文档，拿去给实盘交易员看，会被笑话的**

### 肤浅3：把"脏驱动"当成架构支柱
- "脏驱动"（增量计算）只是一种实现优化，不是架构支柱
- 架构的支柱应该是：数据模型、计算模型、时间模型、错误模型
- 把"脏驱动"和"轮询"并列，像是在找补——"轮询不够酷，再加个脏驱动听起来高级点"
- 真正的架构，应该是"轮询数据 + 拓扑计算图 + 增量优化"，增量是优化，不是支柱
- **建议：摆正位置，不要用次要概念撑门面**

## 七、总结评价

v1.12 是**"态度正确，但深度不足"**的版本。

**好的方面：**
- 诚实化是巨大进步——停止包装，承认轮询，这比什么都重要
- 从状态表到行为表，方向完全正确
- 脏标记收敛，概念更清晰

**不好的方面：**
- 表驱动深度严重不足——"加新类型不改代码"是虚假承诺
- 业务洞察浅——对实盘复杂度、时间维度、错误处理几乎无感
- 前后端一体完全缺失
- 核心抽象缺失——架构像散沙，概念越来越多

**一句话评价：**
> 诚实了，但还不够深刻；方向对了，但路还很长。

**给 v1.13 的目标分数：75/100**
- 诚实化表驱动层级（+5）
- 补充时间模型（+3）
- 拆分行为表恢复正交性（+2）
- 补充边界场景处理（+2）
- 补充前后端一体设计（+1）
