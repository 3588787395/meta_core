## 二、详细评审意见

### 2.1 重构目标：方向对，但指标激进且缺乏基线

**优点：**
- 一句话目标清晰："大泥球 → 表驱动简洁引擎"，方向正确
- 非目标（什么不做）列得不错，边界意识有了
- 有量化思维，不是空喊口号

**问题：**

1. **性能指标拍脑袋，没有基线数据**
   - "空转性能 ≥ 100x"、"单条边 ≥ 10x"、"全量 ≥ 5x" —— 这些数字哪来的？
   - 现状基准测试在哪？没有基线谈什么提升倍数？
   - 建议：先跑基准测试，用真实数据定目标，而不是拍脑袋写漂亮数字

2. **代码行数目标过于激进**
   - engine.py 从 3884 行（实际值，不是文档写的 3504）降到 ≤ 800 行
   - 减少 79%，相当于把 80% 的代码都搬走
   - 问题：核心循环 + 脏标记 + 事件分发 + TTL 淘汰 + 运行模式切换，这些本身就要几百行
   - 建议：目标调整为 ≤ 1200 行更现实，800 行是把核心逻辑也搬出去了，那 engine.py 还剩什么？

3. **"运行时表从 29 张降到 4 张"是偷换概念**
   - 现状 29 张表是怎么统计的？包含哪些？
   - 目标 4 张是"核心运行时表"，但 node_stocks 实际上每个节点一张，怎么算 1 张？
   - 建议：明确统计口径，不要玩数字游戏

---

### 2.2 核心原则：有理念，但缺可操作的判断标准

**优点：**
- 四条原则（表驱动、数据驱动、事件驱动、前后端一体）方向正确
- 每条原则有一句话总结，便于传播

**问题：**

1. **"表驱动原则"的判断标准不够严谨**
   - "新增一种同类功能，只需要加一条表记录，不需要改引擎代码" —— 这个标准很好
   - 但问题：什么算"同类功能"？边界在哪？
   - 比如新增一种传播模式，算不算"同类"？如果算，那 3 种传播模式为什么要写代码而不是纯配置？

2. **"数据驱动原则"的判断标准太绝对**
   - "水位线不变时，引擎开销为 0" —— 这不可能
   - 至少要检查水位线本身吧？函数调用、哈希比较这些不算开销？
   - 建议改成"水位线不变时，引擎开销可忽略（< 1% 正常计算开销）"

3. **"事件驱动原则"没有判断标准**
   - 只有描述，没有"怎么验证做到了"的标准
   - 建议补充：每个事件都能追溯到触发它的边和节点

4. **缺少"演进式重构"原则**
   - 这么大的重构，怎么保证随时可以回退？
   - 怎么保证每一步都可验证？
   - 这是比技术原则更重要的工程原则，居然没提

---

### 2.3 目标架构：方向正确，但细节经不起推敲

#### 2.3.1 架构分层

**问题：**

1. **缺少"接口层/适配层"**
   - 核心引擎怎么和外部交互？API 层在哪？
   - 数据推送的入口在哪？是直接调 tick_table.update 吗？
   - 建议增加明确的"接口层"，定义引擎的输入输出契约

2. **"编译期"和"运行时"的边界没划清**
   - CompiledPool 是编译期产物，但运行时会不会改它？
   - flow_state（执行次数、持续时间）是运行时数据，放在哪？文档里 timing 模块提到了 flow_state，但运行时表清单里没有
   - 这是一个明显的遗漏：flow_state 表在哪？

3. **后处理层定义模糊**
   - "PK排名 / 分析角度 / 看盘面板 / 预警通知" —— 这些是完全不同的东西
   - 预警通知应该属于 events 模块，不应该放在后处理
   - 看盘面板是 UI 层的，为什么在后端后处理里？

#### 2.3.2 核心表清单

**运行时表（4张）—— 严重不够：**

1. **缺少 flow_state 表**
   - 时间触发需要记录"执行次数"、"持续时间"、"首次触发时间"等状态
   - 文档里 timing 模块明确提到了 flow_state，但表清单里没有
   - 这是运行时状态，必须有地方存

2. **缺少 dirty 标记表**
   - `_data_dirty: Set[nid]` 和 `_stock_dirty: Set[nid]` 不是表吗？
   - 如果算运行时状态，为什么不在核心运行时表里？
   - 不要因为是 Set 就不算表，本质上就是运行时状态表

3. **缺少 edge_flow_state 表**
   - 每条边的时间触发状态是独立的，不是按节点存的
   - 29 张降到 4 张是靠"不列出来"实现的？这不行

4. **node_stocks_ts 是冗余的吗？**
   - node_stocks 变化时更新 ts，那为什么不直接把 ts 放进 node_stocks 的结构里？
   - 还是说 node_stocks 是纯数据，ts 是元数据？这个设计决策需要说明

**配置表（8张）—— 基本合理但有疑问：**

1. **edge_semantics.json 为什么是引擎直接读？**
   - 边类型语义应该在编译期就解析好了，运行时不需要读
   - 编译器读了，编译成 edge_type 字段就行

2. **runtime_modes.json 引擎直接读？**
   - 运行模式（实盘/回放/仿真）应该是启动时确定的，不是运行时动态读的
   - 这应该是构造参数，不是配置表

3. **ttl_rules.json 为什么引擎直接读？**
   - TTL 淘汰规则应该编译成节点属性，运行时不需要读配置表
   - 8张核心配置表的定义标准是什么？看起来有点随意

#### 2.3.3 核心模块（8个）—— 划分基本合理，但有重叠

**问题：**

1. **engine.py 和 events.py 的职责边界模糊**
   - engine.py 里有"事件生成"，events.py 也有
   - 建议：engine.py 只负责调度和流程，事件的创建和处理全归 events.py

2. **filters.py 承担了太多**
   - "6 种求值器 + 10 种比较器" + 三套 filter 统一
   - 目标 300 行够吗？我怀疑
   - 建议：如果太复杂，可以拆成 filter_eval.py（求值器）和 filter_compare.py（比较器）

3. **roles.py 是不是太薄了？**
   - 5 种角色，150 行，会不会只是一个分发器？
   - 如果角色行为只是"调用不同的事件生成函数"，那是不是应该合并到 events.py？

4. **缺少 ttl 模块**
   - TTL 淘汰是重要功能，文档里提到了 ttl_rules.json，但没有对应的模块
   - TTL 逻辑放在哪？engine.py 里？那 engine.py 又多了一块

#### 2.3.4 核心流程

**问题：**

1. **脏标记机制描述不完整**
   - "水位线涨了 → 所有源节点标记为'数据脏'" —— 只有源节点？
   - 中间节点的数据脏怎么来？是靠股票脏传播吗？
   - 数据脏和股票脏的区别是什么？文档说数据脏是"水位线涨了，输入数据可能变了"，那过滤条件依赖数据，所以所有有入边的节点都可能数据脏？不对，应该是源节点数据脏，然后边执行后目标节点股票脏

2. **清脏标记的逻辑有疑问**
   - "所有节点的数据脏标记清除（股票脏保留到下轮？）" —— 这个问号说明自己也不确定
   - 股票脏为什么要保留到下轮？下轮水位线涨了，数据脏了，股票脏还有意义吗？
   - 建议：明确脏标记的生命周期，不要留问号

3. **事件生成时机描述不准确**
   - "生成事件（角色表驱动）"写在边执行里
   - 但角色行为是节点级的，不是边级的
   - 应该是：propagate 后目标节点股票变了 → 触发角色行为 → 生成事件
   - 这个因果关系要理清楚

4. **TTL 淘汰在哪？**
   - 核心流程里完全没提 TTL
   - TTL 是在边遍历前做？还是后做？还是独立的步骤？
   - 这是核心功能，不能漏掉

### 2.4 问题诊断：基本准确，但漏掉了根本问题

**优点：**
- 5个问题都真实存在，不是伪问题
- 每个问题有表现、影响、根因，结构完整
- "拓扑与执行顺序混淆"这个问题抓得好，很多人意识不到

**问题：漏掉了更根本的架构缺陷**

1. **缺少"可测试性"问题**
   - 现在的引擎好测试吗？单元测试能覆盖多少？
   - 3884 行的 engine.py，怎么测？
   - 重构目标里应该包含可测试性的提升

2. **缺少"状态管理混乱"问题**
   - 运行时状态散落在各处，没有统一的状态管理
   - 这才是"大泥球"的根本原因之一
   - 5个问题都是现象，状态管理混乱是根因

3. **缺少"错误处理和容错"问题**
   - 引擎运行中出错了怎么办？
   - 单条边执行失败会不会影响整个池？
   - 数据异常怎么处理？
   - 一个生产级的引擎，容错是核心问题

4. **问题三只说了"三套 filter 各搞一套"，没说为什么会这样**
   - 根因是"没有找到 filter 的统一抽象" —— 这个对，但还不够深
   - 更深层的原因是：没有正交分解，没有把"取什么值"和"怎么比较"分开

### 2.5 重构步骤：路线图清晰，但依赖关系错误

**优点：**
- 4个阶段的划分逻辑基本合理：核心 → 外围 → 前端 → 验证
- 每个阶段有目标、产出、验收标准、风险应对

**问题：**

1. **依赖关系图是错的**
   - 文档写的：`T1 ─┐ T2 ─┼─→ T3 ... T4 ─┤ ...`
   - 意思是 T3 依赖 T1/T2/T4/T5/T6/T7？不对吧
   - 看文字说明："T4/T5/T6/T7 可以和 T1/T2 并行开发，然后在 T3 中集成"
   - 那依赖关系应该是：T3 依赖 T1+T2（基础），T3 集成 T4/T5/T6/T7
   - 依赖图画反了或者画乱了，建议重画

2. **阶段时间估计严重乐观**
   - 阶段一：2周（10工作日）做 7 个任务，合计 13 天工作量
   - 且不说 13 天的估计本身就偏低，2周 = 10天，13 > 10，数学题都算错了
   - 还没算集成测试、联调、修 bug 的时间
   - 建议：阶段一定为 3 周更现实

3. **验收标准偏软**
   - "所有现有测试通过" —— 现有测试覆盖率多少？不知道
   - "后处理不影响核心循环" —— 怎么验证？性能 profiler 看调用栈？
   - "用户调的顺序就是执行顺序" —— 怎么测？端到端测试？
   - 建议：每个验收标准要有可执行的验证步骤

4. **缺少"回滚方案"**
   - 重构失败了怎么办？
   - 怎么保证随时可以切回旧引擎？
   - 建议：采用"装饰器模式"或"策略模式"，新旧引擎实现同一个接口，可随时切换

5. **阶段三"前端对齐"放在阶段四前面，对吗？**
   - 阶段三改前端，阶段四才性能验证和回归测试
   - 那如果阶段四发现核心逻辑有问题，前端不是白改了？
   - 建议：阶段四（验证）拆成两部分，核心验证放在阶段二之后，前端对齐放在最后

### 2.6 第一阶段详细计划：任务分解尚可，但细节经不起推敲

#### 2.6.1 任务合理性

| 任务 | 合理性 | 问题 |
|------|--------|------|
| T1: tick_table | 高 | 相对独立，适合起步 |
| T2: compiler | 高 | 编译期独立是核心一步 |
| T3: 核心循环 | 高 | 整个重构的关键 |
| T4: timing 表驱动 | 中 |  timing 逻辑复杂，2天够吗？ |
| T5: filters 表驱动 | 中 | 三套 filter 统一是硬骨头，3天严重低估 |
| T6: propagate | 高 | 简单，0.5天合理 |
| T7: roles | 中 | 角色和事件耦合，单独抽离有难度 |

**主要问题：**

1. **T5（filters）工作量严重低估**
   - 三套 filter 统一 + 6 求值器 + 10 比较器 + 60 组合
   - 还要从 3884 行里剥离出来，还要写单元测试
   - 3 天？开玩笑，至少 5-7 天
   - 而且这是核心难点，不是边边角角

2. **T4（timing）也低估了**
   - 8 种 starttype × 3 种 cxtype = 24 种组合
   - 还要管理 flow_state（执行次数、持续时间等）
   - 2 天紧张，建议 3 天

3. **任务顺序不对**
   - T3（核心循环）依赖 T4/T5/T6/T7 吗？
   - 如果 T4/T5 还没写完，T3 怎么集成？
   - 建议：T1+T2 先做，然后 T4/T5/T6/T7 并行，最后 T3 集成
   - 或者 T3 先搭骨架，用 mock 的 timing/filters，然后逐个替换

#### 2.6.2 验收标准

**普遍问题：太笼统，不可操作**

1. **T1 验收："engine.py 减少约 200 行"**
   - "约"是多少？180 行不行？220 行不行？
   - 建议：给范围，比如 150-250 行

2. **T2 验收："执行顺序按 _order 排序，不是拓扑序"**
   - 怎么验证？写个测试用例？
   - 如果 _order 字段不存在怎么办？默认行为是什么？
   - 建议：补充边界情况的验收标准

3. **T3 验收："行为等价性：新旧引擎同样输入同样输出"**
   - 这是整个第一阶段的验收标准，不是 T3 一个任务的
   - T3 刚写完核心循环，T4/T5/T6/T7 还没集成，怎么验证等价性？
   - 建议：每个任务的验收标准要和任务范围匹配，不要把最终目标塞给单个任务

4. **缺少负面测试的验收标准**
   - 异常输入怎么办？
   - 非法配置怎么办？
   - 空数据怎么办？

#### 2.6.3 风险应对

**问题：太笼统，像模板**

1. **"行为不一致"风险应对："新旧引擎对比测试"**
   - 废话，当然要对比测试
   - 具体怎么对比？全量还是抽样？
   - 发现不一致怎么定位？有没有工具？
   - 建议：写清楚对比测试的策略和工具

2. **"工作量超预期"应对："T4/T5 可先做最小可用版"**
   - 什么是"最小可用版"？哪些功能可以砍？
   - 砍了之后怎么保证整体能跑？
   - 建议：明确定义 MVP 范围

3. **缺少"人员风险"**
   - 几个人做？如果只有一个人，13天的任务2周做不完很正常
   - 有没有 bus factor 问题？

4. **缺少"技术债风险"**
   - 重构过程中会不会引入新的技术债？
   - 为了赶进度，会不会留下一堆 TODO？

## 三、3个最严重的问题

### ❌ 严重问题 1：依赖关系和工作量估计错误，第一阶段必然延期

**表现：**
- 第一阶段 2 周（10 工作日），任务合计 13 天，数学上就不可能
- T5（filters 表驱动）3 天严重低估，实际至少 5-7 天
- 依赖关系图是错的，T3 和 T4/T5/T6/T7 的关系没理清楚
- 没有预留集成测试和 bug 修复的时间

**影响：**
- 第一阶段就延期，整个重构计划的可信度直接归零
- 为了赶进度，代码质量下降，引入新 bug
- 团队士气受挫

**建议：**
- 第一阶段调整为 3 周
- T5 调整为 5-7 天
- 重画依赖关系图，明确串行并行
- 增加 20% 的缓冲时间

---

### ❌ 严重问题 2：运行时表设计有明显遗漏，核心流程不完整

**表现：**
- flow_state（时间触发状态）在模块里提到了，但表清单里没有
- dirty 标记是核心机制，但不算运行时表？
- TTL 淘汰在核心流程里完全没提
- 清脏标记的逻辑留着问号，自己都不确定

**影响：**
- 写到一半发现缺东西，设计返工
- 核心流程有漏洞，行为等价性没法保证
- 表驱动的设计不成立，因为有些状态没地方存

**建议：**
- 列出所有运行时状态，一个都不能少
- 补充完整的核心流程图，包含 TTL 淘汰
- 明确脏标记的生命周期和传播规则
- 不要为了"4 张表"的数字好看就不列了，实事求是

---

### ❌ 严重问题 3：验收标准偏软，无法验证重构是否成功

**表现：**
- 性能指标没有基线数据，100x/10x/5x 是拍脑袋
- "行为等价性"怎么验证？全量回归还是抽样？
- 每个任务的验收标准太笼统，不可操作
- 没有负面测试、边界测试的验收标准

**影响：**
- 重构做完了，不知道算不算成功
- 性能有没有提升，提升了多少，说不清楚
- 行为不一致的 bug 到线上才发现

**建议：**
- 先做基准测试，拿到真实基线数据

## 七、总体评价

### 这个规划能指导重构吗？
**部分能，但需要大改。**
- 方向是对的：表驱动、数据驱动、事件驱动、编译期/运行时分离
- 但细节漏洞太多，按这个计划做，第一阶段必然延期
- 需要补全设计细节、调整工期、完善验收标准，才能真正指导执行

### 目标能达成吗？
**方向能达成，但指标要调整。**
- "表驱动的简洁引擎"这个目标能达成
- 但 "engine.py ≤ 800 行"、"性能提升 100x" 这些数字目标太激进
- 调整为更合理的指标，是可以达成的

### 最大的风险是什么？
**第一阶段延期导致整个计划失控。**
- 工作量低估 + 依赖关系错误 + 没有缓冲 = 必然延期
- 第一阶段就延期，团队信心受挫，后面的阶段就更难了
- 为了赶进度牺牲质量，最后重构变成乱上加乱

### 最需要改进的地方是什么？
**实事求是，不要追求漂亮数字。**
- "4 张核心表"、"800 行"、"100x 性能提升" —— 这些数字看起来很厉害，但经不起推敲
- 好的重构规划不是数字越大越好，而是越真实越好
- 建议放下"漂亮指标"的执念，实事求是地评估和规划
