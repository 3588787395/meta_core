## 二、核心声称改进的逐项验证

### 2.1 声称改进1：股票级水位线 dirty_stocks，删除冗余的 data_dirty

**结论：核心方向正确，但细节缺口大，只能算 60% 完成。**

#### 做对的部分：
1. **"指标计算是单股独立的纯函数"——这个洞察是对的。** 股票 A 的数据不影响股票 B 的指标值，这是增量计算的基石。
2. **删除 data_dirty 的逻辑成立。** `data_dirty = (len(dirty_stocks) > 0)`，全局标记确实冗余。
3. **"指标值增量算，排名全量排"——这个分层是对的。** 指标层和排名层是两个不同的问题，优化策略不同。

#### 没说透的部分（关键问题）：

**问题1：排名类 filter 的"全量排"之后呢——状态存在哪里？**

文档说排名要全量排，但排名 filter 的输出是一个股票集合（如"涨幅前10"）。要判断入池/出池，必须和**上一次的排名结果**做差集。这意味着：
- 排名 filter 需要存储"上次的结果集合"
- 这是一张状态表，但核心运行时表（5张）里完全没有

如果每轮都全量重算排名，然后和 node_stocks[tid] 对比，那没问题——但这就不是"增量"了，而是每轮全量重算 filter 结果。文档说"排名全量排"但没说"排名结果也要全量对比"，容易误导。

**问题2：集合运算（AND/OR/NOT）的增量到底怎么做——状态表在哪里？**

文档说"集合运算层-逻辑组合：增量，只重新组合有变化的比较结果"。但：
- AND/OR/NOT 是逐股票的逻辑运算
- 要增量做，必须知道每个子条件对每只股票的历史结果
- 这意味着需要存储：`edge_compare_results[eid][code] = bool`
- 这张表在核心运行时表里完全没有

没有这张表，"比较层增量比较"和"集合运算层增量组合"都是空话——因为你没有上次的结果可以"沿用"。

**问题3：多周期维度完全缺失。**

dirty_stocks 标记的是"股票数据更新了"，但：
- 日线指标：只有当日 K 线变化时才需要重算（通常最后一根变）
- 周线指标：一周才变一次
- 60分钟线：每小时变一次

一只股票来了一个 tick，它的 1 分钟线变了，但日线、周线可能都没变。这时候 dirty_stocks 里的股票也不需要重算所有周期的指标。

文档完全没有讨论"周期级"的粒度问题。公式引擎内部可能处理了，但股票池引擎和公式引擎的接口里也没有体现这个维度。

**问题4：dirty_stocks 怎么传给公式引擎？**

时序图里股票池引擎调用 `eval_indicator_batch(codes=source_codes, ...)`，但没有传 dirty_stocks。然后说"公式引擎内部检查哪些 codes 需要重算"。

问题来了：公式引擎怎么知道哪些股票数据变了？
- 选项A：公式引擎自己订阅数据更新事件 → 那公式引擎和数据层耦合了，而且 dirty_stocks 信息重复维护
- 选项B：公式引擎每次计算时都比较数据版本号 → 有额外开销，而且需要数据层提供版本号
- 选项C：股票池引擎把 dirty_stocks 传给公式引擎 → 这是最直接的，但接口定义里没有这个参数

文档回避了这个关键问题。

### 2.2 声称改进2：公式引擎接口契约 + 时序图

**结论：方向正确，但边界不清晰，接口定义有遗漏，只能算 50% 完成。**

#### 做对的部分：
1. **"股票池引擎只调用公开接口，不关心内部实现"——这个原则是对的。** 职责分离的意识很好。
2. **三个核心接口（eval_indicator / eval_indicator_batch / get_cache_stats）的划分合理。** 单只、批量、统计，覆盖了主要场景。
3. **时序图的整体数据流是对的。** 数据层 → 股票池引擎 → 公式引擎，三层结构清晰。

#### 没说透的部分（关键问题）：

**问题1：接口缺少 dirty_stocks 参数（或等价的数据版本信息）。**

如果股票池引擎已经知道哪些股票变了（dirty_stocks），为什么不传给公式引擎？让公式引擎自己判断是重复劳动，而且：
- 如果公式引擎判断不准（比如判断逻辑有bug），就会出现"该重算的没重算"或"不该重算的重算了"
- 既然股票池引擎已经有 dirty_stocks 了，直接传给公式引擎是最清晰的边界

建议接口改成：
```python
eval_indicator_batch(codes, formula, period, args=None, dirty_codes=None) -> Dict[code, value]
```

dirty_codes 是可选的：传了就用它判断哪些需要重算，不传就公式引擎自己判断。这样接口既灵活又清晰。

**问题2：公式引擎和数据层的关系完全没定义。**

公式引擎计算指标需要 K 线数据。它怎么获取数据？
- 是直接读 `latest_tick`？那它和数据层耦合了
- 是通过数据层的接口获取？那接口定义是什么？
- 是股票池引擎把数据传给它？那 eval_indicator_batch 里应该有数据参数

文档完全没有讨论这个边界。公式引擎看起来像一个"自给自足"的黑盒，但它不可能凭空计算指标——它需要数据。

**问题3：多输出指标的返回值语义不清晰。**

接口契约里说"多输出指标返回 dict（{output_name: value}）"，但：
- `eval_indicator_batch` 的返回类型写的是 `Dict[str, float | bool | None]`
- 如果有多输出，value 应该是 dict 才对
- 类型定义不一致

而且，多输出指标在比较层怎么用？比较的是哪个输出？这些都没说。

**问题4：时序图里"公式引擎内部处理"太粗了。**

时序图里公式引擎的三步：
1. 检查哪些 codes 需要重算（内部缓存判断）
2. 对需要重算的股票取最新数据 → 计算指标
3. 更新内部缓存

这三步每一步都涉及和外部的交互（第2步要取数据），但都画成了内部处理。这说明公式引擎和数据层的边界确实没理清楚。

### 2.3 声称改进3：前后端共享规格（JSON Schema）

**结论：只有骨架没有血肉，方向正确但落地性差，只能算 30% 完成。**

#### 做对的部分：
1. **"单一真相源"的理念是对的。** 前后端共用同一份定义，避免不一致，这是行业共识。
2. **三个规格文件（formula_registry / node_types / comparison_operators）的选择合理。** 这三个确实是前后端都需要的。
3. **分三阶段落地的思路务实。** 后端先行 → 前端接入 → 双向校验，节奏不错。

#### 没说透的部分（关键问题）：

**问题1：JSON Schema 到底有什么用？——校验什么？什么时候校验？**

文档说"用 schema 约束格式，自动校验"，但没说：
- 后端什么时候校验？启动时？加载配置时？
- 校验失败怎么办？报错退出？还是降级？
- 前端要不要校验？还是只用来渲染？
- Schema 本身谁来维护？怎么保证 Schema 是对的？

这些都是落地时必须回答的问题，但文档完全没提。

**问题2："共享"到底是什么意思？——文件共享还是 API 共享？**

文档说"前后端共用同一份定义"，但落地路径里写的是"前端从后端 API 获取配置"。

这两个不是一回事：
- **文件共享**：同一份 JSON 文件，前后端代码仓库里都有（通过 git submodule 或 npm 包），前后端编译时都用它
- **API 共享**：前端运行时从后端 API 拉取配置

文件共享的好处是编译时就能用（比如生成 TypeScript 类型），API 共享的好处是动态更新。文档说的是"共享规格"，但落地方案更像"API 动态加载"，概念混淆了。

**问题3：规格文件里内容太多，前端不需要的也给了。**

formula_registry.json 里有 `script`（公式脚本代码），前端真的需要吗？
- 前端公式选择器只需要 id、name、category、description、args、outputs 这些显示用的信息
- script 是后端用来计算的，前端拿到没用，反而可能有安全风险（泄露公式逻辑）

真正的共享规格应该是"前后端都需要的最小交集"，而不是把后端的配置整个扔给前端。

**问题4：没有提到代码生成——JSON Schema 的最大价值被浪费了。**

JSON Schema 最大的价值之一是**代码生成**：
- 后端：JSON Schema → Python dataclass / Pydantic model
- 前端：JSON Schema → TypeScript interface / type

这样前后端不仅共享数据定义，还共享类型定义，编译时就能发现不一致。

文档完全没有提到代码生成，只说了"校验"和"动态渲染"，把 JSON Schema 用浅了。

### 2.4 声称改进4：概念瘦身

**结论：删了 data_dirty 是真瘦身，但 dirty_nodes 语义还模糊，整体算 70% 完成。**

#### 做对的部分：
1. **删除 data_dirty 是正确的。** 全局标记确实冗余，dirty_stocks 信息更丰富。
2. **"节点脏 = 节点里有脏股票 OR 节点股票列表变化"——这个定义是清晰的。** 两种情况都导致节点需要重新处理。

#### 没说透的部分：

**问题1：dirty_nodes 这个名字有误导性。**

文档自己也说"dirty_nodes 这个名字可能也要 reconsider"。为什么？
- "脏节点"听起来像"节点本身的配置变了"
- 但实际上是"节点里的股票有变化"或"节点的股票列表变了"
- 叫 `nodes_to_process` 或 `affected_nodes` 可能更准确

名字不准确会导致理解偏差，这也是概念不清晰的表现。

**问题2：两种"脏来源"混在一个集合里，处理逻辑不一样。**

节点脏有两种来源：
1. 有脏股票（数据更新导致）→ 需要重新计算指标、比较、排名
2. 股票列表变化（入池/出池/TTL过期导致）→ 需要 propagate，但不需要重算指标

这两种情况的处理逻辑完全不同，但混在同一个 dirty_nodes 集合里。处理的时候怎么区分？
- 文档的伪代码里没有区分，都是直接走完整的三层 filter
- 但如果只是股票列表变化（比如 TTL 过期移除了一只股票），源节点里其他股票的指标值都没变，完全不需要重算指标

这是一个潜在的性能浪费，也是概念不清晰的表现。

## 三、12条具体改进建议

### P0 级（必须改，否则落不了地）

1. **补充比较结果状态表 `edge_compare_results`**
   - 比较层要做增量，必须存储上次的比较结果
   - 表结构：`Dict[eid → Dict[code → bool]]`
   - 没有这张表，"增量比较"就是空话

2. **补充排名/集合运算结果状态表 `edge_filter_results`**
   - 排名 filter 和集合运算 filter 都需要存储上次的输出集合
   - 表结构：`Dict[eid → Set[code]]`
   - 用来和本轮结果做差集，得到入池/出池
   - 注意：不是所有 edge 都需要，只有带 filter 的边需要

3. **公式引擎接口增加 `dirty_codes` 参数**
   - `eval_indicator_batch(codes, formula, period, args=None, dirty_codes=None)`
   - 传了就用它判断哪些需要重算，不传就公式引擎自己判断
   - 明确边界：股票池引擎知道哪些股票变了，直接告诉公式引擎

4. **明确公式引擎和数据层的边界**
   - 公式引擎怎么获取 K 线数据？必须说清楚
   - 建议：公式引擎有自己的数据访问接口，不直接读 latest_tick
   - 或者：股票池引擎把数据传给公式引擎（但这样接口就胖了）

5. **区分 dirty_nodes 的两种来源**
   - 不要混在一个集合里，或者加标记
   - 建议拆成两个：`data_dirty_nodes`（有脏股票）和 `list_dirty_nodes`（股票列表变了）
   - 处理逻辑不同，性能优化空间不同

### P1 级（重要，但可以推后）

6. **补充多周期维度的讨论**
   - dirty_stocks 是股票级的，但指标还有周期级的粒度
   - 一只股票来了 tick，不代表它所有周期的指标都需要重算
   - 至少要说明"公式引擎内部处理周期级缓存"，不要完全回避

7. **明确 JSON Schema 的落地细节**
   - 什么时候校验？校验失败怎么办？
   - 是文件共享还是 API 共享？还是两者都有？
   - 要不要做代码生成（Python model / TypeScript type）？
   - 这些问题不回答，JSON Schema 就是摆设

8. **精简共享规格，区分"前端需要的"和"后端需要的"**
   - formula_registry 里的 script 字段前端不需要
   - 建议分成两份：formula_registry_common.json（前后端共享）和 formula_registry_internal.json（后端私有）
   - 或者 API 返回时做裁剪

9. **补充多输出指标的完整语义**
   - eval_indicator_batch 的返回类型要明确支持多输出
   - 比较层怎么指定用哪个输出？
   - 这些都要定义清楚，否则接口契约不完整

10. **时序图细化公式引擎和数据层的交互**
    - 公式引擎"取最新数据"这一步，是和谁交互？
    - 把这个交互画出来，边界才清晰

### P2 级（锦上添花）

11. **考虑给 dirty_nodes 改个更准确的名字**
    - 比如 `affected_nodes` 或 `nodes_to_process`
    - 名字准确了，理解成本就低了

12. **补充增量计算的正确性验证策略**
    - 怎么证明增量计算的结果和全量计算一致？
    - 建议：开发环境下每轮都做一次全量计算，和增量结果对比，不一致就报错
    - 这是保障正确性的关键手段

## 四、3条最深刻洞见

### 洞见1："指标计算是单股独立的纯函数"——这是整个增量优化的基石

文档抓住了最核心的一点：股票 A 的数据不影响股票 B 的指标值。这个洞察是对的，而且是根本性的。

从这个前提出发，才能推导出：
- dirty_stocks（股票级水位线）是可行的
- 只有数据变了的股票才需要重算指标
- 性能可以有数量级的提升

很多人做增量优化时，上来就想"怎么增量更新排名"，反而忽略了最基础、最有效的优化点——指标层本身就是可增量的。文档先抓住了指标层的增量，再讨论排名层的全量，这个分层思路是对的。

### 洞见2："公式引擎是独立模块，股票池引擎只调用接口"——边界意识很好

虽然接口定义还有遗漏，但"股票池引擎和公式引擎是两个独立模块"这个意识是对的。

很多系统里，股票池逻辑和指标计算逻辑是搅在一起的，结果就是：
- 想换个公式引擎（比如从 Python 换成 HQChart），整个系统都要改
- 想优化缓存策略，不知道在哪改
- 想测试股票池逻辑，必须依赖真实的行情数据

明确边界之后，两边可以独立演化、独立测试、独立替换。这是架构成熟的标志。

### 洞见3："排名是相对的，必须全量排"——不盲目追求增量，尊重问题本质

文档没有为了"增量"而硬做增量排名，而是老老实实地承认"排名必须全量排"。这是很可贵的。

很多架构师会陷入"什么都要增量"的误区，结果搞出复杂的增量排名算法，bug 一堆，性能还不一定好。文档承认排名的全量性，然后把优化放在指标层（指标值增量算），这个取舍是明智的。

而且文档区分了"指标层增量"和"排名层全量"，两层用不同的策略，这个分层思维很清晰。

## 五、3条最肤浅理解

### 肤浅1："比较层增量比较"——只说了结论，没说状态存在哪里

文档说"独立比较型 filter：只比较 dirty_stocks ∩ source_codes，其他股票的比较结果沿用上次"。

问题是："沿用上次"意味着上次的结果必须存在某个地方。这张表（edge_compare_results）在核心运行时表里完全没有。

没有状态存储，增量就是空中楼阁。这是典型的"说了结论但没给机制"，听起来很美好，但落不了地。

### 肤浅2："前后端共享规格"——只有 JSON Schema 骨架，没有落地细节

文档花了很多篇幅写三个 JSON Schema 的定义，但最关键的问题一个都没回答：
- 怎么共享？文件共享还是 API 共享？
- 校验什么？什么时候校验？校验失败怎么办？
- 代码生成做不做？
- 前端真的需要这么多字段吗？

JSON Schema 只是工具，不是目的。如果不回答上面这些问题，Schema 写得再漂亮也没用。这是典型的"有骨架没血肉"。

### 肤浅3："公式引擎内部判断缓存失效"——把关键边界问题推给黑盒

文档说公式引擎内部自己判断哪些股票需要重算，但完全没说怎么判断。

这是一个关键的边界问题：
- 如果公式引擎自己订阅数据更新 → 它和数据层耦合了，而且 dirty_stocks 信息重复
- 如果公式引擎每次比较数据版本号 → 有额外开销，而且数据层要提供版本号
- 如果股票池引擎传 dirty_stocks → 最直接，但接口里没这个参数

文档把这个问题推给"公式引擎内部实现"，假装它不存在。但这不是内部实现问题，这是边界问题——两个模块怎么交互的问题。回避边界问题，接口契约就是不完整的。

## 七、总结

v1.7 比 v1.6.1 进步明显，股票级水位线的方向是对的，性能提升的逻辑站得住脚。但问题在于：**很多关键设计停留在"说了结论但没给机制"的层面。**

- 比较层增量？——对，但状态表呢？
- 公式引擎契约？——对，但数据怎么来？dirty_stocks 传不传？
- 前后端共享？——对，但怎么共享？共享什么？

架构设计不是喊口号，而是要把每一个"对的方向"落实到可执行的机制上。v1.7 找对了方向，但离"可落地"还有距离。
