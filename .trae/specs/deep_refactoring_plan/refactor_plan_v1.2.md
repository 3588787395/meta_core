## 1. 重构目标

### 1.1 一句话目标

**把 3500 行的"大泥球"引擎，重构成 10 张核心运行时表 + 8 张核心配置表驱动的、不超过 800 行的简洁引擎。**

### 1.2 量化目标

| 指标 | 现状 | 目标 | 减少比例 |
|------|------|------|---------|
| engine.py 代码行数 | 3504 行 | ≤ 800 行 | ≥ 77% |
| 核心循环函数行数 | ~500 行 | ≤ 150 行 | ≥ 70% |
| 运行时表数量 | 29 张 | 10 张核心 | ≥ 66% |
| 核心配置表数量 | 50+ 张（引擎直接依赖） | 8 张 | ≥ 84% |
| 空转性能（水位线不变） | 全量遍历计算 | 直接返回（≈0） | ≥ 100x |
| 单条边触发性能 | 全量遍历 | 只算该边 | ≥ 10x |
| 全量计算性能 | 基准 | ≥ 5x | ≥ 5x |
| 新旧引擎输出一致性 | - | 100% 一致 | - |

### 1.3 非目标（什么不做）

- **不改变用户可见行为**：所有现有股票池模板必须 100% 兼容，输出结果完全一致
- **不新增功能**：重构期间不加新功能，只简化和整理
- **不重构公式引擎**：FormulaRouter 保持现状，只调整调用方式
- **不重构 UI 框架**：前端 editor.js 只做必要的对齐，不大改
- **不替换数据源**：数据推送接口保持不变
- **不重构 XML 导入导出**：converters 保持现状
- **第一阶段不实现持久化**：设计接口但不实现，状态仍为内存态

## 2. 核心原则

### 2.1 表驱动原则

**逻辑隐含于表结构，差异显示于表内容。**

不是把 if-else 搬进 JSON，而是找到正交维度，用组合表达多样性。

- 时间触发：8 种 starttype × 3 种 cxtype = 24 种组合，用 11 条规则覆盖
- 过滤条件：6 种 nset × 10 种 noperate = 60 种组合，用 16 个函数覆盖
- 传播模式：3 种模式 = 3 条记录
- 节点角色：5 种角色 = 5 条行为定义

**判断标准：新增一种同类功能，只需要加一条表记录，不需要改引擎代码。**

### 2.2 数据驱动原则

**数据变了才计算，不变不算。**

核心机制：`latest_tick_ts` 时间水位线。

- 水位线没涨 → 所有 K 线数据不变 → 所有公式结果不变 → 所有过滤结果不变 → 什么都不用算
- 节点股票没变 → 该节点的出边不用检查
- 边的时间条件没到 → 即使源节点脏也不执行

**判断标准：水位线不变时，引擎开销为 0（不进入核心循环）。**

### 2.3 事件驱动原则

**过滤完成触发目标节点更新和预警事件。**

不是轮询所有节点，而是脏标记沿边传播：

```
数据更新 → 源节点脏 → 出边入队 → 执行边 → 目标节点脏 → 目标出边入队 → ...
```

但传播是**分轮次**的，每轮内部严格按执行顺序，轮与轮之间传递脏标记。

事件在状态变化时实时生成，不是 tick 末统一差分：

- 入池事件：股票进入目标节点时立即生成
- 出池事件：股票离开节点时立即生成
- 预警事件：目标节点变化时立即检查规则

### 2.4 前端后端一体原则

**拓扑与综合设置表格一致，流程与执行顺序一致。**

- 后端：`edge_order` 列表 = 执行顺序
- 前端：综合设置表格 = 执行顺序的可视化
- 前端：拓扑画布 = 连接关系的可视化
- 调整执行顺序：前端拖拽 → 写回 `edge.params._order` → 后端重新编译

**判断标准：用户在综合设置里看到的顺序，就是实际执行的顺序。**

### 2.5 可验证原则

**没有基准测试的重构都是耍流氓。**

- 性能基准：空转/全量/典型场景，有量化指标
- 正确性基准：新旧引擎对拍，100% 一致
- 每一步重构都有可验证的验收标准
- 自动化测试贯穿始终

### 2.6 容错与降级原则

**一条边出错不影响整个池子，一个池子出错不影响整个系统。**

- 错误隔离：单条边、单只股票的错误不扩散
- 降级机制：核心功能不可用时，有兜底方案
- 快速失败：配置错误在启动时就发现，不带着问题跑
- 优雅恢复：异常退出后能从 checkpoint 恢复

### 3.6 边队列执行模型（v1.2 核心设计）

> **解决 v1.1 的架构级矛盾：边队列排序 vs 流式级联。

#### 3.6.1 问题：排序 vs 级联的矛盾

v1.1 同时声称两件事：
1. `edge_pending_queue` 按 `edge_order` 排序插入
2. 流式级联：前边执行完，目标节点变脏，后边立即入队执行

这两者矛盾。举个反例：
- edge_order: A → B → C → D
- 初始：A 股票脏 → A 执行 → B 股票脏
- 如果队列按 edge_order 排序插入，B 排在队尾
- 此时队列是 [C, D, B]（C、D 本来就在队列里）
- 但流式级联要求 B 执行完才能触发 C

**两种可能的真相：**
1. "广度优先"：同一轮只处理当前脏的，下一轮再处理级联的 → 叫"分轮次"
2. "深度优先"：前边执行完立即执行后边 → 全局 edge_order 无意义

#### 3.6.2 方案一：两轮遍历模型

**思路：** 固定两轮，第一轮条件边，第二轮无条件边。

```
第一轮：按 edge_order 遍历所有条件边
  - 检查 (data_dirty OR stock_dirty) AND time_triggered
  - 执行 filter + propagate
  - 产生的股票脏标记累积，不立即传播

第二轮：按 edge_order 遍历所有无条件边
  - 检查 stock_dirty（含第一轮产生的）
  - 执行 propagate
  - 产生的股票脏标记推迟到下一 tick

**优点：**
- 实现简单，只有两轮，行为可预测
- 每轮内部严格按 edge_order
- 性能好，只有两轮遍历

**缺点：**
- 级联深度受限：无条件边的级联推迟到下一 tick
- 不够灵活：复杂图可能需要多轮
- 条件边和无条件边的划分有点生硬

#### 3.6.3 方案二：单轮拓扑序 + 脏标记累积

**思路：** 按拓扑序遍历，本轮脏标记下一轮生效，最多 N 轮。

```
每轮：按拓扑序遍历所有边
  - 源节点脏 + 时机满足 → 执行
  - 目标节点变脏 → 写入下一轮脏标记
  - 下一轮：同样按拓扑序
重复直到没有新的脏标记或达到最大轮数
```

**优点：**
- 级联深度不受限（只要在最大轮数内）
- 符合数据流方向一致（都是拓扑序）

**缺点：**
- 执行顺序是拓扑序，不是用户定义的 edge_order
- 和"用户可调整执行顺序"的原则冲突
- 多轮遍历性能可能差

#### 3.6.4 方案对比与选择

| 维度 | 方案一：两轮遍历 | 方案二：拓扑序多轮 | 选定方案：分轮次 edge_order 多轮 |
|------|----------------|----------------|-------------------------------|
| 执行顺序 | edge_order | 拓扑序 | edge_order |
| 级联深度 | 1 级（无条件边推迟到下 tick） | 无限（受最大轮数限制） | 无限（受最大轮数限制） |
| 实现复杂度 | 简单 | 中等 | 中等 |
| 性能 | 好（固定两轮） | 中等（可能多轮） | 中等（可能多轮） |
| 用户可控性 | 高（顺序可控） | 低（拓扑序不可调） | 高（顺序可控） |
| 行为可预测性 | 高 | 中 | 中 |
| 和现有引擎兼容性 | 需验证 | 需验证 | 最接近现有引擎行为 |

**选定方案：分轮次遍历模型（按 edge_order，多轮，脏标记累积）**

选择理由：
1. **执行顺序可控**：每轮内部严格按用户定义的 edge_order，符合"用户调的顺序就是执行顺序"
2. **级联深度足够**：最多 N 轮（默认 10 轮），覆盖绝大多数真实场景
3. **实现简单清晰**：每轮就是一次遍历，逻辑清楚
4. **和现有引擎行为最接近**：现有 engine.py 用的就是多轮遍历模型
5. **性能可控**：最大轮数可配置，极端情况也不会死循环

#### 3.6.5 分轮次遍历模型详细设计

**核心概念：**

- **轮（round）**：一次完整的 edge_order 遍历
- **本轮脏标记**：本轮开始时已经确定的脏节点，本轮所有边都能看到
- **下一轮脏标记**：本轮执行过程中新产生的脏节点，累积起来，下一轮才生效
- **最大轮数**：MAX_ROUNDS = 10（防止极端情况死循环）

**执行流程（每 tick 内）：**

```
Tick 开始
  ↓
初始化：
  - 收集初始脏节点（TTL 淘汰 + 源节点数据脏）
  - 当前轮 = 0
  ↓
循环（while 有脏节点 AND 当前轮 < MAX_ROUNDS：
  ↓
  第 1 步：把当前脏节点收集到本轮待执行边集合
    - 遍历所有脏节点的出边
    - 加入 edge_pending_set
  ↓
  第 2 步：按 edge_order 遍历所有边
    - 边在 edge_pending_set 里？
      - 否 → 跳过
      - 是 → 检查触发条件（数据脏/股票脏/时间触发）
        - 不满足 → 跳过
        - 满足 → 执行边
          - 执行 filter/propagate
          - 目标节点股票变了？
            - 是 → 加入 next_round_dirty（下一轮才生效）
            - 否 → 不加入
  ↓
  第 3 步：轮结束
    - 当前脏节点 = next_round_dirty
    - 清空 next_round_dirty
    - 当前轮 += 1
  ↓
循环结束
  ↓
事件后处理 → 输出
```

**关键规则：**

1. **每轮内部严格按 edge_order 执行
2. **本轮产生的脏标记，下一轮才生效**（不会在本轮看到）
3. **每轮都是全量遍历 edge_order**（不是队列，是遍历 + 集合检查）
4. **最大轮数限制**：防止循环依赖图也不会死循环
5. **循环依赖处理**：每条边每 tick 最多执行 MAX_ROUNDS 次？不，是每轮最多一次，总共最多 MAX_ROUNDS 次

#### 3.6.6 伪代码

```python
MAX_ROUNDS = 10

def run_once(compiled, now_ts):
    # Step 1: 数据更新
    if not tick_table.update(tick_data):
        return []  # 水位线没涨，零计算
    
    # Step 2: 初始化
    event_queue.clear()
    current_dirty = set()  # 本轮脏节点
    next_dirty = set()     # 下一轮脏节点
    edge_executed_count = defaultdict(int)  # 每条边执行次数
    
    # Step 3: TTL 淘汰预处理
    for nid in ttl_nodes:
        changed = ttl_evict(nid, now_ts)
        if changed:
            current_dirty.add(nid)
            roles.on_change(...)  # 生成 EXIT 事件
    
    # Step 4: 标记源节点数据脏
    for nid in source_nodes:
        node_data_ts[nid] = now_ts
        current_dirty.add(nid)
    
    # Step 5: 分轮次执行
    round_num = 0
    while current_dirty and round_num < MAX_ROUNDS:
        # 5a: 收集本轮待执行边
        pending_edges = set()
        for nid in current_dirty:
            for eid in out_edges[nid]:
                pending_edges.add(eid)
        
        # 5b: 按 edge_order 遍历执行
        for eid in compiled.edge_order:
            if eid not in pending_edges:
                continue
            
            sid, tid = compiled.edge_endpoints[eid]
            edge_type = compiled.edge_type[eid]
            
            # 检查是否触发
            data_dirty = _is_data_dirty(sid, ...)
            stock_dirty = _is_stock_dirty(sid, ...)
            time_ok = timing.eval_gate(...)
            
            should_exec = False
            if edge_type == 'unconditional':
                should_exec = stock_dirty
            else:  # conditional
                should_exec = (data_dirty or stock_dirty) and time_ok
            
            if not should_exec:
                tracker.record(..., executed=False)
                continue
            
            # 执行边
            old_tgt = node_stocks[tid].copy()
            if edge_type == 'conditional':
                passed, _ = filters.eval(...)
                propagate.apply(..., passed)
            else:
                propagate.apply(..., all_stocks)
            
            # 检查目标节点是否变化
            if node_stocks[tid] != old_tgt:
                next_dirty.add(tid)
                roles.on_change(...)  # 生成事件
            
            edge_executed_count[eid] += 1
            tracker.record(..., executed=True)
        
        # 5c: 准备下一轮
        current_dirty = next_dirty
        next_dirty = set()
        round_num += 1
    
    # Step 6: 事件后处理
    events.post_process()
    
    # Step 7: 返回事件
    return event_queue.events
```

## 4. 现有问题诊断

### 4.1 问题一：运行前与运行时混淆

**表现：**
- 每 tick 都重算拓扑序、重解析边参数、重找端点
- engine.py 里混杂着配置解析、规格编译、运行时逻辑
- CompiledSchedule 存在但没被充分利用，很多信息运行时还在重复计算

**影响：**
- 性能浪费：每 tick 都在做运行前就能做完的事
- 代码混乱：编译逻辑和运行逻辑搅在一起，难以理解和修改
- bug 隐患：重复计算可能不一致

**根因：**
- 没有明确的"编译期"概念，什么都塞进运行时
- 代码是渐进式累加的，没有统一的架构设计

### 4.2 问题二：数据更新与计算逻辑耦合

**表现：**
- 数据推送进来，直接触发全量计算
- 没有"水位线"概念，不知道数据到底变没变
- K 线合成和股票池计算搅在一起

**影响：**
- 性能差：即使数据没变（比如同一秒重复推送），也全量重算
- 逻辑混乱：数据层和计算层边界不清
- 难以优化：不知道哪里该缓存、哪里该跳过

**根因：**
- 没有把"数据变化"作为一等公民来管理
- 缺少统一的数据层抽象

### 4.3 问题三：三套 filter 各搞一套

**表现：**
- unconditional filter：一套逻辑
- conditional filter：一套逻辑
- formula_eval filter：又一套逻辑
- 三套逻辑有重叠，但各写各的

**影响：**
- 代码重复：相似的逻辑写三遍
- 行为不一致：三套逻辑可能有细微差别
- 难以维护：改一个要改三个地方

**根因：**
- 没有找到 filter 的统一抽象
- 没有用表驱动来组织不同类型的 filter

### 4.4 问题四：事件是 tick 末差分生成，不是实时

**表现：**
- 每个 tick 末，统一对比所有节点的新旧状态，生成事件
- 事件和触发它的边执行没有直接关联
- 预警检查也是统一做的

**影响：**
- 事件溯源困难：不知道哪个边触发了哪个事件
- 难以做增量处理：每次都是全量差分
- 不符合事件驱动的直觉：应该是"变化了就发事件"

**根因：**
- 架构上是"轮询"思维，不是"事件驱动"思维
- 脏标记机制不完善

### 4.5 问题五：拓扑与执行顺序混淆

**表现：**
- 用拓扑排序的结果当执行顺序
- 用户在综合设置里调整的顺序不生效
- 前端有拓扑视图、综合设置表格、执行顺序三种说法，后端只有一个拓扑序

**影响：**
- 用户困惑：为什么我调了顺序不生效？
- 前后端不一致：前端说的和后端做的不是一回事
- 策略无法按用户想要的顺序执行

**根因：**
- 没有区分"拓扑（连接关系）"和"执行顺序（处理次序）"两个概念
- 执行顺序没有作为一等公民来设计

### 4.6 问题六：缺少基准测试框架（v1.1 新增诊断）

**表现：**
- 没有性能基准，不知道重构后快了多少
- 没有正确性基准，不知道重构后行为是否一致
- 重构效果全靠"感觉"，没有数据支撑

**影响：**
- 重构是否成功无法量化验证
- 性能退化无法及时发现
- 回归问题只能靠人工测试

**根因：**
- 重构前没有建立基线
- 缺少自动化对比测试框架

### 4.7 问题七：缺少错误处理与生产级设计（v1.2 新增诊断）

**表现：**
- 完全没有错误处理机制：公式错了怎么办？数据缺了怎么办？
- 完全内存态：重启全丢，没有持久化和恢复
- 没有降级机制：核心功能挂了就全挂
- 没有内存管理：大池子会不会 OOM？

**影响：**
- 生产环境不敢用：一出问题就崩，崩了就丢数据
- 难以排查问题：没有错误日志，没有隔离
- 不可靠：像玩具，不像生产系统

**根因：**
- 只考虑了"正常流程"，没考虑"异常流程"
- 缺少生产级思维

## 7. 基准测试与验证框架

### 7.1 为什么需要基准测试

**没有基准的重构 = 盲人摸象。**

重构前必须建立基线，重构后才能量化回答：
1. 行为是不是一样？（正确性）
2. 性能是不是更好？（性能）
3. 代码是不是更简洁？（可维护性）

本章定义完整的基准测试框架，确保重构每一步都可验证。

### 7.2 正确性基准：新旧引擎对拍

#### 7.2.1 对拍原理

```
┌─────────────┐     tick 序列      ┌─────────────┐
│  旧引擎     │ ─────────────────→ │  新引擎     │
│  (基线)     │                     │  (重构后)   │
└──────┬──────┘                     └──────┬──────┘
       │                                     │
       ▼                                     ▼
┌─────────────┐                     ┌─────────────┐
│  旧结果     │                     │  新结果     │
│  (黄金数据)  │                     │             │
└──────┬──────┘                     └──────┬──────┘
       │                                     │
       └───────────────┬─────────────────────┘
                       │
                       ▼
              ┌─────────────────┐
              │  逐字段对比      │
              │  输出差异报告    │
              └─────────────────┘
```

| 对比层级 | 对比内容 | 通过标准 |

### 7.3 性能基准：三种场景

#### 7.3.1 场景定义

| 场景 | 描述 | 测量指标 | 目标提升 |
|------|------|---------|---------|
| **空转性能** | 数据完全不变（水位线不涨） | 单 tick 耗时 | ≥ 100x |
| **单条边触发** | 只有一条边的源节点变脏 | 单 tick 耗时 | ≥ 10x |
| **全量计算** | 所有股票都变，所有边都执行 | 单 tick 耗时 | ≥ 5x |

#### 7.3.2 性能测试方法

**测试流程：**
1. Warmup：跑 100 个 tick（预热 JIT/缓存）
2. 测量：跑 1000 个 tick，记录每个 tick 的耗时
3. 统计：计算 P50 / P95 / P99 / 平均耗时
4. 对比：与基线对比，计算提升倍数

**测试工具：** `tests/benchmark/perf_benchmark.py`

**使用方式：**
```bash
# 单场景性能测试
python -m tests.benchmark.perf_benchmark --pool large_pool --scenario idle

# 全场景性能测试
python -m tests.benchmark.perf_benchmark --all

# 与基线对比
python -m tests.benchmark.perf_benchmark --all --compare baseline_v1.json

# 快速模式（少跑几次，用于开发期快速验证）
python -m tests.benchmark.perf_benchmark --pool simple_pool --quick
```

#### 7.3.3 性能报告

**报告内容：**
- 三种场景的耗时统计表（P50/P95/P99/平均）
- 吞吐量（ticks/秒）
- 与基线的对比（提升倍数）
- 各池子的性能数据
- 火焰图（可选，用于定位瓶颈）

## 8. 错误处理与生产级设计（v1.2 新增）

### 8.1 设计原则

**一条边出错不影响整个池子，一个池子出错不影响整个系统。**

- **错误隔离**：单条边、单只股票的错误不扩散
- **快速失败**：配置错误在启动时就发现，不带着问题跑
- **优雅降级**：核心功能不可用时，有兜底方案
- **可观测**：出了问题能快速定位原因
- **可恢复**：异常退出后能从 checkpoint 恢复

### 8.2 错误分类与处理策略

| 错误类型 | 典型场景 | 严重程度 | 处理策略 | 告警级别 |
|---------|---------|---------|---------|---------|
| **数据错误** | 某只股票没有行情数据、数据格式错误 | 低 | 跳过该股票，记录警告 | Warning |
| **公式错误** | 公式计算异常、除零、引用不存在的指标 | 中 | 跳过该股票，记录错误，该边继续执行其他股票 | Error |
| **配置错误** | pool_config 非法、边的端点不存在、参数缺失 | 高 | 启动时校验失败，直接报错退出（快速失败） | Critical |
| **系统错误** | 内存不足、IO 错误、公式引擎崩溃 | 高 | 熔断：该池子暂停，告警通知，保留现场 | Critical |
| **边执行异常** | 某条边执行时抛出未预期的异常 | 高 | 跳过该边，记录错误堆栈，其他边继续执行 | Error |
| **节点状态异常** | 节点股票数据结构损坏 | 极高 | 熔断：该节点重置为初始状态，告警 | Critical |

### 8.3 错误隔离机制

#### 8.3.1 股票级隔离

**原理：** 单只股票的错误不影响同一条边的其他股票。

**实现：**
```python
def eval_edge(edge_id, codes, ...):
    passed = []
    for code in codes:
        try:
            # 单只股票的计算
            result = eval_single_stock(code, ...)
            if result:
                passed.append(code)
        except Exception as e:
            # 记录错误，但不中断整体流程
            log.error(f"Edge {edge_id} failed for {code}: {e}")
            error_counter.incr(edge_id, code)
            continue
    return passed
```

#### 8.3.2 边级隔离

**原理：** 单条边的错误不影响同 tick 内的其他边。

**实现：**
```python
for eid in edge_order:
    try:
        execute_edge(eid, ...)
    except Exception as e:
        # 记录错误，跳过这条边，继续下一条
        log.error(f"Edge {eid} execution failed: {e}")
        error_tracker.record_edge_error(eid, e)
        continue
```

#### 8.3.3 池子级隔离

**原理：** 单个池子的错误不影响其他池子。

**实现：**
- 每个池子有独立的引擎实例
- 池子之间不共享状态
- 一个池子崩了，其他池子正常运行

### 8.4 降级机制

#### 8.4.1 公式引擎降级

**正常模式：** 调用 FormulaRouter 计算复杂公式
**降级模式：** 公式引擎不可用时，使用简化计算

| 降级级别 | 触发条件 | 行为 |
|---------|---------|------|
| L0 正常 | 公式引擎正常 | 正常调用公式引擎 |
| L1 重试 | 单次调用失败 | 重试 3 次，间隔 10ms |
| L2 跳过 | 重试仍失败 | 该公式返回 False（不通过），记录错误 |
| L3 熔断 | 1 分钟内失败率 > 50% | 该公式所在的边暂停执行，告警 |
| L4 恢复 | 手动恢复或定时检测 | 逐步恢复执行 |

#### 8.4.2 数据源降级

| 降级级别 | 触发条件 | 行为 |
|---------|---------|------|
| L0 正常 | 实时行情正常推送 | 正常更新水位线 |
| L1 延迟 | 数据推送延迟 < 5s | 继续使用旧数据，不触发计算 |
| L2 暂停 | 数据推送延迟 > 30s | 暂停计算，告警，数据恢复后补算 |
| L3 本地缓存 | 数据源完全断开 | 使用本地缓存的最后一帧数据 |

### 8.5 状态持久化与恢复

> 第一阶段设计接口但不实现，状态仍为内存态。架构上预留位置，后续阶段实现。

#### 8.5.1 需要持久化的状态

| 状态 | 持久化频率 | 恢复必要性 |
|------|-----------|-----------|
| `node_stocks`（节点股票列表） | 每 tick 增量 | 高（重启后不能丢股票） |
| `timing_state`（时间触发状态） | 每 tick 增量 | 中（影响时间触发计数） |
| `node_data_ts` / `node_stock_ts` | 每 tick | 低（重启后重新计算即可） |
| `event_queue` | 每 tick | 低（历史事件有历史记录） |
| `execution_tracker` | 定期（可选） | 低（调试用，丢了也没关系） |

#### 8.5.2 持久化接口设计

```python
class StateStore:
    """状态持久化接口（第一阶段只定义接口，不实现）"""
    
    def save_checkpoint(self, pool_id: str, state: dict) -> None:
        """保存 checkpoint"""
        pass
    
    def load_checkpoint(self, pool_id: str) -> Optional[dict]:
        """加载最近的 checkpoint"""
        pass
    
    def list_checkpoints(self, pool_id: str) -> List[str]:
        """列出所有 checkpoint"""
        pass
```

#### 8.5.3 恢复流程

```
引擎启动
  ↓
检查是否有持久化状态
  ├─ 有 → 加载状态，继续运行
  └─ 无 → 从头初始化
  ↓
正常运行
```

#### 8.5.4 Checkpoint 策略

| 策略 | 触发时机 | 优点 | 缺点 |
|------|---------|------|------|
| 每 tick 保存 | 每个 tick 结束 | 数据最完整，恢复点最近 | IO 开销大 |
| 定期保存 | 每 10s / 每 100 tick | 开销可控 | 最多丢 10s 数据 |
| 事件触发 | 有重要事件时 | 关键时刻不丢 | 平时可能丢 |

**推荐：** 定期保存（每 10s）+ 重要事件触发（如 target 节点变化）

### 8.6 内存管理

#### 8.6.1 内存占用预估

**假设：** 5000 只股票，10 个节点，每只股票 entry_info 约 100 字节

| 数据结构 | 预估大小 | 说明 |
|---------|---------|------|
| `latest_tick` | ~5000 × 200B = 1MB | 每只股票的行情数据 |
| `node_stocks` | ~10 × 5000 × 100B = 5MB | 所有节点的股票列表 |
| 其他运行时表 | ~1MB | timing_state、脏标记等 |
| **合计** | **~7MB** | 运行时状态很小 |

**结论：** 5000 只股票 × 10 节点的池子，运行时内存仅约 7MB，完全在可控范围内。

#### 8.6.2 大池子内存控制

| 场景 | 内存占用 | 控制策略 |
|------|---------|---------|
| 1 万只股票 × 20 节点 | ~28MB | 没问题，不需要特殊处理 |
| 5 万只股票 × 50 节点 | ~350MB | 需要关注，考虑分页或懒加载 |
| 10 万只股票 × 100 节点 | ~1.4GB | 需要优化，考虑只存股票代码集合 |

**优化方向：**
- `node_stocks` 只存 `Set[code]`，`entry_info` 存在单独的 LRU 缓存
- 冷节点的股票列表序列化到磁盘，用的时候再加载
- 股票代码用整数编码（2 字节存 6 位代码）

#### 8.6.3 缓存淘汰策略

| 缓存 | 淘汰策略 | 最大容量 |
|------|---------|---------|
| 公式计算结果缓存 | LRU | 10000 条 |
| execution_tracker 环形缓冲 | 环形覆盖 | 最近 1000 个 tick |
| 事件历史 | 定期清理 | 最近 1 小时 |
| 错误日志 | 滚动文件 | 最近 7 天 |

#### 8.6.4 内存泄漏防护

- 所有缓存都有最大容量限制
- 环形缓冲不会无限增长
- 定期执行 GC（可选）
- 有内存使用监控，超过阈值告警

### 8.7 并发安全设计

> 第一阶段单线程实现，性能优化阶段再考虑多线程。这里先明确线程模型。

#### 8.7.1 线程模型（第一阶段：单线程）

```
┌─────────────────┐
│  数据推送线程    │  →  把数据放进队列
└─────────────────┘
           ↓
    ┌─────────────┐
    │  数据队列    │  （线程安全的队列）
    └─────────────┘
           ↓
┌─────────────────┐
│  引擎执行线程    │  →  单线程跑引擎核心循环
└─────────────────┘
```

**说明：**
- 数据推送和引擎执行是两个线程
- 通过线程安全队列传递数据
- 引擎核心逻辑是单线程的，不需要考虑并发安全
- 简单可靠，第一阶段就用这个模型

#### 8.7.2 多线程演进方向（未来）

如果未来性能不够，可以演进到多线程：

| 演进阶段 | 模型 | 复杂度 | 性能提升 |
|---------|------|--------|---------|
| L1 | 单线程（当前） | 低 | 1x（基线） |
| L2 | 数据层读写锁 | 中 | ~1.2x |
| L3 | 边级并行（独立的边并行执行） | 高 | ~2-4x |
| L4 | 股票级并行（单条边内多线程计算） | 极高 | ~4-8x |

**第一阶段只做到 L1（单线程），架构上预留演进空间。**

### 8.8 日志与监控

#### 8.8.1 日志分级

| 级别 | 使用场景 | 示例 |
|------|---------|------|
| DEBUG | 调试信息，开发期用 | 每条边的执行详情、脏标记变化 |
| INFO | 正常运行信息 | 引擎启动/停止、tick 计数 |
| WARNING | 异常但不影响运行 | 单只股票数据缺失、重试成功 |

| CRITICAL | 严重错误，系统不可用 | 配置错误、内存不足、熔断 |

#### 8.8.2 关键指标监控

| 指标 | 类型 | 告警阈值 | 说明 |
|------|------|---------|------|

### 8.9 灰度发布与回滚

> 架构上设计好，第一阶段不一定全实现。

#### 8.9.1 双引擎并行模式

```
实时数据 → 旧引擎（主） → 事件输出（真实生效）
        ↘ 新引擎（备） → 事件输出（只对拍，不生效）
                 ↓
            对拍对比 → 差异报告
```

**步骤：**
1. 新旧引擎并行运行，新引擎结果不落地
2. 跑一段时间（1-2 周），对拍验证
3. 确认没问题后，切流量到新引擎
4. 旧引擎保留一段时间做 fallback

#### 8.9.2 回滚方案

| 回滚触发条件 | 回滚操作 | RTO |
|-------------|---------|-----|
| 对拍发现严重差异 | 切回旧引擎 | < 1 分钟 |
| 新引擎性能不达标 | 切回旧引擎 | < 1 分钟 |
| 新引擎崩溃 | 自动切回旧引擎 | < 10 秒 |

## 9. 版本变更摘要（v1.1 → v1.2）

### 9.1 变更原因
