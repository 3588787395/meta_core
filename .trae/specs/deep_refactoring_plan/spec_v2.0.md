# 股票池架构设计 v2.0

> 版本主题：回归本质版——做减法，直指核心
> 设计原则：最少概念、最少表、最直接逻辑
> 目标：用最简单的话讲清楚股票池到底是什么、运行时到底发生了什么

---

## 一、股票池的本质

**股票池 = 节点 + 边 + 过滤条件，数据顺着边从源节点流到目标节点。**

- **节点**：装股票的篮子（备选池、状态池、条件节点，都是篮子）
- **边**：连接两个篮子的管道
- **过滤条件**：管道上的筛子，决定哪些股票能流过去

就这么简单。

## 二、运行时核心循环

### 2.1 最简洁伪代码（12 行）

```python
while running:
    sleep(tick_interval)                      # 等一个 tick
    if not is_trading_time(): continue        # 非交易时间跳过
    
    new_data = poll_latest_data()             # 拉最新行情
    data_changed = new_data.time != last_time # 数据有没有变
    
    for edge in exec_order:                   # 按执行顺序遍历边
        if should_trigger(edge) and (source_node_changed or data_changed):
            filtered = filter(edge.condition, source_node.stocks)  # 过滤
            target_node.stocks = filtered                            # 更新目标
            emit_events_if_changed(target_node)                     # 发预警
    
    last_time = new_data.time
```

### 2.2 人话解释

1. **每隔 1 秒醒一次**，看看是不是交易时间
2. **拉一下最新行情**，对比上一次的时间戳——没变就啥事没有
3. **按顺序检查每条边**：
   - 触发时间到了吗？（定时条件，比如开盘后 30 分钟）
   - 源节点股票变了吗？（比如备选池加了新股）
   - 行情数据变了吗？（最新 tick 时间推进了）
4. **三个条件满足两个**（时间到了 + 源变了或数据变了）→ 执行过滤
5. 过滤完 → 目标节点股票变了 → 触发预警/事件

### 2.3 关键洞察（全部来自代码验证）

| 洞察 | 代码对应位置 | 说明 |
|------|-------------|------|
| 最新 tick 时间不变 → 不用重算 | `_refresh_latest_tick` + `_is_data_dirty` | `engine.py:3597` 刷新 latest_tick，hash 没变就不置 data_dirty |
| 拓扑运行前就定了，运行时不变 | `_compile_pool` + `CompiledSchedule` | `engine.py:1354` 编译一次缓存，运行期只读 |
| 执行顺序可以不同于拓扑 | `compiled.topo_order` vs 可配置顺序 | 当前按深度排序，理论上可由用户调整 |
| 触发 = 时间条件 AND (源变了 OR 数据变了) | `_run_tick_event_driven` | `engine.py:3627` `triggered = fired and (is_dirty(sid) or is_data_dirty())` |
| 过滤完 → 更新目标 + 预警 | `_process_edge_pipeline` → `_run_post_propagate_hooks` | `engine.py:2725-2733` |

## 三、到底需要几张表？

### 3.1 配置表（3 张就够了）

| # | 表名 | 一句话说明 | 代码对应 |
|---|------|-----------|---------|
| 1 | **pool_config** | 一个池子的完整定义：有哪些节点、哪些边、每条边的过滤条件是什么 | `pool_config = {nodes, edges}` |
| 2 | **formula_lib** | 公式库：所有可用的选股公式/指标定义 | `builtin_formulas.json` + `custom_formulas.json` |
| 3 | **system_config** | 系统参数：tick 间隔、交易时间、缓存策略等 | `timing.json` + `data_config.json` + `defaults.json` |

**就 3 张。** 其他所有配置表（现在有 90+ 张）都是这 3 张的过度拆分。

### 3.2 运行时表（3 张就够了）

| # | 表名 | 一句话说明 | 代码对应 |
|---|------|-----------|---------|
| 1 | **node_stocks** | 每个节点当前有哪些股票 | `self._rt['node_stocks']` `engine.py:508` |
| 2 | **latest_tick** | 每只股票的最新行情数据（唯一真相源） | `self._latest_tick` `engine.py:462` |
| 3 | **event_queue** | 预警/事件队列（入池、出池、预警等） | `self._alert_queue` + `self._event_queue` |

**就 3 张。** 其他运行时表都是中间状态或缓存，不是核心。

### 3.3 为什么现在有 90+ 张配置表？

因为走了"表驱动"的极端——把一切都拆成表：
- 节点类型拆一张表、边类型拆一张表、算子拆一张表...
- 每种 UI 组件拆一张表、每个枚举拆一张表...
- 结果是：简单的逻辑变成了"查表 → 查表 → 再查表"，反而更难理解

**表驱动不是目的，简单才是。**

## 四、前端和后端怎么对应？

### 4.1 对应关系表

| 前端概念 | 后端概念 | 说明 |
|---------|---------|------|
| **综合设置表格** | pool_config（节点 + 边） | 表格的每一行就是一个节点或一条边，左列缩进就是拓扑结构 |
| **拓扑画布** | pool_config（节点 + 边） | 同一份数据的可视化展示，圆圈=节点，连线=边 |
| **执行顺序** | exec_order（边的处理顺序） | 可以和拓扑顺序不同，用户可以拖拽调整 |

### 4.2 一句话总结

**综合设置 = 拓扑 = pool_config，它们是同一件事的三种表现形式。**

- 综合设置：表格视图（方便编辑参数）
- 拓扑画布：图形视图（方便看结构）
- pool_config：数据结构（程序内部用）

### 4.3 执行顺序 vs 拓扑顺序

- **拓扑顺序**：由连接关系决定（A→B→C，A 一定在 B 前面）
- **执行顺序**：用户可以调整（同层级的节点可以改先后）
- **约束**：执行顺序不能违背拓扑依赖（A 必须在 B 前面执行）

代码验证：`compiled.topo_order` 目前是按深度排序（`engine.py:1379`），理论上可以换成用户指定的顺序。

## 五、现在代码的问题在哪？

### 5.1 核心问题：又臭又长的根因

**四个"各搞一套"，导致代码重复、逻辑分散、难以理解：**

| 问题 | 表现 | 严重程度 |
|------|------|---------|
| **数据更新各搞一套** | K线更新、tick更新、备选池刷新——各有各的路径，各有各的缓存 | ⭐⭐⭐⭐⭐ |
| **公式计算各搞一套** | 条件过滤用一套、tracker 用一套、预警用一套——重复计算 | ⭐⭐⭐⭐ |
| **界面刷新各搞一套** | 表格刷新、画布刷新、预警面板刷新——各推各的事件 | ⭐⭐⭐⭐ |
| **配置加载各搞一套** | 引擎加载一套、表驱动引擎加载一套、前端又加载一套 | ⭐⭐⭐ |

### 5.2 其他问题

1. **概念太多**：L1/L2、四层架构、三态逻辑、27 张表、表驱动... 大部分是人为制造的复杂度
2. **engine.py 一个文件 5000+ 行**：什么都往里塞，核心逻辑被淹没
3. **过度表驱动**：简单的 if/else 拆成"配置表 + 查表 + 分派"，反而更绕
4. **运行时表名满天飞**：`_RUNTIME_TABLE_NAMES` 有 30+ 个，大部分是中间状态
5. **前后端数据模型不一致**：前端是 DZH/TDX 的 XML 结构，后端是另一套结构，中间转来转去

### 5.3 最核心的那个问题

> **数据更新、K线组合、公式计算、界面刷新——现在是各搞一套，代码又臭又长。**

（来自用户的洞察，完全正确）

## 六、简化的方向和步骤

### 6.1 简化原则

1. **能合并的合并**：90 张配置表 → 3 张核心表
2. **能内联的内联**：简单逻辑不要拆成"表驱动"
3. **能删的删掉**：没用的概念、没用的中间表、没用的抽象层
4. **一个真相源**：数据只有一个入口，计算只有一个引擎，事件只有一个总线

### 6.2 分三步走

#### 第一步：合并数据层（解决"数据更新各搞一套"）

**目标：一个 `latest_tick` 是唯一真相源，所有计算从这里取数**

- [ ] 把 K 线更新、tick 更新、备选池刷新统一成一条数据通路
- [ ] 取消各种重复缓存（`_data_cache`、`_filter_cache`、`_last_snapshot`...）
- [ ] 数据更新只做一件事：写 `latest_tick`，标记脏

#### 第二步：合并计算层（解决"公式计算各搞一套"）

**目标：一个公式引擎，所有过滤/指标/tracker 都走这里**

- [ ] 条件过滤、tracker 计算、预警判断——统一调用同一个公式引擎
- [ ] 相同股票相同周期的 K 线只算一次，结果复用
- [ ] 过滤逻辑回归本质：输入=股票列表+条件，输出=过滤后的列表

#### 第三步：合并配置层（解决"配置表 90 张"）

**目标：3 张核心配置表 + 一个池子定义文件**

- [ ] 把分散的配置合并回 `pool_config`
- [ ] 公式库独立成 `formula_lib`
- [ ] 系统参数合并成 `system_config`
- [ ] 删掉其他 80+ 张表（或合并进这 3 张）

### 6.3 最终会变成什么样？

```
核心文件（5 个以内）：
├── engine.py          # 主循环 + 边执行（500 行以内）
├── formula_engine.py  # 公式计算（独立模块）
├── data_provider.py   # 数据接入（独立模块）
├── pool_config.py     # 配置加载 + 校验
└── event_bus.py       # 事件总线（预警/刷新通知）

核心表（6 张）：
配置表：pool_config / formula_lib / system_config
运行表：node_stocks / latest_tick / event_queue
```

**就这么多。** 其他都是锦上添花，不是核心。

## 七、一句话总结

> **股票池就是几根管子连几个篮子，数据从上游流到下游，管子上有筛子过滤，筛子的触发条件是"时间到了而且有新数据"。**

理解了这句话，就理解了股票池的全部本质。
