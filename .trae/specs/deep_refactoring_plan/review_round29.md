## 一、总体评价

这是一篇**有一定深度、但不够严谨的理解笔记**。作者对变换单元的执行模型有基本正确的认知，对 dirty 级联传播机制的把握基本到位，按单元执行 vs 按边执行的对比框架也搭起来了。

**但问题在于**：许多结论停留在"表面正确"的层面，对 edge case 的挖掘不够深，对代码细节的理解有几处明显偏差，重构可能性分析过于乐观，工作量估计严重不足。

**价值判断**：
- ✅ 作为入门级理解材料，可以帮助新人建立变换单元的基本概念
- ⚠️ 作为重构指导文档，**还不够格**——遗漏了太多关键细节，风险评估偏乐观
- ❌ 直接按此文档动手重构，大概率会踩坑

## 二、正确的点（至少5条）

### ✅ 1. 6步执行语义的核心框架基本正确

文档将变换单元执行拆分为6步（入边触发→入边过滤→条件节点标脏→出边触发→出边搬运→目标池标脏），这个**宏观框架是对的**。

代码验证：
- 入边触发判定：`engine.py:3621-3629` ✅
- 入边条件过滤：`_filter_conditional` at `engine.py:2528-2627` ✅
- 标脏目标节点：`engine.py:3641` ✅
- 出边触发：同主循环，因拓扑序条件节点后处理 ✅
- 出边搬运：`_filter_unconditional` at `engine.py:2476-2526` ✅
- 目标池标脏：`engine.py:3641` ✅

### ✅ 2. dirty 级联传播机制的理解基本准确

文档抓住了核心：**边执行 → 标脏目标节点 → 下游边检查源节点是否脏 → 触发执行 → 继续标脏**。

三个脏源（node_dirty / data_dirty / edge_fired）和触发公式 `triggered = fired AND (node_dirty OR data_dirty)` 的描述完全正确，代码引用 `engine.py:3627` 准确。

### ✅ 3. 入边和出边通过 dirty 标记"隐式串联"的洞察有价值

"入边和出边之间没有显式的调用关系，完全靠 dirty 标记串起来"——这个观察是准确的，也是理解当前架构的关键钥匙。

代码证据：主循环 `engine.py:3606-3641` 完全按边遍历，没有任何"变换单元"的概念，两条边的串联完全依赖拓扑序 + dirty 标记。

### ✅ 4. 变换单元类型体系（3种）描述正确

tdx_condition / transfer_condition / dzh_condition_pool 三种类型的划分，与 `edge_strategies.json` 中 `transformation_unit_strategies` 的定义完全一致。

"入边都是 conditional、出边都是 unconditional、只有中间条件计算不同"——这个总结也对。

### ✅ 5. 编译期已有 units 分组但运行时仍按边执行的发现准确

文档指出 `_group_transformation_units`（`engine.py:2217-2247`）在编译期做了分组，但 `_run_tick_event_driven` 运行时仍按边遍历——这个发现是对的，也是重构的重要前提。

补充验证：`_build_processing_plan`（`engine.py:1289-1331`）确实把 units 又展开回了边列表。

### ✅ 6. "渐进式重构、先验证等价性"的策略方向正确

文档提出的四步重构路线（增加新模式→建立等价性测试→逐步切换→清理旧代码）是稳妥的工程化思路，没有激进地主张一步到位。

## 三、有偏差的点（至少3条）

### ⚠️ 1. 6步执行语义不完整——漏掉了 post_propagate_hooks 和边级副作用

**问题**：文档的6步模型只覆盖了"过滤+搬运"的核心路径，但漏掉了一个重要环节：**`_run_post_propagate_hooks`**。

代码事实（`engine.py:2713-2735`）：
```python
def _process_edge_pipeline(self, ctx):
    # 步骤 1：表驱动筛选 + 流转 + 变换
    if not self._apply_edge_filter(ctx):
        return True
    # 步骤 2：后处理 hooks
    self._run_post_propagate_hooks(ctx, tgt_b_codes, fa, mv, io)
```

后处理 hooks 包括什么？从 `_run_post_propagate_hooks`（`engine.py:2896-2913`）的调用链看，涉及 count 统计、tracker 更新、事件发射、callback、TTL 等**副作用逻辑**。

**影响**：
- 入边和出边**各自**都有 post_propagate_hooks
- 如果重构为按单元执行，需要明确：这些 hooks 是分别执行还是合并执行？
- 特别是 tracker 更新和事件发射，如果执行时机变了，下游监听者的行为会变

**偏差程度**：中等——不影响核心数据流，但影响副作用语义。

### ⚠️ 2. 等价性分析过于乐观——多入边/多出边不是"待确认"，而是语义差异很大

**问题**：文档在 edge case 分析中说"多入边/多出边 ⚠️ 待确认"，语气轻飘飘的。但实际上，**多入边的语义是理解当前架构的关键难点之一，也是重构的最大绊脚石**。

代码事实：
- `_group_transformation_units`（`engine.py:2240-2246`）只在 `len(in_list) == 1 and len(out_list) == 1` 时才配对为单元
- 多入边的条件节点，每条入边**独立写入**条件节点，是**合并语义**（merge）
- 多出边的条件节点，每条出边**独立读出**条件节点，是**扇出语义**（fan-out）

**按边执行 vs 按单元执行在多入边场景下的差异**：

| 场景 | 按边执行（当前） | 按单元执行（假设） |
|------|-----------------|-------------------|
| 条件节点有2条入边，A入边触发了B没触发 | A入边执行→写入条件节点→标脏→出边执行（基于A的结果） | 需要定义"单元触发"语义：是任一入边触发就执行？还是所有入边都触发才执行？ |
| 同一tick内两条入边先后触发 | 第一条执行→标脏→出边可能先被触发（取决于拓扑序位置） | 可以控制为"收集所有入边结果后统一执行出边" |

这不是"待确认"的小问题，而是**设计空间中一个核心抉择**。文档轻描淡写地带过，是不负责任的。

**偏差程度**：严重——直接影响重构方案的可行性评估。

### ⚠️ 3. 性能对比分析粗浅——触发判定开销不是瓶颈，缓存才是

**问题**：文档说"节省约 50% 的触发判定开销"、"触发判定本身开销不大"。这个结论后半句对（开销不大），但前半句误导人。

**真实的性能瓶颈在哪？**

从代码看，`_filter_conditional`（`engine.py:2528-2627`）的时间花在：
1. **策略执行**（`engine.py:2613-2617` 调用 actual handler）——这才是大头，尤其是公式求值
2. **缓存查找/写入**（`engine.py:2582-2597` / `2620-2623`）——有开销但可控
3. 流转属性解析、变更检测——相对较小

而 `_should_trigger_edge`（`engine.py:1757-1785`）的 gate 判定，主要是查表和时间比较，**确实很快**。

**所以"节省一次 gate 判定"的性能收益可以忽略不计。**

真正的性能优化空间在于：
- 变换单元级别的缓存（输入指纹→输出结果），而不是边级缓存
- 公式求值的批量优化
- 空源早退的提前判定

文档把性能收益的赌注押错了地方。

**偏差程度**：中等——不影响正确性，但会误导对重构收益的判断。

### ⚠️ 4. 出边"没有业务触发条件"的说法不准确

**问题**：文档说"出边没有独立的业务触发条件，只有数据触发条件"。这个说法**在绝大多数情况下是对的，但有例外**。

代码证据：`_filter_unconditional`（`engine.py:2490-2495`）里有源变更检测——如果源节点没变，即使被标脏了（比如误标），也会跳过。这是一层保护。

但更重要的是，从 `_build_processing_plan`（`engine.py:1321-1329`）可以看到：
```python
# 独立边来自 transfer_condition 等条件节点时，若边策略声明了 apply_filter/discard_rejected，
# 则强制使用 conditional filter_type，确保公式过滤逻辑被执行（而非直通传递）
if ft == 'unconditional':
    strat = self._resolve_chain([...])
    if strat and strat.get("action") in ("apply_filter", "discard_rejected"):
        ft = 'conditional'
```

这意味着**某些"出边"实际上可能走 conditional 逻辑**——它们源节点类型是条件节点（按语义应该是 unconditional），但配置了过滤动作，所以被强制升级为 conditional。

这是一个**现实存在的 edge case**，文档完全没有提及。

**偏差程度**：轻微——主要影响 standalone_edges 的归类，但反映出文档对代码细节的掌握还不够。

## 四、遗漏的点（至少3条）

### ❌ 1. 遗漏了 `_update_node_snapshot` 的双重标脏机制

**问题**：文档说标脏是通过 `_mark_dirty(tid)` 实现的，但没有提到主循环中还有另一处标脏：`_update_node_snapshot`。

代码事实（`engine.py:3637-3641`）：
```python
tid = ec['tid']
if self._update_node_snapshot(tid, node_stocks.get(tid, [])):
    pass  # _update_node_snapshot 内部自动标脏
# Phase 2: 显式标目标节点为脏（级联传播）
self._mark_dirty(tid)
```

注意：`_update_node_snapshot` 内部已经会标脏（`engine.py:2188-2207`），然后下面又调用了一次 `_mark_dirty`。**这是重复标脏**，但因为 `_dirty_nodes` 是 set，重复加不影响结果。

**为什么这个细节重要？**

因为它揭示了一个设计意图的演变：
- 早期：`_update_node_snapshot` 负责检测变化并标脏（被动式）
- 现在：不管有没有变化，执行完边就强制标脏（主动式）——第3641行的 `_mark_dirty`

**这意味着"边执行了 → 目标节点就一定脏"是当前代码的硬保证**，而不是"只有目标节点真的变了才脏"。

这个细节对重构有影响：按单元执行时，出边执行完是否也要无条件标脏？还是可以优化为检测到变化才标脏？

### ❌ 2. 遗漏了 formula_eval 边类型——第三种边的存在

**问题**：文档通篇只讨论 conditional 和 unconditional 两种边类型，但实际上有**三种**：`formula_eval`。

代码证据：
- `_filter_strategies` 字典（`engine.py:2454-2457`）有三个 entry：`unconditional` / `conditional` / `formula_eval`
- `_filter_formula_eval`（`engine.py:2629-2710`）是独立实现的
- `pipeline_phases` 配置中，replay_guard / tdx_guard / duration_guard 都同时作用于 `conditional` 和 `formula_eval`

**formula_eval 边是什么？** 它类似于 conditional（有时间 gate、有过滤逻辑），但过滤方式是公式批量求值。它的源节点类型是什么？目标节点类型是什么？它是否构成变换单元？

文档完全忽略了第三种边，这是一个**重大遗漏**——因为重构方案必须明确 formula_eval 怎么归类：
- 是作为第四种变换单元类型？
- 还是作为 standalone_edges 的子类？
- 还是和 conditional 合并处理？

### ❌ 3. 遗漏了 pre_tick / post_tick 流水线与主循环的交互

**问题**：文档只分析了 `_run_tick_event_driven` 内部的执行流程，但没有讨论它的上下文——`_tick` 方法中的 pre_tick 和 post_tick。

代码事实（`engine.py:3650-3661`）：
```python
async def _tick(self, pool_config, node_stocks, current_bar_data=None, mode_state=None):
    if not mode_state or mode_state.get('inject', True):
        await self._pre_tick(nodes, node_stocks, current_bar_data)
    prev = self._snapshot_node_stocks(node_stocks)
    for nid in nodes:
        self._update_node_snapshot(nid, node_stocks.get(nid, []))
    node_stocks, tevs = self._run_tick_event_driven(pool_config, node_stocks, current_bar_data)
    self._update_trackers(...)
    self._emit_transfer_events(...)
    self._post_tick(node_stocks, current_bar_data)
    return node_stocks
```

**为什么这很重要？**

因为：
1. **pre_tick** 可能修改节点状态（注入数据等），这是 dirty 的初始来源之一
2. **post_tick** 的 tracker 更新、TTL 清理等，会影响下一个 tick 的节点状态
3. `_update_trackers` 和 `_emit_transfer_events` 是在主循环之后、post_tick 之前执行的——这些副作用的时序如果在重构中改变了，可能引入难以追踪的 bug

重构不能只看主循环，必须考虑整个 tick 的完整生命周期。

### ❌ 4. 遗漏了回放模式（replay）的特殊语义

**问题**：文档的分析都是基于"通用模式"的，但回放模式下的触发逻辑有特殊处理。

代码证据：
- `_should_trigger_edge`（`engine.py:1757-1785`）内部会根据模式路由到不同的 gate 评估逻辑
- `pipeline_phases` 中的 `replay_guard` 只在 replay 模式下对 conditional 和 formula_eval 生效
- 回放模式下时间是虚拟推进的，和实时模式的 wall clock 不一样

**影响**：
- 回放模式下的级联传播时序可能和实时模式有微妙差异
- 如果重构按单元执行，回放模式的 begin/end/interval 语义需要重新验证
- 这是等价性测试必须覆盖的场景，但文档没有提到

### ❌ 5. 遗漏了缓存一致性问题——边级缓存 vs 单元级缓存

**问题**：文档提到了"变换单元级别的缓存"作为优化方向，但没有分析当前边级缓存的行为及其与重构的冲突。

代码事实：
- 当前缓存在 `_filter_conditional` 中（`engine.py:2582-2597` / `2620-2623`），是**边级**的
- 缓存 key 由 `_unit_cache_key` 生成（注意函数名虽然叫 unit_cache，但实际是边级的）
- unconditional 边**没有缓存**（`edge_semantics.json` 中 `cache_filter_result: false`）

**重构后的缓存问题**：
1. 如果按单元执行，缓存是放在入边、出边还是单元级别？
2. 当前出边没有缓存，因为无条件搬运很快。但单元级缓存是否可以包含完整的"入边过滤+出边搬运"结果？
3. 多入边场景下，缓存 key 怎么定义？

这不是小问题——缓存策略直接影响性能和正确性，文档完全没有展开。

## 五、重构可能性评估

### 收益评估：被高估了

| 收益项 | 文档说法 | 实际评估 |
|--------|---------|---------|
| 概念更清晰 | ✅ 强调 | **部分成立**。对标准三元组结构确实更清晰，但对非标准拓扑反而增加了认知负担（需要理解"为什么这些是 standalone_edges"） |
| 代码更简洁 | ✅ 强调 | **存疑**。主循环可能更简洁，但需要增加大量"单元识别/分类/回退"的逻辑，整体代码量未必减少 |
| 调试更容易 | ✅ 强调 | **部分成立**。单元级断点/日志确实方便，但当问题出在 standalone_edges 或非标准拓扑时，调试反而更复杂（两套逻辑） |
| 优化空间更大 | ✅ 强调 | **过于乐观**。文档提到的优化（单元级缓存、并行、增量更新）在按边执行模型下也能做，不是非重构不可 |

**净收益判断**：有收益，但没有文档说的那么大。属于"做了更好，但不做也能活"的级别。

### 风险评估：被低估了

| 风险项 | 文档说法 | 实际评估 |
|--------|---------|---------|
| 改动量大 | ⚠️ 提到 | **严重低估**。文档说主循环"从按边遍历改成按单元遍历"，听起来很简单，但实际上涉及：触发逻辑、缓存、副作用、回放模式、多种边类型、非标准拓扑回退……远不止改个循环那么简单 |
| 破坏现有功能 | ⚠️ 提到 | **风险很高**。现有代码经过大量真实场景打磨，有很多隐含的假设和 edge case 处理。重构很容易在不经意间破坏某些微妙的时序或语义 |
| 性能回退 | ⚠️ 提到 | **中等风险**。如果单元级缓存设计得好，性能可能提升；但如果设计不好（比如增加了不必要的对象创建或函数调用），性能可能下降 |
| 调试成本 | ⚠️ 提到 | **严重低估**。两种执行模式并存期间，debug 成本是双倍的——出了 bug 先要确定是模式本身的问题还是实现的问题 |

**额外风险（文档没提的）**：
1. **团队学习成本**：所有开发者都要理解两套模型，以及它们的对应关系
2. **回退路径依赖**：一旦有 bug 回退到按边执行，可能掩盖更深层的问题
3. **配置兼容性**：现有 42 个 DZH 文件、995 个 TDX 文件的拓扑是否都能正确识别为标准单元？如果有大量 standalone_edges，重构的意义就大打折扣

### 工作量估计：严重低估

文档说"约 2-3 周的工作量（1人，含测试）"。

**我的估计（保守估计，1人）**：

| 阶段 | 工作量 | 说明 |
|------|--------|------|
| 详细设计 | 1周 | 多入边/多出边语义、formula_eval 归类、缓存策略、副作用时序……这些都需要想清楚，不能边做边想 |
| 核心实现 | 2-3周 | 主循环重写、单元识别优化、两种模式的切换框架 |
| 等价性测试框架 | 1-2周 | 自动化测试 infrastructure、测试用例生成（需要覆盖各种拓扑+模式+edge case） |
| 调试与修复 | 2-4周 | 等价性测试跑通前的调试周期，取决于 bug 数量 |
| 回归验证 | 1-2周 | 用真实的 DZH/TDX 文件跑一遍，确保行为一致 |
| 文档更新 | 0.5周 | 架构文档、开发指南 |
| **合计** | **7.5-12.5周** | **约 2-3 个月** |

**为什么差这么多？** 因为文档低估了：
1. 等价性测试的工作量——这不是写几个测试用例就行，需要系统性的覆盖
2. 调试周期——重构类项目的 bug 往往是"差一个 tick"、"少一个 edge case"这种，调试很慢
3. 真实场景验证——实验室跑通了不算，真实股票池跑通才算

## 七、下一个深挖方向

**方向：多入边条件节点的语义分析与执行模型选择**

为什么是这个方向？
1. **它是重构的核心决策点**：不搞清楚多入边的语义，就没法设计按单元执行的模型
2. **当前文档几乎空白**：只用"待确认"三个字带过，完全不够
3. **它决定了重构的价值**：如果真实场景中大量存在多入边，那么"标准变换单元"的覆盖率就低，重构的收益就小

**建议的分析框架**：
1. **数据统计**：42个DZH文件、995个TDX文件中，多入边条件节点占比多少？多出边呢？
2. **语义分类**：多入边的合并语义是什么？是 OR（任一入边满足就进入）？还是 AND（所有入边都满足才进入）？还是按顺序覆盖？
3. **执行时序**：同一tick内多条入边先后触发时，出边执行几次？现在的行为是期望的吗？
4. **设计选型**：如果按单元执行，多入边怎么建模？是"扇入单元"还是"保持边级执行"？
5. **回退策略**：如果多入边不能归约为标准单元，standalone_edges 的比例有多高？重构还有意义吗？

**产出物**：一份多入边/多出边语义分析报告，含数据统计、语义分类、设计选型建议。
