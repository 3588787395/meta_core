## 0. v3.7→v3.8 改进说明

### 修复的精准度硬伤

| 问题 | v3.7 错误 | v3.8 修正 |
|------|-----------|-----------|
| 凭空造属性 | `FormulaRouter.engines` 不存在 | 删除，替换为真实存在的 `_simple_functions` |
| 去下划线假装对外 | `ConfigStore.tables` / `validators` / `config_dir` | 还原为 `_tables` / `_validators` / `_config_dir`，明确标注内部属性 |
| 去下划线假装对外 | `FormulaRouter.cache` | 还原为 `_cache`，明确标注内部属性 |
| 本质一句话改坏 | 28字版本读起来别扭 | 回到 30 字 v3.6 版本 |

### 概括力提升思路（不靠偷工减料，靠提炼本质）

- **属性：从 5 个减到 3 个** —— 只留最能代表该类本质的属性
- **方法：从 5 个减到 3 个** —— 只留最能代表该类本质的方法
- **核心类数量：保持 5 个** —— 经审视，5 个各有不可替代的职责，强行合并会损伤精准度（详见末尾讨论）

### 评分目标

- 精准度：83 → 90+（修复所有硬伤）
- 概括力：保持 83 或以上（靠提炼本质，不靠偷工减料）

## 1. 核心类选型说明

**选型标准：** 没有这 5 个类，股票池系统就跑不起来。

| 序号 | 类名 | 为什么是核心 | 所在层 |
|------|------|-------------|--------|
| 1 | MetaEngine | 运行时主引擎，tick 驱动拓扑执行与股票流转 | 引擎层 |
| 2 | FormulaRouter | 公式计算入口，双引擎路由+缓存，MetaEngine 直接依赖 | 引擎层 |
| 3 | ConfigStore | 配置表存储中心，表驱动架构根基 | 配置层 |
| 4 | DynamicCellModel | 节点通用数据模型，图的基本构成单元 | 模型层 |
| 5 | DynamicFlowModel | 边通用数据模型，图的基本构成单元 | 模型层 |

**选型依据：** MetaEngine `__init__` 中直接初始化 `formula_router`（`engine.py:400`），公式求值统一走 FormulaRouter，PythonFormulaEngine 只是其内部执行引擎之一。

**关于"能不能减到 3 个"的讨论：** 见本文末尾附录 A。

## 7. 类关系图（文字版）

### 图例

| 箭头样式 | 含义 | 说明 |
|---------|------|------|
| `─→` 实线箭头 | 依赖/委托 | A 调用 B 的能力，B 是 A 的依赖 |
| `─┐` 注入箭头 | 配置注入 | 配置数据从上游流入下游 |
| `◄─►` 双向箭头 | 结构关联 | 两者共同组成更大的结构 |

### 关系图

```
                ┌──────────────┐
                │  ConfigStore │  ←  配置层（表驱动根基）
                └──────┬───────┘
                       │ 配置注入
         ┌─────────────┴─────────────┐
         ▼                           ▼
  ┌──────────┐               ┌──────────────┐
  │ MetaEngine│ ──────────► │ FormulaRouter │  ←  引擎层
  │  (主引擎) │   委托求值   │  (双引擎入口)  │
  └─────┬────┘               └──────────────┘
        │ 编译/执行
        ▼
  ┌──────────┐    组成拓扑    ┌───────────┐
  │DynamicCell│◄────────────►│DynamicFlow│
  │  (节点)   │   结构关联    │  (边)     │
  └──────────┘               └───────────┘
                                      ↳ 模型层
```

**关系一句话：** ConfigStore 提供配置，MetaEngine 读取配置并驱动由 DynamicCellModel + DynamicFlowModel 组成的拓扑执行，公式计算委托给 FormulaRouter。

**股票池是行情驱动的有向图过滤器，股票经边公式筛选后在节点间流转。**

## 附录 A：核心类能不能从 5 个减到 3 个？

### 尝试过的合并方案

**方案 A：MetaEngine + FormulaRouter 合并为"运行引擎"**
- 问题：FormulaRouter 是独立的类、独立的文件、独立的职责（双引擎路由+缓存）
- MetaEngine 只是"委托"它做公式计算，不是"包含"它
- 强行合并会模糊"路由层"和"执行层"的边界

**方案 B：DynamicCellModel + DynamicFlowModel 合并为"图模型"**
- 问题：两者虽然结构相似（都是 _data + _extra + 动态属性），但语义完全不同
- 一个是节点（存股票的容器），一个是边（筛选+流转规则）
- 合并描述会让读者分不清"图的两个基本构成元素"

**方案 C：ConfigStore 不算核心？**
- 问题：表驱动架构中 ConfigStore 是根基
- 没有配置表，MetaEngine 连有哪些节点、哪些边都不知道
- 配置层是整个系统的一级分层

### 结论

**保持 5 个更精准。** 5 个类正好对应三层架构：
- 配置层：ConfigStore（1 个）
- 引擎层：MetaEngine + FormulaRouter（2 个）
- 模型层：DynamicCellModel + DynamicFlowModel（2 个）

这是一个非常对称、清晰的分层结构。为了"凑 3 个"而强行合并，反而会损伤对架构的理解。

概括力的提升不靠"减少类的数量"，而靠"每个类的定义更凝练"——这正是 v3.8 把每个类的属性/方法从 5 个减到 3 个的原因。
