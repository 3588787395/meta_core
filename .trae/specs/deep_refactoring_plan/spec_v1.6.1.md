## 一、本质认知：实盘 vs 回测（v1.6.1 最重要的纠正）

### 1.1 根本性错误：v1.6 用了回测思维

v1.6 隐含了一个错误假设："日线一天只算一次"、"5分钟线5分钟才变一次"。

**这是回测思维，不是实盘思维。**

回测里的K线：
- 都是"已完成"的K线
- 日线就是一整天的数据，不会变了
- 5分钟线就是5分钟的数据，不会变了
- 所以"日线一天只算一次"是对的

**实盘里的K线：**
- 最新一根K线（不管什么周期）都是"未完成"的
- 随着每个tick的到来，close/high/low/volume 都在实时变化
- 今天的日线，每个tick收盘价都在变，最高价也可能变，成交量也在变
- 所以**所有周期的最新指标值，每个tick都可能变**
- 不存在"日线一天只算一次"这种事

### 1.2 正确的认知：一个全局水位线就够了

**用户的核心洞察是对的：最新tick时间不变 → 所有数据都不变 → 所有计算结果都不变 → 不需重新计算。**

就这么简单。

不需要什么"周期级脏标记"、"周期级版本号"——那都是过度设计。

```
实盘正确逻辑：
  tick来了 → latest_tick_ts 更新了 → 所有数据都可能变了 → 所有指标都可能变了
  或者：
  tick没来 → latest_tick_ts 没变 → 所有数据都没变 → 所有指标都没变 → 啥都不用算
```

对于股票池过滤场景：
- 我们关心的是"当前哪些股票满足条件"
- 用的是指标的最新值
- 最新值包含了最新一根未完成的K线
- 所以只要tick变了，所有指标的最新值都可能变
- 所以一个全局的 `latest_tick_ts` 就够了，不需要按周期分

### 1.3 那指标缓存还有意义吗？

**有，但不在股票池引擎这一层。**

指标缓存的正确位置是**公式引擎内部**：
- 公式引擎可以缓存历史K线的指标值（已完成的K线，指标值不变）
- 公式引擎可以做增量计算（只更新最新一根K线的指标值）
- 这些都是公式引擎自己的优化，股票池引擎不需要关心

**股票池引擎的职责：**
- tick变了吗？变了就调用公式引擎重算
- 没变就什么都不做
- 不关心公式引擎内部怎么缓存、怎么优化

这是正确的职责分离。

### 1.4 一句话本质（v1.6.1 修正版）

**股票池 = 一组节点 × 一组边 × 一个全局数据水位线 × 公式注册表 × 比较算子集 × 一个事件队列。**

- **节点**：装股票的容器（备选池/状态池/条件池/目标池）
- **边**：节点之间的连接，带触发条件（时间 + 过滤条件 + 传播模式）
- **全局数据水位线**：`latest_tick_ts`（或 `data_dirty` 标记）——**数据变没变？一个标记就够了。**没变就啥都不用算。
- **公式注册表**：`formula_registry` —— 所有可用指标的元数据，编译期去重，运行时共享。
- **比较算子集**：`comparison_operators` —— 独立的比较操作符，与指标正交。
- **脏节点队列**：`dirty_nodes` —— 需要重新计算的节点。节点脏了 = 该节点的所有出边都需要检查。

### 1.5 核心洞察：数据不变则结果不变（纯函数性质）

**这是最根本的洞察，v1.6 把它搞复杂了。**

```
指标是纯函数：
  输入数据不变 → 输出结果不变

推论：
  latest_tick_ts 没变 → 所有数据都没变 → 所有指标结果都没变 → 所有filter结果都没变
  → 所有边的执行结果都没变 → 节点状态都没变 → 啥都不用做
```

**所以只需要一个全局标记：数据变了吗？**
- 变了：该算的算
- 没变：啥都不用干

就这么简单。不需要按周期分，不需要版本号对比（那是公式引擎内部的事）。

## 二、核心设计：单一水位线 + filter三层 + 公式注册表

### 2.1 运行时内存表（核心运行时表一共 5 张，v1.6.1 极简版）

| 表名 | 类型 | 读时机 | 写时机 | 说明 |
|------|------|--------|--------|------|
| `latest_tick` | Dict[code → bar_dict] | 公式引擎计算时读 | 行情推送时写 | **唯一真相源**。所有股票的最新tick数据。 |
| `node_stocks` | Dict[nid → List[code]] | propagate 读写、filter 读 | 边执行/TTL过期后写 | 各节点当前股票列表 |
| `dirty_nodes` | Set[nid] | 执行循环读 | 节点股票状态变化时加入 / 数据更新时加入 | **脏节点集合**。节点脏了=所有出边需要检查 |
| `ttl_expiry_queue` | Heap[(expire_ts, nid, code)] | tick 开始时弹出 | 股票入池时插入 | TTL 过期队列。按过期时间排序的最小堆 |
| `data_dirty` / `latest_tick_ts` | bool / float | 边触发检查时读 | tick数据更新时写 | **全局水位线**。数据变了吗？一个标记就够了。 |

| `indicator_cache` | — | **删除（移出股票池引擎）**。指标缓存是公式引擎内部的事，股票池引擎不维护指标缓存，只调用公式引擎。 |

### 2.2 数据层 vs 公式引擎 vs 股票池引擎：职责明确分离

**v1.6.1 明确三层职责：**

```
┌─────────────────────────────────────────────────────────┐
│  股票池引擎层（最上层）                                   │
│  - 只关心：数据变了吗？变了就调公式引擎算                 │
│  - 维护：node_stocks, dirty_nodes, ttl_expiry_queue     │
│  - 维护：全局水位线 data_dirty / latest_tick_ts         │
│  - 不关心：K线怎么合成、指标怎么缓存、怎么增量计算       │
├─────────────────────────────────────────────────────────┤
│  公式引擎层（中间层）                                    │
│  - 输入：股票代码 + 公式名 + 参数 + 周期                 │
│  - 输出：指标值                                          │
│  - 内部优化：K线缓存、指标缓存、增量计算、历史值复用      │
│  - 股票池引擎不需要知道这些优化，只需要调用 get_indicator() │
├─────────────────────────────────────────────────────────┤
│  数据层（最底层）                                        │
│  - 接收原始tick数据                                      │
│  - 维护 latest_tick（唯一真相源）                        │
│  - K线合成（如果需要）                                    │
│  - 通知上层：数据更新了（通过回调或事件）                 │

```

| 执行 filter 三层 | ✅ | ❌（只提供指标值） |
| 传播状态 | ✅ | ❌ |
| 发事件 | ✅ | ❌ |
| 维护 latest_tick | 共享（数据层写，两方都读） | 共享 |
| K线合成 | ❌ | ✅（或数据层） |
| K线缓存 | ❌ | ✅ |
| 指标缓存 | ❌ | ✅ |
| 指标增量计算 | ❌ | ✅ |
| 公式解析/编译 | ❌ | ✅ |

### 2.3 编译期：公式注册表 + 比较算子正交化（保留 v1.6 的正确设计）

**这部分 v1.6 是对的，v1.6.1 完全保留。**

**编译期做的事：**

1. 加载 `formula_registry`（公式注册表，所有可用指标）
2. 加载 `comparison_operators`（比较算子集，所有可用比较算子）
3. 遍历所有边的 filter 配置
4. 提取每个 filter 用到的（公式 + 参数 + 周期）三元组
5. 全局去重：相同三元组合并为一个指标，分配 indicator_id
6. 提取每个 filter 用到的比较算子和参数
7. 边只保存引用：指标ID + 比较算子ID + 参数

**编译期产物（不变，全部保留）：**

| 编译产物 | 类型 | 说明 |
|----------|------|------|
| `formula_registry` | Dict[indicator_id → formula_spec] | 公式注册表。所有去重后的指标，编译期一次性收集 |
| `comparison_operators` | Dict[op_id → operator_spec] | 比较算子集。所有可用的比较算子，独立于指标 |

| `edge_filter_type` | Dict[eid → 'independent' / 'global'] | filter 类型：单股独立型 / 全局依赖型 |

### 2.5 全局水位线机制（替代周期级版本号）

**这是 v1.6.1 最核心的简化。**

#### 数据更新时

```python
# 数据层：tick 数据更新时
def on_tick(code, bar):
    # 1. 写最新 tick
    latest_tick[code] = bar
    
    # 2. 标记全局数据脏（或更新 latest_tick_ts）
    data_dirty = True
    # 或者：
    latest_tick_ts = time.time()
    
    # 3. 股票所在节点标记为脏
    for nid in code_nodes[code]:
        dirty_nodes.add(nid)
```

**就这么简单。没有周期级版本号，没有递增版本号。**

#### 边触发检查时

```python
# 边触发检查：三要素 AND
def should_trigger_edge(eid):
    # 1. 时间条件满足吗？
    if not timing_satisfied(eid):
        return False
    
    # 2. 数据变了吗？（全局水位线，一个标记就够了）
    if not data_dirty:
        # 数据没变，所有计算结果都不会变，跳过
        # （除非节点状态变了，所以还要检查节点脏）
        pass
    
    # 3. 源节点脏了吗？（节点股票变化 OR 数据变化导致的脏）
    if not is_dirty(source_node(eid)):
        return False
    
    return True
```

**注意：`data_dirty` 和 `node_dirty` 是 OR 的关系——任一为真，边都可能需要重新计算。**
- 节点脏：节点里的股票变了（增/减），需要重新filter
- 数据脏：数据变了，指标值可能变了，需要重新filter

#### 指标计算时

```python
# 股票池引擎获取指标值（调用公式引擎）
def get_indicator(indicator_id, code):
    spec = formula_registry[indicator_id]
    # 直接调用公式引擎，不关心它内部怎么缓存
    return formula_engine.calculate(
        code=code,
        formula=spec['name'],
        period=spec['period'],
        args=spec['args'],
    )
```

**股票池引擎不需要做版本号对比，不需要维护指标缓存。** 这些都是公式引擎内部的事。

公式引擎内部可以做的优化（股票池引擎不需要知道）：
- 历史K线的指标值缓存（已完成的K线，值不变）
- 增量计算（只更新最新一根K线）
- 等等...

### 2.6 边触发机制：节点脏驱动 + 三要素 + 边执行步骤（保留正确部分）

**边执行的完整步骤（v1.6.1 修正版）：**

```
边执行步骤（filter三层 + propagate是边的步骤）：
  1. gate：时间条件检查
  2. filter 第一层：指标计算（调用公式引擎，公式引擎自己管缓存）
  3. filter 第二层：比较判断（独立型增量）
  4. filter 第三层：集合运算（AND/OR/NOT/排名）
  5. propagate：传播（copy/move/overwrite）← 边的步骤，不是filter层
  6. 发事件
  7. 目标节点脏标记
```

**三要素（v1.6 正确，v1.6.1 保留，但把"数据版本"简化为"数据变了吗"）：**

```
边执行 = 时间条件满足 
       AND (源节点有变化 OR 数据有变化)
       AND （首次执行 OR 上一次执行后有变化）
```

**v1.6.1 补充：数据变化的判断是全局的，不是周期级的。**

```
数据变了吗？
  → data_dirty == True 或 latest_tick_ts > last_process_ts
  → 变了：所有指标都需要重新计算（但公式引擎内部可以做增量优化）
  → 没变：所有指标结果都不变，不用算
```

## 三、运行前 vs 运行时：严格分离（v1.6.1 简化版）

### 3.1 运行前（设计时 + 加载时）做的事

全部一次性做完，运行时只读。和 v1.6 基本一致，不涉及周期级缓存的部分都保留。

| 阶段 | 做什么 | 产出 |
|------|--------|------|
| **设计时** | 用户拖拽节点、连线、配置参数、设置执行顺序 | pool_config (JSON) |
| **加载时** | 解析 pool_config，**全局收集指标并去重**，拆分 filter 为三层，判断 filter 类型，编译所有规格 | CompiledPool |

**CompiledPool v1.6.1 和 v1.6 基本相同**，因为编译期不涉及运行时的周期级版本号问题。

### 3.2 运行时做的事（事件驱动 + 三层filter + 全局水位线 + 节点脏驱动）

就一个循环（**节点脏驱动 + 全局数据水位线 + 公式引擎计算指标 + 增量/全量混合策略**）：

```
1. 等数据更新（或时间步进）
2. 新数据来了吗？
   → 没来：去步骤 3
   → 来了：
       latest_tick[code] = new_bar
       data_dirty = True  （全局标记，数据变了）
       # 股票所在节点标记为脏
       for nid in code_nodes[code]:
           dirty_nodes.add(nid)
3. 处理 TTL 过期：
   从 ttl_expiry_queue 弹出所有 expire_ts <= now 的股票
   → 从对应节点 node_stocks[nid] 移除
   → 节点 nid 加入 dirty_nodes
4. 处理 dirty_nodes（按边的执行顺序）：
   while dirty_nodes 不为空：
      取出一个节点 nid
      
      遍历 nid 的所有条件出边，按 edge_order 排序：
         eid = 当前边
         sid, tid = edge_endpoints[eid]
         
         a. 检查三要素：
            ① 时间触发条件满足吗？
               → 不满足：跳过
            ② 数据变了吗 OR 源节点变了吗？
               data_dirty OR is_dirty(sid)
               → 都没变：跳过
         
         b. === 第一层：指标计算（调用公式引擎） ===
            indicator_ids = edge_indicator_refs[eid]
            source_codes = node_stocks[sid]
            
            对每个 ind_id in indicator_ids:
                spec = formula_registry[ind_id]
                # 直接调用公式引擎，不关心它内部怎么缓存
                values = formula_engine.calculate_batch(
                    codes=source_codes,
                    formula=spec['name'],
                    period=spec['period'],
                    args=spec['args'],
                )
                # （可选）股票池引擎可以缓存一轮内的结果，但跨tick不缓存
                # 跨tick的缓存是公式引擎的事
            
            # 所有指标值都准备好了
         
         c. === 第二层：比较判断（独立型增量） ===
            compare_spec = edge_compare_spec[eid]
            operator = comparison_operators[compare_spec["operator_id"]]
            
            如果是独立比较型：
               → 增量比较：只重算数据变了的股票
               → 汇总得到 per_stock_result[code] = bool
         
         d. === 第三层：集合运算（AND/OR/NOT/排名） ===
            set_op_spec = edge_set_op_spec[eid]
            
            如果是排名型：
               → 全量读指标值（从公式引擎的结果）
               → 全量排名
               → passed_codes = 排名结果
            
            如果是逻辑组合型：
               → 组合多个比较结果
               → passed_codes = 组合结果
         
         e. === propagate（边的步骤，不是filter层） ===
            propagate_spec = edge_propagate_spec[eid]
            → 应用传播模式到 node_stocks[tid]
            → 对比得到 entered_codes 和 exited_codes
         
         f. 如果有变化：
              - tid 加入 dirty_nodes
              - 处理无条件边：立即同步 propagate
              - 立即发射入池/出池事件
      
      # 处理完这个节点的所有边后，从 dirty_nodes 移除
      dirty_nodes.discard(nid)
5. 清 data_dirty（本轮tick处理完了）
6. 回去等下一次数据更新
```

**v1.6.1 核心循环的关键变化（相对于 v1.6）：**

1. **砍掉周期级版本号**：没有 period_version，只有一个全局 data_dirty 标记
2. **砍掉股票池引擎的指标缓存**：指标缓存是公式引擎内部的事
3. **砍掉kline_cache作为核心表**：K线缓存是数据层/公式引擎的事
4. **保留所有正确的设计**：filter三层、公式注册表、比较算子正交化、节点脏驱动、传播是边的步骤

## 附录：为什么 v1.6 会犯这个错误？

### 回测思维 vs 实盘思维

| 维度 | 回测思维（错误） | 实盘思维（正确） |
|------|----------------|----------------|
| K线状态 | 所有K线都是已完成的 | 最新一根K线是未完成的，一直在变 |
| 日线更新频率 | 一天一次（收盘后） | 每个tick都可能变（收盘价、最高价、成交量都在变） |
| 5分钟线更新频率 | 5分钟一次 | 每个tick都可能变 |
| 缓存粒度 | 可以按周期分（不同周期更新频率不同） | 不需要按周期分（最新tick变了所有周期都可能变） |
| 指标更新 | 按周期更新（不同周期更新时间不同） | 最新值每个tick都可能变 |

### 为什么会混淆？

因为我们平时说"日线"、"5分钟线"的时候，隐含的语境往往是"已完成的"。
- "昨天的日线" —— 已完成，不会变了
- "上一根5分钟线" —— 已完成，不会变了

但实盘中我们关心的是"当前"的指标值，用的是"最新一根K线"——不管什么周期，这根K线都是未完成的，一直在变。

所以对于股票池过滤（关心的是"现在满足条件吗"）：
- 用的都是最新值
- 最新值包含最新一根未完成的K线
- 最新tick变了 → 所有周期的最新值都可能变
- 所以一个全局水位线就够了

### 那历史K线的缓存呢？

历史K线（已完成的）的指标值确实是不变的，可以缓存。
但这是**公式引擎内部的优化**，不是股票池引擎需要关心的。

公式引擎可以这样做：
- 缓存历史K线的指标值（已完成的，不会变）
- 最新一根K线的指标值，每个tick重算
- 或者增量更新最新一根K线的指标值

这些都是公式引擎自己的事，股票池引擎不需要知道。
股票池引擎只需要知道："数据变了吗？变了我就调用公式引擎重算。"
