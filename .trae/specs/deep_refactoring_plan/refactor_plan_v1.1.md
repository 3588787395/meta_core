## 1. 重构目标

### 1.1 一句话目标

**把 3500 行的"大泥球"引擎，重构成 10 张核心运行时表 + 8 张核心配置表驱动的、不超过 800 行的简洁引擎。**

### 1.2 量化目标

| 指标 | 现状 | 目标 | 减少比例 |
|------|------|------|---------|
| engine.py 代码行数 | 3504 行 | ≤ 800 行 | ≥ 77% |
| 核心循环函数行数 | ~500 行 | ≤ 150 行 | ≥ 70% |
| 运行时表数量 | 29 张 | 10 张核心 | ≥ 66% |
| 核心配置表数量 | 50+ 张（引擎直接依赖） | 8 张 | ≥ 84% |
| 空转性能（水位线不变） | 全量遍历计算 | 直接返回（≈0） | ≥ 100x |
| 单条边触发性能 | 全量遍历 | 只算该边 | ≥ 10x |
| 全量计算性能 | 基准 | ≥ 5x | ≥ 5x |
| 新旧引擎输出一致性 | - | 100% 一致 | - |

### 1.3 非目标（什么不做）

- **不改变用户可见行为**：所有现有股票池模板必须 100% 兼容，输出结果完全一致
- **不新增功能**：重构期间不加新功能，只简化和整理
- **不重构公式引擎**：FormulaRouter 保持现状，只调整调用方式
- **不重构 UI 框架**：前端 editor.js 只做必要的对齐，不大改
- **不替换数据源**：数据推送接口保持不变
- **不重构 XML 导入导出**：converters 保持现状

## 2. 核心原则

### 2.1 表驱动原则

**逻辑隐含于表结构，差异显示于表内容。**

不是把 if-else 搬进 JSON，而是找到正交维度，用组合表达多样性。

- 时间触发：8 种 starttype × 3 种 cxtype = 24 种组合，用 11 条规则覆盖
- 过滤条件：6 种 nset × 10 种 noperate = 60 种组合，用 16 个函数覆盖
- 传播模式：3 种模式 = 3 条记录
- 节点角色：5 种角色 = 5 条行为定义

**判断标准：新增一种同类功能，只需要加一条表记录，不需要改引擎代码。**

### 2.2 数据驱动原则

**数据变了才计算，不变不算。**

核心机制：`latest_tick_ts` 时间水位线。

- 水位线没涨 → 所有 K 线数据不变 → 所有公式结果不变 → 所有过滤结果不变 → 什么都不用算
- 节点股票没变 → 该节点的出边不用检查
- 边的时间条件没到 → 即使源节点脏也不执行

**判断标准：水位线不变时，引擎开销为 0（不进入核心循环）。**

### 2.3 事件驱动原则

**过滤完成触发目标节点更新和预警事件。**

不是轮询所有节点，而是脏标记沿边传播：

```
数据更新 → 源节点脏 → 出边入队 → 执行边 → 目标节点脏 → 目标出边入队 → ...
```

事件在状态变化时实时生成，不是 tick 末统一差分：

- 入池事件：股票进入目标节点时立即生成
- 出池事件：股票离开节点时立即生成
- 预警事件：目标节点变化时立即检查规则

### 2.4 前端后端一体原则

**拓扑与综合设置表格一致，流程与执行顺序一致。**

- 后端：`edge_order` 列表 = 执行顺序
- 前端：综合设置表格 = 执行顺序的可视化
- 前端：拓扑画布 = 连接关系的可视化
- 调整执行顺序：前端拖拽 → 写回 `edge.params._order` → 后端重新编译

**判断标准：用户在综合设置里看到的顺序，就是实际执行的顺序。**

### 2.5 可验证原则

**没有基准测试的重构都是耍流氓。**

- 性能基准：空转/全量/典型场景，有量化指标
- 正确性基准：新旧引擎对拍，100% 一致
- 每一步重构都有可验证的验收标准
- 自动化测试贯穿始终

### 3.2 运行时表设计（10 张核心表）

> v1.0 只有 4 张表，遗漏了大量必要的运行时状态。v1.1 补全到 10 张核心运行时表。

#### 表 1：`latest_tick` — 最新行情数据表

| 项 | 说明 |
|---|------|
| **用途** | 所有股票的最新 tick 数据，唯一真相源 |
| **主键** | `code`（股票代码） |
| **关键字段** | `price`, `volume`, `amount`, `open`, `high`, `low`, `prev_close`, `ts` |
| **数据结构** | `Dict[code → bar_dict]` |
| **生命周期** | 引擎启动时初始化，行情推送时更新，引擎停止时销毁 |
| **读时机** | filter 计算、公式求值 |
| **写时机** | 行情推送时（tick_table.update） |
| **谁管理** | `tick_table.py` |

#### 表 2：`latest_tick_ts` — 全局时间水位线

| 项 | 说明 |
|---|------|
| **用途** | 最新 tick 的时间戳，数据不变则值不变 |
| **主键** | 无（单值） |
| **关键字段** | `ts: float` |
| **数据结构** | `float` |
| **生命周期** | 同 latest_tick |
| **读时机** | 边触发判定、TTL 检查 |
| **写时机** | 数据真的变了的时候（hash 变化） |
| **谁管理** | `tick_table.py` |

#### 表 3：`node_stocks` — 节点股票列表

| 项 | 说明 |
|---|------|
| **用途** | 每个节点当前持有的股票列表 |
| **主键** | `nid`（节点 ID） |
| **关键字段** | `stocks: Dict[code → entry_info]`，entry_info 包含 `enter_ts`（入池时间） |
| **数据结构** | `Dict[nid → Dict[code → {enter_ts, ...}]]` |
| **生命周期** | 编译后初始化（源节点填充初始股票），运行时动态变化，重置时清空 |
| **读时机** | propagate 读写、filter 读、事件生成 |
| **写时机** | 边执行后、TTL 淘汰后、手工调整后 |
| **谁管理** | `engine.py` + `propagate.py` |

#### 表 4：`node_data_ts` — 节点数据时间戳（数据脏标记）

| 项 | 说明 |
|---|------|
| **用途** | 每个节点最后一次数据更新的时间戳（对应数据脏） |
| **主键** | `nid` |
| **关键字段** | `data_ts: float` |
| **数据结构** | `Dict[nid → float]` |
| **生命周期** | 同 node_stocks |
| **读时机** | 边触发判定（条件边需要检查数据脏） |
| **写时机** | 全局水位线上涨时，源节点的 data_ts 更新 |
| **谁管理** | `engine.py` |

#### 表 5：`node_stock_ts` — 节点股票变化时间戳（股票脏标记）

| 项 | 说明 |
|---|------|
| **用途** | 每个节点股票列表最后变化的时间戳（对应股票脏） |
| **主键** | `nid` |
| **关键字段** | `stock_ts: float` |
| **数据结构** | `Dict[nid → float]` |
| **生命周期** | 同 node_stocks |
| **读时机** | 边触发判定（所有边都检查股票脏） |
| **写时机** | 节点股票变化时（边执行后、TTL 淘汰后） |
| **谁管理** | `engine.py` |

#### 表 6：`edge_pending_queue` — 待执行边队列

| 项 | 说明 |
|---|------|
| **用途** | 因源节点变脏而待执行的边队列（事件驱动核心） |
| **主键** | 无（有序列表，元素是 eid） |
| **关键字段** | `queue: List[eid]`，按 edge_order 排序插入 |
| **数据结构** | `List[eid]`（去重、保序） |
| **生命周期** | 每 tick 开始时可能有初始项，处理过程中动态增减，tick 结束时清空 |
| **读时机** | 核心循环（从队列头取边执行） |
| **写时机** | 节点变脏时（把出边加入队列）、边执行完后（从队列移除） |
| **谁管理** | `engine.py` |

#### 表 7：`edge_executed_set` — 本 tick 已执行边集合

| 项 | 说明 |
|---|------|
| **用途** | 记录本 tick 已执行过的边，防止循环依赖导致的死循环 |
| **主键** | `eid` |
| **关键字段** | `executed: Set[eid]` |
| **数据结构** | `Set[eid]` |
| **生命周期** | 每 tick 开始时清空，tick 结束时保留（用于调试） |
| **读时机** | 边入队前检查（已执行过的边不重复入队） |
| **写时机** | 边执行完后标记 |
| **谁管理** | `engine.py` |

#### 表 8：`timing_state` — 时间触发状态

| 项 | 说明 |
|---|------|
| **用途** | 每条边的时间触发状态（执行次数、首次触发时间等） |
| **主键** | `eid` |
| **关键字段** | `exec_count: int`（执行次数）, `first_trigger_ts: float`（首次触发时间）, `last_trigger_ts: float`（上次触发时间） |
| **数据结构** | `Dict[eid → {exec_count, first_trigger_ts, last_trigger_ts}]` |
| **生命周期** | 编译后初始化，运行时更新，重置时重置 |
| **读时机** | timing 判定（cxtype 需要执行次数/持续时间） |
| **写时机** | 边触发执行后 |
| **谁管理** | `timing.py` |

#### 表 9：`event_queue` — 事件队列

| 项 | 说明 |
|---|------|
| **用途** | 本 tick 生成的所有事件（入池/出池/预警/信号） |
| **主键** | 无（有序列表） |
| **关键字段** | `events: List[event_dict]`，event 包含 `type`, `code`, `node_id`, `ts`, `edge_id`, `reason` |
| **数据结构** | `List[event_dict]` |
| **生命周期** | 每 tick 开始时清空，执行过程中追加，tick 结束时输出 |
| **读时机** | 事件分发、预警检查、历史记录 |
| **写时机** | 节点股票变化时（角色行为生成事件） |
| **谁管理** | `events.py` |

#### 表 10：`execution_tracker` — 执行跟踪器（调试用）

| 项 | 说明 |
|---|------|
| **用途** | 记录每条边的执行轨迹，用于调试和性能分析 |
| **主键** | `tick_seq + eid`（每 tick 每条边一条记录） |
| **关键字段** | `tick_seq`, `eid`, `trigger_reason`（data_dirty/stock_dirty）, `executed`（是否执行）, `skipped_reason`, `duration_ms`, `changed_count` |
| **数据结构** | `List[track_record]`（环形缓冲，保留最近 N 个 tick） |
| **生命周期** | 引擎启动时初始化，运行时追加，超过缓冲大小后覆盖 |
| **读时机** | 调试查询、性能分析、问题定位 |
| **写时机** | 每条边执行/跳过后记录 |
| **谁管理** | `tracker.py`（可选模块） |

### 3.6 核心流程（从 tick 到事件的完整路径）

> v1.0 的流程太粗略，遗漏了 TTL、告警、错误处理、循环防护等关键步骤。v1.1 补全完整流程。

```
┌─────────────────────────────────────────────────────────────────────┐
│                     Tick 入口（外部调用 run_once）                   │
└─────────────────────────────────┬───────────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Step 1: 数据更新（tick_table.update）                              │
│    ├─ 写 latest_tick[code] = new_bar                               │
│    ├─ 计算全量 hash                                                │
│    ├─ hash 没变 → 返回 False（水位线不涨）                          │
│    └─ hash 变了 → latest_tick_ts = now()，返回 True                │
└─────────────────────────────────┬───────────────────────────────────┘
                                  │
                    ┌─────────────┴─────────────┐
                    │ 水位线涨了吗？             │
                    └─────────────┬─────────────┘
                                  │
           ┌────────────── 否 ────┴──── 是 ──────────────┐
           │                                              │
           ▼                                              ▼
┌──────────────────────┐                   ┌───────────────────────────────┐
│  直接返回空 events   │                   │  Step 2: 初始化本 tick 状态    │
│  （零计算开销）      │                   │    ├─ edge_executed_set.clear()│
└──────────────────────┘                   │    ├─ event_queue.clear()      │
                                           │    └─ edge_pending_queue.clear()│
                                           └───────────────┬───────────────┘
                                                           │
                                                           ▼
                                           ┌───────────────────────────────┐
                                           │  Step 3: TTL 淘汰预处理       │
                                           │    遍历所有有 TTL 的节点：    │
                                           │    ├─ 检查股票 enter_ts + ttl │
                                           │    ├─ 超时的股票从节点移除     │
                                           │    ├─ 节点股票变了 →          │
                                           │    │   更新 node_stock_ts     │
                                           │    │   出边加入待执行队列      │
                                           │    │   生成 EXIT 事件          │
                                           │    └─ 继续检查下一个节点      │
                                           └───────────────┬───────────────┘
                                                           │
                                                           ▼
                                           ┌───────────────────────────────┐
                                           │  Step 4: 标记源节点数据脏     │
                                           │    遍历所有源节点：            │
                                           │    ├─ node_data_ts = now_ts   │
                                           │    └─ 把源节点的出边加入队列   │
                                           │       （但只有条件边才响应数据脏）│
                                           └───────────────┬───────────────┘
                                                           │
                                                           ▼
                                           ┌───────────────────────────────┐
                                           │  Step 5: 边队列处理循环       │
                                           │  while edge_pending_queue 非空:│
                                           │    ├─ 从队列头取边 eid        │
                                           │    ├─ 已执行过？→ skip        │
                                           │    ├─ 取源节点 sid            │
                                           │    ├─ 判定是否触发：          │
                                           │    │  无条件边：              │
                                           │    │    stock_dirty → 触发    │
                                           │    │    data_dirty → 不触发   │
                                           │    │  条件边：                │
                                           │    │    (stock_dirty OR data_dirty)│
                                           │    │    AND time_triggered → 触发│
                                           │    ├─ 不触发 → skip，取下一条 │

                                           │    │  │  propagate 写入目标 │  │
                                           │    │  └────────────────────┘  │

                                           │    │  ├─ 没变 → 不标记       │
                                           │    │  └─ 变了 →              │
                                           │    │       更新 node_stock_ts│

                                           │    │       （流式级联）      │
                                           │    ├─ 角色行为：             │

                                           │    │  │ Step 5b: 生成事件   │  │
                                           │    │  │  roles.on_change()  │  │
                                           │    │  │  → 入池/出池事件    │  │
                                           │    │  │  → 预警检查         │  │

                                           │    │  └────────────────────┘  │
                                           │    ├─ 标记 eid 已执行         │
                                           │    └─ 记录到 tracker          │
                                           └───────────────┬───────────────┘
                                                           │
                                                           ▼
                                           ┌───────────────────────────────┐
                                           │  Step 6: 事件后处理           │
```

## 4. 现有问题诊断

### 4.1 问题一：运行前与运行时混淆

**表现：**
- 每 tick 都重算拓扑序、重解析边参数、重找端点
- engine.py 里混杂着配置解析、规格编译、运行时逻辑
- CompiledSchedule 存在但没被充分利用，很多信息运行时还在重复计算

**影响：**
- 性能浪费：每 tick 都在做运行前就能做完的事
- 代码混乱：编译逻辑和运行逻辑搅在一起，难以理解和修改
- bug 隐患：重复计算可能不一致

**根因：**
- 没有明确的"编译期"概念，什么都塞进运行时
- 代码是渐进式累加的，没有统一的架构设计

### 4.2 问题二：数据更新与计算逻辑耦合

**表现：**
- 数据推送进来，直接触发全量计算
- 没有"水位线"概念，不知道数据到底变没变
- K 线合成和股票池计算搅在一起

**影响：**
- 性能差：即使数据没变（比如同一秒重复推送），也全量重算
- 逻辑混乱：数据层和计算层边界不清
- 难以优化：不知道哪里该缓存、哪里该跳过

**根因：**
- 没有把"数据变化"作为一等公民来管理
- 缺少统一的数据层抽象

### 4.3 问题三：三套 filter 各搞一套

**表现：**
- unconditional filter：一套逻辑
- conditional filter：一套逻辑
- formula_eval filter：又一套逻辑
- 三套逻辑有重叠，但各写各的

**影响：**
- 代码重复：相似的逻辑写三遍
- 行为不一致：三套逻辑可能有细微差别
- 难以维护：改一个要改三个地方

**根因：**
- 没有找到 filter 的统一抽象
- 没有用表驱动来组织不同类型的 filter

### 4.4 问题四：事件是 tick 末差分生成，不是实时

**表现：**
- 每个 tick 末，统一对比所有节点的新旧状态，生成事件
- 事件和触发它的边执行没有直接关联
- 预警检查也是统一做的

**影响：**
- 事件溯源困难：不知道哪个边触发了哪个事件
- 难以做增量处理：每次都是全量差分
- 不符合事件驱动的直觉：应该是"变化了就发事件"

**根因：**
- 架构上是"轮询"思维，不是"事件驱动"思维
- 脏标记机制不完善

### 4.5 问题五：拓扑与执行顺序混淆

**表现：**
- 用拓扑排序的结果当执行顺序
- 用户在综合设置里调整的顺序不生效
- 前端有拓扑视图、综合设置表格、执行顺序三种说法，后端只有一个拓扑序

**影响：**
- 用户困惑：为什么我调了顺序不生效？
- 前后端不一致：前端说的和后端做的不是一回事
- 策略无法按用户想要的顺序执行

**根因：**
- 没有区分"拓扑（连接关系）"和"执行顺序（处理次序）"两个概念
- 执行顺序没有作为一等公民来设计

### 4.6 问题六：缺少基准测试框架（v1.1 新增诊断）

**表现：**
- 没有性能基准，不知道重构后快了多少
- 没有正确性基准，不知道重构后行为是否一致
- 重构效果全靠"感觉"，没有数据支撑

**影响：**
- 重构是否成功无法量化验证
- 性能退化无法及时发现
- 回归问题只能靠人工测试

**根因：**
- 重构前没有建立基准线
- 缺少自动化对比测试框架

## 7. 基准测试与验证框架（v1.1 新增）

### 7.1 为什么需要基准测试

**没有基准的重构 = 盲人摸象。**

重构前必须建立基线，重构后才能量化回答：
1. 行为是不是一样？（正确性）
2. 性能是不是更好？（性能）
3. 代码是不是更简洁？（可维护性）

本章定义完整的基准测试框架，确保重构每一步都可验证。

### 7.2 正确性基准：新旧引擎对拍

#### 7.2.1 对拍原理

```
┌─────────────┐     tick 序列      ┌─────────────┐
│  旧引擎     │ ─────────────────→ │  新引擎     │
│  (基线)     │                     │  (重构后)   │
└──────┬──────┘                     └──────┬──────┘
       │                                     │
       ▼                                     ▼
┌─────────────┐                     ┌─────────────┐
│  旧结果     │                     │  新结果     │
│  (黄金数据)  │                     │             │
└──────┬──────┘                     └──────┬──────┘
       │                                     │
       └───────────────┬─────────────────────┘
                       │
                       ▼
              ┌─────────────────┐
              │  逐字段对比      │
              │  输出差异报告    │
              └─────────────────┘
```

#### 7.2.2 对比维度

| 对比层级 | 对比内容 | 通过标准 |
|---------|---------|---------|
| 节点股票 | 每个节点每 tick 的股票列表 | 完全一致（股票集合、入池时间） |
| 事件序列 | 入池/出池/预警/信号事件 | 事件数量、类型、股票、顺序完全一致 |
| 时间触发 | 每条边的触发时机 | 触发 tick 序号完全一致 |
| TTL 淘汰 | TTL 触发的股票移除 | 移除时机、移除股票完全一致 |

#### 7.2.3 对拍工具

**工具位置：** `tests/benchmark/compare_engines.py`

- 每个差异的详细对比（旧值 vs 新值）

### 7.3 性能基准：三种场景

#### 7.3.1 场景定义

| 场景 | 描述 | 测量指标 | 目标提升 |
|------|------|---------|---------|
| **空转性能** | 数据完全不变（水位线不涨） | 单 tick 耗时 | ≥ 100x |
| **单条边触发** | 只有一条边的源节点变脏 | 单 tick 耗时 | ≥ 10x |
| **全量计算** | 所有股票都变，所有边都执行 | 单 tick 耗时 | ≥ 5x |

#### 7.3.2 性能测试方法

**测试流程：**
1. Warmup：跑 100 个 tick（预热 JIT/缓存）
2. 测量：跑 1000 个 tick，记录每个 tick 的耗时
3. 统计：计算 P50 / P95 / P99 / 平均耗时
4. 对比：与基线对比，计算提升倍数

**测试工具：** `tests/benchmark/perf_benchmark.py`

**使用方式：**
```bash
# 单场景性能测试
python -m tests.benchmark.perf_benchmark --pool large_pool --scenario idle

# 全场景性能测试
python -m tests.benchmark.perf_benchmark --all

# 与基线对比
python -m tests.benchmark.perf_benchmark --all --compare baseline_v1.json

# 快速模式（少跑几次，用于开发期快速验证）
python -m tests.benchmark.perf_benchmark --pool simple_pool --quick
```

#### 7.3.3 性能报告

**报告内容：**
- 三种场景的耗时统计表（P50/P95/P99/平均）
- 吞吐量（ticks/秒）
- 与基线的对比（提升倍数）
- 各池子的性能数据
- 火焰图（可选，用于定位瓶颈）

**性能基线保存：**
- 基线数据保存在 `tests/benchmark/baselines/`
- 每次重构里程碑保存一个基线版本
- 可追溯性能变化历史

## 8. 版本变更摘要（v1.0 → v1.1）

### 8.1 变更原因

上一轮评审评分 68/100，3 个最严重问题：
1. 依赖关系和工作量估计错误，第一阶段必然延期
2. 运行时表设计有明显遗漏，核心流程不完整
3. 验收标准偏软，无法验证重构是否成功

### 8.2 主要变更内容

#### 架构设计补全
- **运行时表：** 从 4 张扩展到 10 张核心表
  - 新增：node_data_ts（数据脏标记）
  - 新增：node_stock_ts（股票脏标记）
  - 新增：edge_pending_queue（待执行边队列）
  - 新增：edge_executed_set（循环防护）
  - 新增：timing_state（时间触发状态）
  - 新增：event_queue（事件队列）
  - 新增：execution_tracker（执行跟踪器）
- **核心流程：** 从粗略 5 步补全到完整 7 步
  - 新增 TTL 淘汰预处理
  - 新增边队列事件驱动循环
  - 新增循环防护机制
  - 新增事件后处理
  - 补充边触发判定真值表
- **模块边界：** 8 个模块的职责、输入输出、依赖关系全部明确定义

#### 工期计划调整
- **第一阶段：** 从 2 周调整为 3 周
- **新增阶段零：** 基准测试搭建（0.5 周前置）
- **任务拆分：** 从 7 个任务扩展到 12 个（含 3 个前置 + 9 个阶段一任务）
  - 新增 T0-1/T0-2/T0-3：基准测试框架
  - 新增 T8：TTL 淘汰机制完善
  - 新增 T9：执行跟踪器
- **缓冲时间：** 增加 20% 缓冲（3 天）
- **每周缓冲：** 每周第 7 天为缓冲日

#### 验收标准硬化
- 每个任务的验收标准从"描述性"改为"可量化、可验证"
- 引入对拍通过率、单元测试覆盖率、性能提升倍数等硬指标
- 每个任务都绑定具体的基准测试池子

#### 新增基准测试框架（第 7 章）
- **正确性基准：** 新旧引擎对拍（4 个对比维度）
- **性能基准：** 三种场景（空转/单条边/全量）
- **测试用例集：** 5 个典型池子（简单/多节点/多分支/复杂条件/大池子）
- **测试自动化：** 开发期验证 + 提交前验证 + CI 集成
- **代码质量基准：** 行数、复杂度、覆盖率等量化指标

## 附录：术语表

| 术语 | 定义 |
|------|------|
| 水位线 | `latest_tick_ts`，数据最新时间戳，水位线不涨则数据不变 |
| 脏标记 | 节点"需要重新处理"的标记，分数据脏和股票脏 |
| 数据脏 | 水位线涨了，该节点的输入数据可能变了 |
| 股票脏 | 节点的股票列表变了（入池/出池/TTL淘汰） |
| 执行顺序 | `edge_order`，边的处理次序，用户可在综合设置调整 |
| 拓扑 | 节点和边的连接关系图，用来画界面和校验 |
| CompiledPool | 编译后的股票池配置，运行时只读 |
| 表驱动 | 逻辑隐含于表结构，差异显示于表内容 |
| 对拍测试 | 新旧引擎相同输入、对比输出的测试方法 |
| 基准测试 | 建立性能/正确性基线，用于对比重构效果的测试 |
| TTL | Time To Live，股票在节点中的存活时间 |
| 流式级联 | 同 tick 内前边的执行结果能被后边立即看到 |
