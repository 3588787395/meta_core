### 2.3 函数 3：`propagate_stocks` —— 5.5/10（问题最多）

**做得好的：**

| 问题 | 严重度 | 说明 |
|------|--------|------|

| `get_node_ttl_config(to_id)` 从哪来？ | 🔴 高 | 函数参数里没有编译后的配置，这个函数是全局的？从哪里查配置？ |
| `pool_now_ts()` 是全局函数？ | 🔴 高 | 在这个函数里直接调用全局时间函数，合适吗？为什么不作为参数传入？（测试时怎么 mock？） |
| copy 模式用 `copy.deepcopy(s)` 的理由是什么？ | 🟡 中 | 股票对象里有什么可变状态需要深拷贝？如果只是 `{code, name, ...}` 浅拷贝就够了。深拷贝的性能代价很大 |
| move 模式下，已在目标节点的股票不会出现在 `entered` 里，但会从源节点移除——语义对吗？ | 🟡 中 | 一只股票同时在源和目标，move 模式下从源移除但目标不动，那它算不算"流转"？事件怎么发？ |

### 2.4 函数 4：`check_alerts` —— 5/10（设计缺陷最大）

**做得好的：**
- 作用域模型的引入方向正确
- 冷却机制、告警事件结构的基本想法是对的

**设计缺陷与漏洞：**

| 问题 | 严重度 | 说明 |
|------|--------|------|
| **边级/池级告警与"按股票循环"的设计矛盾** | 🔴 高 | 边级告警的例子是 `transferred_count > 0`（统计性的，不针对单只股票），但 `check_alerts` 内部是 `for stock in stocks_to_check` 逐只检查。池子级告警"池子空了"也是统计性的。这两种 scope 不该按股票循环 |
| `scope_obj` 用鸭子类型判断（`'from' in scope_obj`） | 🔴 高 | 太脆弱了。如果 node 配置里恰好也有 `from` 字段怎么办？应该有明确的 `_type` 字段或用不同的类 |
| 冷却 key 是 `(rule_id, code)`，但池级告警没有 code | 🔴 高 | "池子空了"这个告警的 code 填什么？空字符串？这会导致冷却逻辑出错 |
| node 级告警的 `changes` 可能是入池列表也可能是出池列表，但规则怎么知道是哪种？ | 🟡 中 | 调用时分别传了 `changes.entered` 和 `changes.exited`，但 `_build_alert_context` 里不包含"这是入池还是出池"的信息。告警规则的条件表达式怎么区分？ |
| `_build_alert_context` 完全没有伪代码 | 🔴 高 | 这是核心！告警条件里能用哪些变量？ctx 的结构是什么？开发者全靠猜 |
| `_render_alert_message` 完全没有伪代码 | 🟡 中 | 模板变量怎么替换？ |
| 告警规则的 condition 可用变量没有契约 | 🟡 中 | `tracker.profit_pct`、`transferred_count`、`total_stocks`——这些变量从哪来？不同 scope 下可用的变量集一样吗？ |

**最严重的设计缺陷：** 三级作用域（node/edge/pool）的告警检查模式不一样：
- node 级：针对单只股票，逐只检查
- edge 级：针对流转统计，检查一次
- pool 级：针对全池状态，检查一次

但 `check_alerts` 用同一套"按股票循环"的逻辑处理所有三种 scope，这是削足适履。应该拆成不同的检查函数，或者用策略模式。

## 四、3 条最深刻的洞见

### 洞见 1：时间源二分法（触发时间 vs 数据时间）是真洞察

**为什么深刻：** 这不是"为了统一而统一"的形式主义，而是直击现有代码的核心痛点——触发判断和数据计算混用时间源，导致 replay 模式和 live 模式下行为不一致，bug 难排查。

`pool_now()` 管"该不该做"，`data_ts()` 管"用什么数据算"，两者各司其职，这个划分是本质性的，不是拍脑袋的。

### 洞见 2：数据不变 = 不用算，抓住了性能优化的牛鼻子

**为什么深刻：** 很多人优化性能一上来就加缓存、改算法，但股票池系统最大的性能浪费是"重复计算相同数据下的相同结果"。

只要数据时间戳没变，所有 K 线、指标、过滤结果都不会变。这个简单的观察可以砍掉 80% 的无用计算，比任何算法优化都有效。

### 洞见 3：告警/信号规则需要作用域，不能全局一锅粥

**为什么深刻：** v2.2 里告警规则是全局的，然后用 scope 字段（`tracker`、`node` 之类模糊的词）来区分，既不清晰也不高效。v2.3 提出"规则定义在库里，绑定到节点/边/池上"，这个模型是对的——既复用了规则定义，又明确了作用范围，性能也好（运行时只检查绑定的规则）。

虽然实现细节还有很多问题，但方向是对的。

## 五、3 条最肤浅的理解

### 肤浅 1："股票池 = 篮子 + 管子 + 筛子"的比喻停留在表面

**为什么肤浅：** 这个比喻适合给老板讲，但作为架构设计文档的"本质"总结就太浅了。

股票池的本质是**有状态的数据流处理器**：
- 状态 = 节点里的股票 + 持仓跟踪 + 时序状态
- 数据流 = 边触发 → 过滤 → 流转 → 产生信号/告警
- 时间驱动 = 按 tick 推进，状态随时间演化

"篮子 + 管子"是静态结构视角，漏掉了"状态演化"和"时间驱动"这两个核心维度。

### 肤浅 2：作用域模型只停留在"怎么绑定"，没回答"为什么需要三级"

**为什么肤浅：** 文档花了很多篇幅讲"怎么把告警规则绑定到节点/边/池上"，但没讲清楚——
- 为什么需要三级？两级（节点级 + 池级）够不够？
- 边级告警和"边的源/目标节点的告警"有什么本质区别？
- 信号规则为什么也需要三级？边级信号的使用场景是什么？

如果没有明确的使用场景支撑，三级作用域就是过度设计。

### 肤浅 3：重构路径"五步走"是拍脑袋的瀑布式规划

**为什么肤浅：** 五步（数据层 → 运行时表 → 计算层 → 编译期 → 配置层）听起来顺，但：
- 为什么是这个顺序？依据是什么？
- 每一步的验收标准是什么？怎么验证"做对了"？
- 每一步需要多久？有里程碑吗？
- 中间可以回退吗？

更严重的是，第一步"统一数据层"的工作，现有代码已经做了一大半了（`_latest_tick` + `DataQuery`），说明规划时没有仔细勘察现状。

## 七、总体结论

### 7.1 到 80 分了吗？——没有，76 分

v2.3 比 v2.2 有进步（+1 分），但离 80 分的"可指导重构"及格线还差 4 分。

**主要差距在可落地性上。** 4 个核心函数虽然有伪代码了，但：
- 2 个有设计缺陷（`propagate_stocks` 的 overwrite bug、`check_alerts` 的 scope 矛盾）
- 依赖大量未定义的函数和变量
- 信号管理、tracker 更新、事件总线这些核心模块还是黑盒

开发者拿着这个文档写代码，还是会有 20 个以上的"这个东西是什么/从哪来/怎么用"的问题要问。

### 7.2 能指导重构吗？——部分能，但仅限第一步

- ✅ 重构第一步（统一数据层）基本可以动手了（虽然需要基于实际代码调整）
- ❌ 第二步及以后还不行，太粗
- ❌ 核心函数的伪代码需要先修 bug 才能用

### 7.3 还差什么？

一句话：**肉没长全，而且长出来的肉里还有骨头长歪了的。**

具体来说：
1. 伪代码的质量问题（2 个设计缺陷需要修）
2. 核心黑盒的数量问题（还有至少 4-5 个核心函数是黑盒）
3. 契约缺失（函数之间的输入输出格式没有严格定义）
4. 对现有代码现状了解不足（导致重构规划有偏差）
