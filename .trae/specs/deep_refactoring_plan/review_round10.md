# 股票池深度重构规划 v1.10 评审报告（第10轮里程碑）

> 评审日期：2026-07-01
> 评审版本：v1.10
> 上轮成绩：78/100（v1.9）
> 本轮成绩：**76/100**
> 评审结论：**架构设计初具雏形，但距离"可以指导开发"还有明显差距，需要继续迭代。**

---

## 一、总体评价

v1.10 是一次**认知澄清型**迭代，而非**架构突破型**迭代。本轮解决了5个认知层面的问题：

1. ✅ 并发模型从"只讲一致性"深化到"一致性+性能平衡"
2. ✅ 批次化从"架构核心"正确降维为"性能优化手段"
3. ✅ 版本屏障从"全局一个版本号"修正为"分层一致性边界"
4. ✅ 比较层 entered 处理 bug 修复（先设 None 再计算）
5. ✅ 三态（True/False/None）从"只在比较层"扩展到"全链路传播"

**值得肯定的进步：**
- 架构师开始反思之前的概念错误，这是成熟的表现
- 三态逻辑运算规则定义完整，类 SQL NULL 语义的类比准确
- 批次化定位的纠正是关键认知升级，"事件驱动+状态机才是核心"这个判断是对的
- 分层一致性边界的提法比"全局版本号"更接近本质

**但必须指出的问题：**
- 本轮更多是"把之前说错的话说对"，而非"把之前没有的东西加上"
- 很多关键设计仍然停留在"概念描述"层面，没有可落地的具体定义
- 与实际代码库（config/ 目录下 80+ JSON 配置表）的脱节问题依然严重
- 前后端一体维度几乎空白
- 错误处理、可观测性、扩展性等架构必备要素仍然缺失

**一句话总结：** 概念方向大体正确，但深度和广度都还不够，离"可以指导开发"还有 2-3 轮迭代的距离。

## 二、分项得分（满分100）

### 1. 行为洞察深度（23/30）—— 比v1.9进步2分

**得分依据：**

| 维度 | 评分 | 说明 |
|------|------|------|
| 并发模型理解 | 7/10 | 认识到单线程CPU瓶颈、提出向量化方案、分析批次权衡。但性能估算过于乐观，对实盘tick不均匀到达考虑不足 |
| 三态逻辑完整性 | 8/10 | AND/OR/NOT 规则定义完整，传播路径清晰。但 None 语义过于模糊，未区分"数据不足/数据过期/计算错误/停牌"等多种情况 |
| 版本屏障认知 | 5/10 | 从全局版本号到分层一致性是进步，但"单线程事件循环是天然版本屏障"的说法不准确——版本屏障的核心是"快照语义"，单线程只是保证串行，不自动等于快照 |

**关键问题：**

## 三、15条具体改进建议

### 架构设计类（5条）

**1. 明确"版本屏障"的精确定义，停止使用"单线程是天然版本屏障"这种模糊说法**
- 版本屏障的核心是：**计算开始时，输入数据有一个确定的快照，计算过程中输入不变化**
- 单线程只是保证"没有并发写入"，但如果计算过程中主动调用了可能修改数据的函数，单线程也没用
- 建议：明确定义每层的"快照获取方式"和"有效期"，用精确的术语替代模糊的比喻

**2. 给 None 细分语义，不要让一个 None 承载所有"不确定"**
- 建议至少区分：`NONE_DATA_INSUFFICIENT`（数据不足）、`NONE_SUSPENDED`（停牌）、`NONE_ERROR`（计算错误）、`NONE_EXPIRED`（数据过期）
- 不同类型的 None 传播规则可以不同：比如计算错误应该告警，数据不足应该静默等待
- 否则排障时你根本不知道一个 None 是"正常的新股数据不够"还是"系统出bug了"

**3. 明确批次化的语义等价性前提，不要假设"批次处理=逐条处理"**
- 批次处理和逐条处理语义等价的前提是：**计算只依赖最终状态，且批次内无依赖关系**
- 这个前提成立吗？比如：同一只股票在一个批次内有两笔tick，指标计算是用最新价，那没问题；但如果是"累计成交量"呢？你需要把两笔都加上
- 建议：明确写出"语义等价性假设清单"，哪些计算满足、哪些不满足、不满足的怎么办

**4. 补充横切关注点的设计：错误处理、降级、监控、扩展性**
- 错误处理：指标计算失败了怎么办？是返回 None 还是抛异常？影响范围多大？
- 降级策略：公式引擎挂了怎么办？股票池还能跑吗？用旧数据还是直接停？
- 监控：怎么知道系统健不健康？有哪些指标？延迟？吞吐？错误率？
- 扩展性：将来要加新的 filter 类型怎么加？加新的事件源怎么加？

**5. 重新审视 dirty_stocks 和 node_data_dirty 的关系，能合并就合并**
- 目前两张表都是"脏标记"，只是粒度不同
- 单线程事件循环里，真的需要全局和节点级两套脏标记吗？
- 建议：要么合并成一张，要么明确说明为什么需要两张，各自的使用场景是什么

### 表驱动类（5条）

**6. 所有配置表和运行时表都必须有完整的结构定义（Schema）**
- 目前很多表只有名字和一句话说明，没有字段定义
- 比如 `edge_set_op_spec`，是树结构还是扁平结构？支持嵌套吗？操作符有哪些？
- 建议：用 JSON Schema 或表格形式，定义每一张表的完整结构

**7. 三态逻辑运算改成真正的表驱动，而不是函数实现**
- 现在的 `tri_state_and()` 是代码，不是表驱动
- 表驱动应该是：定义一张 3×3 的真值表，查表得到结果
- 好处：规则变了不用改代码，改表就行；规则可以动态配置；规则可以序列化传输

**8. 梳理实际代码库的80+配置表，和设计文档里的表建立映射关系**
- 实际 config/ 目录下有 80+ JSON 文件，但设计文档里只提了几张
- 这些表哪些是编译期的、哪些是运行时的？哪些是核心的、哪些是外围的？
- 建议：做一张"实际配置表 → 设计概念"的映射表，不然设计和实现永远两张皮

**9. 补充错误表、审计表、统计信息表等运行必备表**
- `calculation_errors`：计算错误记录表（哪只股票、哪个指标、什么错误、什么时候）
- `audit_log`：审计日志表（谁在什么时候改了什么配置）
- `performance_stats`：性能统计表（各层耗时、缓存命中率、批次大小分布）
- 这些不是"可选的锦上添花"，是生产系统必备的

**10. 明确"编译期"和"运行时"的边界，哪些表在编译期生成、哪些在运行时生成**
- 现在的说法是"编译期一次性收集"，但编译期到底做什么？
- 建议：画一张"编译期产物 → 运行时输入"的流程图，明确各阶段的输入输出

### 事件驱动类（3条）

**11. 明确事件模型的完整定义：ID、时间戳、版本、payload、幂等键**
- 现在的事件只有类型，没有完整定义
- 每个事件应该有：唯一ID、发生时间、事件类型、payload schema、版本号、幂等键
- 没有这些，事件溯源、事件重放、幂等处理都无从谈起

**12. 明确 `wait_for_event()` 的实现机制，不要回避"是不是轮询"的问题**
- 如果是用 `asyncio` 等真正的事件循环，那没问题
- 如果是 `while True: sleep(10ms); check_queue()`，那就是轮询
- 建议：诚实说明实现方式，以及为什么选择这种方式，不用硬凹"纯事件驱动"

**13. 补充事件溯源和重放能力的设计考量**
- 事件驱动架构的核心价值之一就是"事件可以重放"
- 系统出问题了，能不能用历史事件重放来复现？
- 建议：至少在架构层面预留事件持久化和重放的接口，不一定要现在实现，但要考虑到

### 前后端一体类（2条）

**14. 明确前后端共享什么、不共享什么**
- 配置表共享吗？公式定义共享吗？filter逻辑共享吗？
- 如果共享，怎么共享？是同一份代码跑在两端，还是序列化配置？
- 如果不共享，怎么保证两端行为一致？

**15. 设计实时数据推送方案**
- 股票池状态变化怎么推到前端？
- 是全量推送还是增量推送？
- 推送频率怎么控制？会不会把前端卡爆？
- 建议：明确推送模型，比如"节点股票变化事件 → WebSocket推送 → 前端增量更新"

## 四、5条最深刻洞见

**洞见1：批次化是性能优化，不是架构核心——这个认知升级非常关键**
- 从 v1.9 的"批次是一等公民"到 v1.10 的"批次是实现细节"，这是本质性的认知进步
- 很多人做系统一开始就把"批量处理"当成核心，最后把架构搞复杂了
- 先有"逐条处理的正确语义"，再用"批量处理"做性能优化，这个顺序不能反

**洞见2：三态（True/False/None）是股票池的本质需求，二态必然导致语义错误**
- 股票池里"不知道"是真实存在的状态，不是"可以先随便设一个"
- 新股数据不足、停牌无成交、指标计算出错，这些都是"既不能算通过也不能算不通过"的情况
- 类 SQL NULL 语义的类比非常准确，三态逻辑运算规则定义得也很完整

**洞见3：分层一致性比全局版本号更合理——每层有自己的边界**
- 全局一个版本号听起来简单，但实际上粒度太粗，导致不必要的失效
- 数据层、指标层、比较层、集合运算层，各有各的更新频率和一致性要求
- 分层管理版本，才能做到真正的增量计算

**洞见4：股票池引擎是 IO 密集型，公式引擎是 CPU 密集型——职责分离是对的**
- 这个判断是对的：股票池引擎做调度和状态管理（轻量），公式引擎做计算（重量）
- 两者的性能特征完全不同，优化方向也不同
- 职责分离后，各自可以在自己的领域做到最优

**洞见5：新入池股票先设 None 再计算——"保守估计"原则非常重要**
- 这不是一个小 bug 修复，而是一个设计原则的体现：宁可不判，也不瞎判
- 金融系统里，错误的结论比没有结论更可怕
- 这个"保守策略"应该贯穿整个系统的设计，而不只是比较层

## 五、5条最肤浅理解

**肤浅1："5000只股票×100个指标毫秒级"——性能估算过于乐观，缺乏依据**
- 拍脑袋说"应该在毫秒级"，但没有任何 benchmark 数据支撑
- 实际情况可能是：简单指标（MA）确实快，但复杂指标（MACD、布林带、自定义公式）不一定
- TA-Lib 的向量化程度参差不齐，pandas rolling 也不是零开销
- 最关键的是：内存带宽才是瓶颈，5000只股票的K线数据全读一遍就要时间

**肤浅2："单线程事件循环是天然的版本屏障"——混淆了"串行"和"快照"**
- 单线程保证的是"事情一件一件做"，不是"计算过程中输入不变"
- 版本屏障的核心是**快照语义**：计算开始时输入有一个确定的版本，计算过程中即使底层更新了，本次计算也看不到
- 单线程只是更容易实现版本屏障，但单线程本身不等于版本屏障
- 如果计算过程中调用了修改数据的函数，单线程也会有一致性问题

**肤浅3：None 语义过载——把所有"不确定"都塞进一个 None**
- "新股数据不足"、"停牌"、"计算错误"、"数据过期"，这些完全是不同的情况
- 但文档里都用 None 表示，传播规则也都一样
- 后果是：排障困难（不知道为什么是 None）、策略单一（所有情况都保守处理）
- 正确的做法是：区分不同类型的"未知"，至少有错误码或子类型

**肤浅4："批次处理和逐条处理语义等价"——假设了前提但没说清楚前提是什么**
- 文档说"只要批次内没有依赖，结果就一样"，但哪些计算有依赖、哪些没有？
- 比如：成交量是累加的，同一只股票一个批次内有两笔tick，批量处理（直接用最新累计值）和逐条处理（两笔都加）结果一样吗？
- 再比如："收盘价穿越均线"这种事件，你攒一批处理可能就漏掉了中间的穿越
- 不说清楚前提，就是耍流氓

**肤浅5：前后端一体几乎空白——完全是后端视角，不考虑前端怎么用**
- 股票池系统最终是给人用的，前端展示、交互、实时推送都是核心需求
- 实际代码库里有大量 UI 配置（dashboard_schema、ui_components 等），说明需求是真实存在的
- 但设计文档完全是后端视角，好像股票池算出来就完事了
- 没有前后端一体的设计，最后必然是各做各的，逻辑不一致，体验割裂

## 六、后续迭代方向（如果还有第11轮的话）

### 优先级 P0：可落地性（必须做）

**1. 所有表的 Schema 化**
- 给每一张配置表和运行时表写完整的结构定义
- 用 JSON Schema 或表格形式，字段名、类型、含义、约束，都写清楚
- 目标：开发者拿到 Schema 就能直接写代码，不用猜

**2. 批次化语义等价性证明**
- 明确列出：哪些计算满足"批次处理=逐条处理"，哪些不满足
- 不满足的怎么办？是放弃批次化，还是特殊处理？
- 目标：批次化不是"看起来没问题"，而是"证明没问题"

**3. 错误处理策略设计**
- 每一层可能出什么错？出错了怎么办？影响范围多大？怎么恢复？
- 指标计算失败、公式引擎挂了、数据源断了，这些场景都要有预案
- 目标：错误是可预期的，不是意外

### 优先级 P1：深度（应该做）

**4. None 语义细分**
- 把 None 拆成多种子类型，不同类型有不同的传播规则和处理策略
- 至少区分：数据不足、停牌、计算错误、数据过期

**5. 事件模型完整定义**
- 事件ID、时间戳、版本、payload schema、幂等键
- 事件持久化和重放能力的接口设计

**6. 监控与可观测性设计**
- 关键指标：延迟、吞吐、错误率、缓存命中率
- 告警策略：什么情况告警、告警给谁、怎么告警
- 排障工具：怎么快速定位问题

### 优先级 P2：广度（可以做）

**7. 前后端一体设计**
- 哪些配置共享、哪些逻辑共享、怎么共享
- 实时数据推送方案

**8. 扩展性设计**
- 新 filter 类型怎么加
- 新事件源怎么加
- 新节点类型怎么加

**9. 性能基准测试**
- 用真实数据测一下：5000只股票、100个指标，到底要多久
- 不同批次大小的延迟/吞吐对比
- 用数据说话，不要拍脑袋

## 七、总体结论：距离"可以指导开发"还差多远？

**我的判断：还差 30% 的路，大概还需要 2-3 轮迭代。**

具体来说：

| 维度 | 现状 | 目标（可以指导开发） | 差距 |
|------|------|---------------------|------|
| 概念正确性 | 70% | 90% | 大方向对了，但很多关键概念定义模糊 |
| 设计完整性 | 50% | 85% | 缺少错误处理、监控、扩展性等横切关注点 |
| 可落地性 | 40% | 80% | 表结构、接口、数据格式都没有精确定义 |
| 与实际代码匹配度 | 30% | 70% | 设计文档与实际80+配置表严重脱节 |
| 前后端一体 | 10% | 60% | 几乎空白 |

**"可以指导开发"的标准是什么？**
- 开发者拿着设计文档，不需要问架构师，就能开始写代码
- 表有 Schema，接口有定义，流程有步骤，错误有预案
- 边界清晰，职责明确，不会出现"这事儿归谁管"的争议

**v1.10 目前的状态：**
- 大方向是对的：事件驱动+状态机、三层filter、三态、分层一致性，这些都没问题
- 但深度不够：很多概念只有名字没有精确定义
- 广度不够：很多架构必备的东西没考虑
- 落地性差：开发者拿着这个文档还是写不了代码

**建议：**
- 下一轮（v1.11）不要加新概念了，就做一件事：**把现有的概念说清楚、写具体**
- 所有表都写 Schema，所有接口都签名，所有流程都有步骤，所有错误都有预案
- 目标：从"概念设计"走向"可落地的设计"

- 行为洞察深度：23/30
- 表驱动深度：19/25
- 事件驱动纯度：14/20
- 架构清晰度：13/15
- 前后端一体：7/10

**评价：第10轮是认知澄清轮，把之前说错的话说对了，这是进步。但"说对话"只是第一步，"说具体话"才是更难的挑战。架构设计不是写散文，是写工程说明书——精确、完整、可落地，才是硬道理。**
