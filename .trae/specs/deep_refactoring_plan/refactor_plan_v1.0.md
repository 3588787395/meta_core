# 股票池引擎重构规划 v1.0

> 文档版本：v1.0
> 创建日期：2026-07-01
> 状态：规划中

---

## 1. 重构目标

### 1.1 一句话目标

**把 3500 行的"大泥球"引擎，重构成 4 张核心运行时表 + 8 张核心配置表驱动的、不超过 800 行的简洁引擎。**

### 1.2 量化目标

| 指标 | 现状 | 目标 | 减少比例 |
|------|------|------|---------|
| engine.py 代码行数 | 3504 行 | ≤ 800 行 | ≥ 77% |
| 核心循环函数行数 | ~500 行 | ≤ 150 行 | ≥ 70% |
| 运行时表数量 | 29 张 | 4 张核心 | ≥ 86% |
| 核心配置表数量 | 50+ 张（引擎直接依赖） | 8 张 | ≥ 84% |
| 空转性能（水位线不变） | 全量遍历计算 | 直接返回（≈0） | ≥ 100x |
| 单条边触发性能 | 全量遍历 | 只算该边 | ≥ 10x |
| 全量计算性能 | 基准 | ≥ 5x | ≥ 5x |

### 1.3 非目标（什么不做）

- **不改变用户可见行为**：所有现有股票池模板必须 100% 兼容，输出结果完全一致
- **不新增功能**：重构期间不加新功能，只简化和整理
- **不重构公式引擎**：FormulaRouter 保持现状，只调整调用方式
- **不重构 UI 框架**：前端 editor.js 只做必要的对齐，不大改
- **不替换数据源**：数据推送接口保持不变
- **不重构 XML 导入导出**：converters 保持现状

## 2. 核心原则

### 2.1 表驱动原则

**逻辑隐含于表结构，差异显示于表内容。**

不是把 if-else 搬进 JSON，而是找到正交维度，用组合表达多样性。

- 时间触发：8 种 starttype × 3 种 cxtype = 24 种组合，用 11 条规则覆盖
- 过滤条件：6 种 nset × 10 种 noperate = 60 种组合，用 16 个函数覆盖
- 传播模式：3 种模式 = 3 条记录
- 节点角色：5 种角色 = 5 条行为定义

**判断标准：新增一种同类功能，只需要加一条表记录，不需要改引擎代码。**

### 2.2 数据驱动原则

**数据变了才计算，不变不算。**

核心机制：`latest_tick_ts` 时间水位线。

- 水位线没涨 → 所有 K 线数据不变 → 所有公式结果不变 → 所有过滤结果不变 → 什么都不用算
- 节点股票没变 → 该节点的出边不用检查
- 边的时间条件没到 → 即使源节点脏也不执行

**判断标准：水位线不变时，引擎开销为 0（不进入核心循环）。**

### 2.3 事件驱动原则

**过滤完成触发目标节点更新和预警事件。**

不是轮询所有节点，而是脏标记沿边传播：

```
数据更新 → 源节点脏 → 出边检查 → 执行 → 目标节点脏 → 目标出边检查 → ...
```

事件在状态变化时实时生成，不是 tick 末统一差分：

- 入池事件：股票进入目标节点时立即生成
- 出池事件：股票离开节点时立即生成
- 预警事件：目标节点变化时立即检查规则

### 2.4 前端后端一体原则

**拓扑与综合设置表格一致，流程与执行顺序一致。**

- 后端：`edge_order` 列表 = 执行顺序
- 前端：综合设置表格 = 执行顺序的可视化
- 前端：拓扑画布 = 连接关系的可视化
- 调整执行顺序：前端拖拽 → 写回 `edge.params._order` → 后端重新编译

**判断标准：用户在综合设置里看到的顺序，就是实际执行的顺序。**

### 3.4 核心流程（从数据到事件的完整路径）

```
1. 数据更新入口
   └─ tick_table.update(tick_data)
      ├─ 写 latest_tick[code] = new_bar
      ├─ 计算全量 hash
      ├─ hash 没变 → 返回 False（什么都不做）
      └─ hash 变了 → latest_tick_ts = now()，返回 True

2. 脏标记
   └─ 水位线涨了 → 所有源节点标记为"数据脏"

3. 边遍历（按 edge_order 顺序）
   └─ 对每条边 eid：
      ├─ 源节点脏吗？（数据脏 OR 股票脏）
      │  └─ 不脏 → skip
      ├─ 时间条件满足吗？
      │  └─ 不满足 → skip
      └─ 执行边：
         ├─ 条件边 → filter 过滤
         ├─ 无条件边 → 直接 propagate
         ├─ propagate 写入目标节点
         ├─ 目标节点股票变了吗？
         │  ├─ 没变 → 不标记
         │  └─ 变了 → 目标节点标记为"股票脏"
         └─ 生成事件（角色表驱动）

4. 清脏标记
   └─ 所有节点的数据脏标记清除（股票脏保留到下轮？）

5. 事件输出
   └─ 返回 events 列表（入池/出池/预警/信号）
```

## 4. 现有问题诊断

### 4.1 问题一：运行前与运行时混淆

**表现：**
- 每 tick 都重算拓扑序、重解析边参数、重找端点
- engine.py 里混杂着配置解析、规格编译、运行时逻辑
- CompiledSchedule 存在但没被充分利用，很多信息运行时还在重复计算

**影响：**
- 性能浪费：每 tick 都在做运行前就能做完的事
- 代码混乱：编译逻辑和运行逻辑搅在一起，难以理解和修改
- bug 隐患：重复计算可能不一致

**根因：**
- 没有明确的"编译期"概念，什么都塞进运行时
- 代码是渐进式累加的，没有统一的架构设计

### 4.2 问题二：数据更新与计算逻辑耦合

**表现：**
- 数据推送进来，直接触发全量计算
- 没有"水位线"概念，不知道数据到底变没变
- K 线合成和股票池计算搅在一起

**影响：**
- 性能差：即使数据没变（比如同一秒重复推送），也全量重算
- 逻辑混乱：数据层和计算层边界不清
- 难以优化：不知道哪里该缓存、哪里该跳过

**根因：**
- 没有把"数据变化"作为一等公民来管理
- 缺少统一的数据层抽象

### 4.3 问题三：三套 filter 各搞一套

**表现：**
- unconditional filter：一套逻辑
- conditional filter：一套逻辑
- formula_eval filter：又一套逻辑
- 三套逻辑有重叠，但各写各的

**影响：**
- 代码重复：相似的逻辑写三遍
- 行为不一致：三套逻辑可能有细微差别
- 难以维护：改一个要改三个地方

**根因：**
- 没有找到 filter 的统一抽象
- 没有用表驱动来组织不同类型的 filter

### 4.4 问题四：事件是 tick 末差分生成，不是实时

**表现：**
- 每个 tick 末，统一对比所有节点的新旧状态，生成事件
- 事件和触发它的边执行没有直接关联
- 预警检查也是统一做的

**影响：**
- 事件溯源困难：不知道哪个边触发了哪个事件
- 难以做增量处理：每次都是全量差分
- 不符合事件驱动的直觉：应该是"变化了就发事件"

**根因：**
- 架构上是"轮询"思维，不是"事件驱动"思维
- 脏标记机制不完善

### 4.5 问题五：拓扑与执行顺序混淆

**表现：**
- 用拓扑排序的结果当执行顺序
- 用户在综合设置里调整的顺序不生效
- 前端有拓扑视图、综合设置表格、执行顺序三种说法，后端只有一个拓扑序

**影响：**
- 用户困惑：为什么我调了顺序不生效？
- 前后端不一致：前端说的和后端做的不是一回事
- 策略无法按用户想要的顺序执行

**根因：**
- 没有区分"拓扑（连接关系）"和"执行顺序（处理次序）"两个概念
- 执行顺序没有作为一等公民来设计

## 6. 第一阶段详细计划

### 6.1 阶段目标

**核心引擎重构完成，行为与旧引擎 100% 等价，engine.py 从 3504 行降到 ≤ 800 行。**

### 6.2 任务分解

#### Task 1: 提取 tick_table（数据层独立）

**目标：** latest_tick 表独立封装，带 hash 比较和水位线机制

**做什么：**
- 新建 `core/runtime/tick_table.py`
- 封装 `TickTable` 类：
  - `data`: Dict[code → bar_dict]
  - `ts`: float（水位线时间戳）
  - `_hash`: str（全量数据 hash）
- `update(tick_data) → bool` 方法：
  - 更新 tick 数据
  - 计算新 hash
  - hash 没变 → 返回 False（水位线不涨）
  - hash 变了 → 更新 ts，返回 True
- 从 engine.py 中剥离所有 tick 数据管理逻辑

**影响文件：**
- 新增：`core/runtime/tick_table.py`
- 修改：`core/engine.py`（移除 tick 数据管理逻辑，改用 TickTable）

**验收标准：**
- 相同数据重复 update 返回 False，水位线不变
- 不同数据 update 返回 True，水位线递增
- hash 计算正确（修改任意字段 hash 变化）
- engine.py 减少约 200 行

**预估工作量：** 1 天

---

#### Task 2: 提取 compiler（编译期独立）

**目标：** pool_config → CompiledPool，运行前一次性编译

**做什么：**
- 新建 `core/compiler.py`
- 定义 `CompiledPool` 数据结构：
  - `nodes`: Dict[nid → node_dict]
  - `node_type`: Dict[nid → type_name]
  - `edges`: Dict[eid → edge_dict]
  - `edge_endpoints`: Dict[eid → (sid, tid)]
  - `edge_order`: List[eid]（**从 edge.params._order 读取，不是拓扑排序**）
  - `edge_type`: Dict[eid → 'conditional' | 'unconditional']
  - `edge_timing_spec`: Dict[eid → spec]
  - `edge_filter_spec`: Dict[eid → spec]
  - `edge_propagate_spec`: Dict[eid → spec]
  - `out_edges`: Dict[nid → List[eid]]
  - `in_edges`: Dict[nid → List[eid]]
  - `source_nodes`: List[nid]
  - `node_role`: Dict[nid → role_name]
- `compile(pool_config) → CompiledPool` 方法
- 从 engine.py 中剥离所有编译/解析逻辑

**影响文件：**
- 新增：`core/compiler.py`
- 修改：`core/engine.py`（移除编译逻辑，改用 CompiledPool）

**验收标准：**
- 执行顺序按 `_order` 排序，不是拓扑序
- 端点解析正确（sid/tid）
- 邻接表正确（out_edges/in_edges）
- 源节点判定正确（入度为 0）
- engine.py 减少约 400 行

**预估工作量：** 2 天

#### Task 3: 重写核心循环（脏标记 + 边遍历）

**目标：** 按执行顺序遍历，脏的才处理，水位线不变零计算

**做什么：**
- 重写 engine.py 核心循环
- 实现脏标记机制：
  - 数据脏：`_data_dirty: Set[nid]`（水位线涨了标记）
  - 股票脏：`_stock_dirty: Set[nid]`（节点股票变化标记）
  - `_is_node_dirty(nid) → bool`
  - `_mark_data_dirty(nid)`
  - `_mark_stock_dirty(nid)`
  - `_clear_all_dirty()`
- 实现 `run_once(compiled, now_ts) → events`：
  1. 按 `compiled.edge_order` 遍历边
  2. 检查源节点脏不脏 → 不脏 skip
  3. 检查时间条件 → 不满足 skip
  4. 执行边（filter + propagate）
  5. 目标节点股票变了 → 标记股票脏 + 生成事件
  6. 最后清脏标记
- engine.py 总行数 ≤ 800 行
- 核心循环函数 ≤ 150 行

**影响文件：**
- 修改：`core/engine.py`（核心循环重写）

**验收标准：**
- 水位线不变时，零计算（直接返回空 events）
- 源节点不脏时，出边不执行
- 时间条件不满足时，边不执行
- 执行顺序与 edge_order 一致
- 行为等价性：新旧引擎同样输入同样输出

## 附录：术语表

| 术语 | 定义 |
|------|------|
| 水位线 | `latest_tick_ts`，数据最新时间戳，水位线不涨则数据不变 |
| 脏标记 | 节点"需要重新处理"的标记，分数据脏和股票脏 |
| 数据脏 | 水位线涨了，该节点的输入数据可能变了 |
| 股票脏 | 节点的股票列表变了（入池/出池/TTL淘汰） |
| 执行顺序 | `edge_order`，边的处理次序，用户可在综合设置调整 |
| 拓扑 | 节点和边的连接关系图，用来画界面和校验 |
| CompiledPool | 编译后的股票池配置，运行时只读 |
| 表驱动 | 逻辑隐含于表结构，差异显示于表内容 |
