## 二、详细评审

### 2.1 行为洞察深度（22/30）

**做得好的（18分基础）：**
1. ✅ 抓到了"时间是股票计算的核心复杂度"——这是本质认知，比v1.12进步巨大
2. ✅ 意识到实盘边界场景（停牌/新股/异常）——不再活在理想世界
3. ✅ 三态逻辑处理不确定性——方向正确，股票池本质就是处理不确定性
4. ✅ 保守策略（宁可漏掉不错入）——符合选股系统的风险偏好

**深度不足的地方（扣8分）：**

**1. 没有区分"数据时间"和"系统时间"（-3分）**
这是实盘最核心的坑，没有之一。文档通篇讲时间模型，但只讲了周期，没讲两种时间的本质区别：
- **数据时间（data_time）：** 行情数据本身的时间戳（如K线的时间）
- **系统时间（system_time）：** 我们收到/处理这条数据的时间

实盘中这两个时间永远不一致：
- 网络延迟：数据时间 < 系统时间
- 数据补发：数据时间 << 系统时间（历史数据回补）
- 数据修正：数据时间 < 系统时间，但数据被修正了
- 周期确认：是按数据时间确认还是按系统时间确认？

文档中的"周期确认事件"默认两个时间是一致的，这在实盘中不成立。

**2. 停牌判断逻辑幼稚（-2分）**
```python
def is_suspended(bar):
    if bar.get('vol', 0) == 0 and bar.get('change_pct', 0) == 0:
        return True
```
这是典型的"用数据特征猜状态"，不是真正的停牌判断。真实情况：
- 停牌股票可能根本没有数据推送（bar 是 None，不是 vol=0）
- 开盘前集合竞价阶段 vol=0 但不是停牌
- 有些股票全天成交量极小但不是停牌
- 真正的停牌信息来自交易所公告，不是从行情数据猜

**3. 没有交易日历概念（-1分）**
周末、节假日怎么办？文档中的周期模型默认每天都有日线，这是不成立的。
- 周一的日线是周五之后的第一个交易日
- 节假日没有交易，没有K线
- 周期确认需要基于交易日历，不是自然日

**4. 没有复权/除权除息概念（-1分）**
真实股票数据最常见的"异常"就是除权除息：
- 价格突然跳空（-10%甚至更多）但不是异常
- 成交量突然放大但不是异常
- 指标计算需要前复权/后复权

文档把"价格跳空过大"当成异常，这是错误的——除权除息的跳空是正常的。

**5. 股票状态机没有转换规则（-1分）**
四种状态（normal/suspended/insufficient_data/abnormal）之间怎么转换？
- 停牌的股票复牌后，什么时候从 suspended 变回 normal？
- 数据不足的股票，什么时候变成 normal？
- 异常的股票，什么时候恢复正常？
- 状态转换需要确认机制吗？（比如连续3个tick正常才从abnormal变回normal）

文档只有状态定义，没有状态机转换规则。

### 2.2 表驱动深度（14/25）

**做得好的（10分基础）：**
1. ✅ L1分发表驱动定义清晰——用表替代if-else，诚实
2. ✅ L2/L3层级定义清晰——知道自己在哪里，要去哪里
3. ✅ 诚实承认"加新节点要写代码"——不再吹"改表不改代码"的牛

**核心问题：L2组合表驱动是"嘴上说说"（扣11分）**

**1. "部分实现"是夸大，实际是0个L2（-4分）**
文档说"operator_table + combine_table + propagate_table 可以组合出 filter"，但：
- 组合器在哪里？谁来组合？怎么组合？
- 三个表之间的组合接口是什么？
- 组合后的产物是什么？数据结构是什么？
- 现有的代码里有这个组合逻辑吗？

答案是：没有。只有三个独立的L1表，没有组合引擎。三个L1表放在一起不等于L2组合表驱动——就像一堆砖放在一起不等于房子。

**2. filter的组合模型不成立（-3分）**
文档说 `filter = 指标 × 比较算子 × 集合运算`，这个模型有问题：
- 真实的filter是一棵树，不是笛卡尔积
- 比如：(MA5 > 10 AND VOL > 1000万) OR (MACD金叉)
- 这是 `OR(AND(GT(MA5, 10), GT(VOL, 1000万)), MACD_CROSS)`
- 不是简单的"指标×算子×运算"三元组

L2组合表驱动需要的是**表达式树的表驱动表示**，不是三个表的笛卡尔积。

**3. 没有L2组合引擎的设计（-2分）**
L2组合表驱动的核心不是有几张表，而是有一个**组合引擎**：
- 输入：组合配置（来自表）
- 输出：可执行的行为
- 引擎本身是通用的，不需要为新组合写代码

文档完全没有这个组合引擎的设计——没有接口、没有数据结构、没有执行流程。

**4. node_type_table拆成4张表仍是L1（-2分）**
把1张L1表拆成4张L1表，还是L1。正交拆分是架构改进，但不是表驱动层级的提升。
- 文档把"正交拆分"和"L2组合"混为一谈了
- 4张表都是分发表，都是L1
- L2需要的是"组合"，不是"拆分"

**做得好的（7分基础）：**
1. ✅ 表的职责比v1.12清晰
2. ✅ 分层概念更清楚
3. ✅ 有表清单和读写时机

**边界模糊的地方（扣5分）：**

**1. node_behavior_table vs edge_behavior_table 边界不清（-2分）**
`trigger_mode`（data_driven/time_driven）放在 `edge_behavior_table` 里，但：
- 触发模式是边的行为吗？还是边的属性？

这个边界没划清。

- 为什么不统一成"事件触发"？数据变化是事件，周期确认也是事件
- 两种触发模式下，边的执行逻辑有多少是重复的？
- 统一的事件模型 vs 分开的执行路径，哪个更好？

文档没有讲清楚这个架构选择。

**4. 三态逻辑的实现位置不明确（-1分）**
三态逻辑（True/False/None）在哪里实现？

- 还是在集合运算层（combine_table的运算处理三态）？
- 还是在propagate层处理？

文档说"edge_compare_results存三态"，但三态的传播规则、运算规则在哪个层面实现，没有明确归属。

## 三、16条具体改进建议

### P0级（必须改，否则下一轮不通过）

**1. 区分数据时间和系统时间，这是实盘的基石**
- 给每个数据项加上 data_time 和 receive_time 两个时间戳
- 周期确认基于 data_time，不是系统时间
- 明确"乱序数据"（迟到的数据）的处理策略
- 这是时间模型的第一性问题，不解决的话时间模型都是空中楼阁

**2. L2组合表驱动：要么做出来，要么诚实说没做**
- 现在的"部分L2"是自欺欺人
- 要么真正设计出组合引擎（组合器接口、数据结构、执行流程）
- 要么老实承认"目前只有L1，L2是未来目标，本轮不做"
- 不要用"部分实现"这种模糊的说法包装

**3. 设计真正的停牌检测机制，不要从行情数据猜**
- 停牌信息应该来自数据源的主动通知（如果有的话）
- 或者基于"多久没收到数据"来判断（比如连续N个tick没有数据 = 疑似停牌）
- 要区分"停牌"和"数据源断了"两种情况
- vol=0且change_pct=0的判断是错的，删掉

**4. 引入交易日历，周期模型不能基于自然日**
- 定义 trading_calendar 表/模块
- 周期确认、TTL计算、时间偏移都要基于交易日历
- 周末、节假日不产生K线
- 这是时间模型的必要组成部分，不是可选的

**5. 明确4张表的正交边界，消除交叉**
- `trigger_mode` 从 edge_behavior_table 移出来，单独放 schedule_table
- `name` 的归属要明确：如果是显示用就移到 ui_table，如果是标识符就改名叫 type_name
- 每张表的"变化原因"要可枚举——改X只能改Y表
- 写一个"正交性验证矩阵"：改每个字段会影响什么维度

### P1级（重要，建议本轮改）

**6. 设计股票状态机，明确状态转换规则**
- 画状态转换图：normal ↔ suspended, normal ↔ insufficient_data, normal ↔ abnormal
- 每个转换的触发条件是什么？
- 转换需要确认吗？（比如连续3个tick正常才从abnormal变回normal）
- 状态转换要发事件吗？

**7. 补充除权除息处理，不要把正常跳空当异常**
- 异常检测规则里，要排除除权除息的情况
- 或者在数据层就做复权处理
- 价格跳空的异常阈值，要考虑除权除息的影响

**8. 统一事件模型：数据变化和周期确认都是事件**
- 不要把时间驱动和数据驱动分成两条完全独立的执行路径
- 统一成"事件驱动"：数据变化事件、周期确认事件、TTL过期事件...
- 边的执行逻辑是统一的，只是触发事件不同
- 这样可以减少代码重复，架构更清晰

**9. 明确三态逻辑的实现层次和传播规则**
- 三态是从哪一层产生的？（比较层）
- 三态在哪一层运算？（集合运算层）
- 三态在哪一层被消费？（propagate层的保守策略）
- 每一层对三态的处理规则要写清楚
- 画一个三态传播的数据流图

**10. 补充精确的数据结构定义**
- 每张表的字段类型、取值范围、默认值
- 每个核心数据结构（period_data, stock_status等）的精确格式
- 函数的输入输出类型
- 伪代码要细化到能直接转成代码的程度

### P2级（优化，下一轮再改）

**11. 设计filter的表达式树模型，替代笛卡尔积模型**
- filter = 表达式树，节点是算子/运算/指标
- 支持任意嵌套的AND/OR/NOT
- 支持排名、TopN等集合操作
- 这才是真正的L2组合表驱动的基础

**12. 补充错误处理策略**
- 数据拉取失败：重试？降级？告警？
- 公式计算异常：返回None？跳过？记录日志？
- 状态转换异常：保持原状态？强制转换？
- 定义错误码和错误处理流程

**13. 补充性能设计**
- 估算各表的内存占用
- 定义性能指标（延迟、吞吐量）
- 识别性能瓶颈点
- 设计优化策略（缓存、批量、增量）

**14. 设计可观测性**
- 怎么知道系统运行正常？
- 关键指标：处理延迟、股票状态分布、触发次数...
- 日志策略：什么级别、什么内容
- 监控告警：什么情况告警、怎么告警

**15. 设计测试策略**
- 单元测试：每个表、每个handler
- 集成测试：端到端的股票池运行
- 边界测试：停牌、新股、异常数据
- 性能测试：5000只股票的延迟
- 怎么验证时间模型的正确性？

**16. 补充回测场景的时间模型**
- 回测时，数据时间和系统时间是一致的（按节奏回放）
- 实盘时，两个时间不一致
- 时间模型要同时支持回测和实盘两种模式
- 回测模式下，周期确认怎么模拟？

## 四、3条最深刻洞见

### 洞见1：时间是股票计算的核心复杂度
**原文位置：** 2.1节
> "股票计算的核心复杂度就是时间"

这句话说得非常准。股票池系统90%的坑都在时间上：多周期、延迟、乱序、周期边界、未完成K线... 能意识到这一点，说明架构师开始摸到股票系统的本质了。之前的版本完全忽略时间，现在把时间模型作为核心，这是认知上的巨大进步。

### 洞见2：股票池本质是处理不确定性
**原文位置：** 4.2-4.4节
三态逻辑（True/False/None）+ 保守策略（不确定的不入池），这个组合非常准。股票池不是做确定性计算的，是在不确定的信息中做保守决策。能从"二态逻辑"升级到"三态逻辑"，说明理解了选股系统的本质——不是找"对的股票"，而是排除"明显不对的股票"。

### 洞见3：表驱动有层级，不是非黑即白
**原文位置：** 1.2节
L1（分发）→ L2（组合）→ L3（DSL）的三层级定义非常清晰。很多人一谈表驱动就是"改表不改代码"，但实际上表驱动是逐步演进的。能诚实地定位自己在L1，并规划向L2演进，这比吹牛逼说自己是"真正表驱动"要难得多，也有价值得多。

## 五、3条最肤浅理解

### 肤浅1：停牌 = vol=0且change_pct=0
**原文位置：** 7.3节 `is_suspended` 函数
这是典型的"从数据特征反推状态"的新手思维。停牌是一个事实状态，不是数据特征。真正的停牌信息来自交易所公告，不是从行情数据猜的。用vol=0判断停牌，会把"开盘前集合竞价"、"数据源断了"、"成交量极小"等多种情况误判为停牌。

**更深刻的理解应该是：** 停牌是一个独立的状态维度，有自己的信息来源和确认机制。行情数据只是辅助验证，不是判断依据。

### 肤浅2：filter = 指标 × 比较算子 × 集合运算
**原文位置：** 1.5节
这个笛卡尔积模型太简单了，只能表达最简单的filter（单指标单条件）。真实的filter是任意嵌套的表达式树：`(A AND B) OR (C AND NOT D)`，还有排名、TopN、窗口计算等复杂操作。用"三个表笛卡尔积"定义L2组合表驱动，说明对"组合"的理解还停留在表面。

**更深刻的理解应该是：** L2组合表驱动的核心是**组合引擎**——一个能解释执行配置化表达式树的通用引擎。表是原料，引擎是工厂，没有工厂，原料只是原料。

### 肤浅3：价格跳空过大 = 数据异常
**原文位置：** 4.7节
"价格跳空过大（比如涨跌幅 > 20%，但不是新股）"被列为异常类型，这是完全错误的。除权除息会导致价格跳空-10%甚至更多，这是正常的，不是异常。把正常的除权除息当成异常数据过滤掉，会导致指标计算错误。

**更深刻的理解应该是：** 数据异常的判断需要上下文（除权除息信息、停牌信息、历史数据分布等），不能只看单根K线的特征。

## 七、总结

v1.13是一个**进步明显但仍有大量包装**的版本。

**最大的亮点是诚实化**——不再吹"加新节点不改代码"的牛，明确定义L1/L2/L3三层级，知道自己在哪里。这是架构成熟的标志。

**最大的问题是"嘴上说说"的成分还是太多**——L2组合表驱动只有概念没有设计、时间模型只抓到了表面、正交拆分有交叉、实盘边界处理只有框架。架构设计不是列概念清单，是要把每个概念的细节、边界、交互都想清楚。

**给架构师的一句话：** 诚实化是好的开始，但不要停留在"诚实的概念罗列"。下一步要从"有什么概念"深入到"每个概念怎么工作"。宁可少做几个概念，也要把每个概念做深做透。
