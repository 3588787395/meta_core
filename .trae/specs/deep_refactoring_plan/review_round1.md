## 二、流式执行真实性审查

### 2.1 声称修正了什么

v1.1 声称从"批处理"改为"流式串行"：
- 每条边执行完立即更新节点、立即发事件、立即标记脏
- 后一条边能看到前一条边的执行结果
- 脏标记同 tick 内流式级联

### 2.2 实际做到了什么

| 维度 | 是否真正流式 | 证据 | 说明 |
|------|-------------|------|------|
| **事件发射** | ✅ 是 | §7.2 伪代码第 435-436 行：`self._emit_events(edge_events)` 在 for 循环内部 | 每条边执行完立即发，不攒到最后，这点改到位了 |
| **脏标记传播** | ✅ 是 | §7.2 伪代码第 424-426 行：`_mark_stock_dirty(tid)` 在 for 循环内部 | 前边弄脏的节点，后边能立即看到，这点也对 |
| **节点更新** | ✅ 是 | `_execute_edge` 直接修改 `node_stocks[tid]` | 目标节点立即更新，后边的边能读到最新状态 |
| **边触发检查** | ❌ 不是 | §7.2 伪代码第 405 行：`for eid in compiled.edge_order:` 遍历所有边 | 还是全量遍历 + 条件跳过，本质是轮询不是事件驱动 |

### 2.3 结论

**流式执行改了一半——"输出"是流式的，"输入"还是轮询的。**

事件发射和脏传播确实流式化了，这是进步。但边的触发机制还是"每 tick 遍历所有边检查脏标记"，这和批处理时代的区别只是"以前批量发事件，现在逐条发"，触发逻辑的本质没变。

## 三、表驱动真实性审查

### 3.1 声称的表驱动

> "逻辑在表结构里，差异在表内容里"  
> "8 + 3 = 11 条规则覆盖 24 种组合"  
> "6 个求值器 + 10 个比较器 = 60 种筛选方式"

### 3.2 逐项检查

| 表 | 表驱动等级 | 评价 |
|----|-----------|------|
| `timing.json` | ⭐⭐⭐⭐ 真表驱动 | 8 种 start × 3 种 cx 的正交分解，用组合表达多样性，这是真表驱动的味道 |
| `filter_specs.json` | ⭐⭐⭐ 半表驱动 | 6 个求值器 + 10 个比较器的思路对，但"求值器"和"比较器"本身是函数引用，表只是在选函数，不是在表达逻辑 |
| `propagate_modes.json` | ⭐⭐ dispatch 表 | 3 条记录对应 3 个 if，换了个存储方式而已，不是表驱动的本质 |
| `node_roles.json` | ⭐⭐ dispatch 表 | 5 种角色对应 5 套行为，同样是用表做选择，逻辑还是在代码里 |
| 其余 11 张表 | ⭐ 配置表 | 纯配置数据，谈不上"表驱动"——任何系统都有配置 |

### 3.3 核心问题：表驱动 ≠ 把 if 搬进 JSON

文档自己也说了"表驱动不是把 if 搬进 JSON"，但实际大部分表就是这么做的。

**真表驱动的标准**：表的数据本身就是逻辑，改变表的内容就能改变行为，不需要改代码。  
**当前的状态**：表只是用来"选函数"，函数本身才是逻辑。加一种新的传播模式？还是要写代码。加一种新角色？还是要写代码。

timing.json 之所以亮眼，是因为它找到了**正交维度**，用组合爆炸来代替枚举。但这种思路只在 timing 上贯彻了，其他地方都没跟上。

### 3.4 结论

**表驱动是"部分达标"。** timing 和 filter 的正交分解是亮点，但整体深度不够，大部分表只是"配置化的 dispatch"，离"逻辑在表结构里"还有不小差距。给 17/25 分。

## 四、分项详细评审

### 4.1 行为洞察深度（22/30）

**做得好的（+22分）：**

1. **水位线洞察（+8）**："最新 tick 时间不变 → 所有 K 线数据不变 → 不需重新计算"——这是真懂行的人才能说出来的话。抓住了股票池性能优化的命门。
2. **执行顺序=行顺序（+7）**：意识到"综合设置表格行顺序就是执行顺序"，而不是拓扑排序——这说明真的去理解了用户交互和系统行为的关系，不是闭门造车。
3. **流式级联（+7）**：理解了"同 tick 内前边影响后边"的级联效应，这比把股票池当成 DAG 批量计算的认知要深刻一层。

**扣分项（-8分）：**

1. **两种脏标记混为一谈（-3）**："数据脏"（水位线涨了，全局的）和"股票脏"（节点股票变了，沿边传播的）是完全不同性质的东西，混在一个 `_is_node_dirty()` 里，迟早出 bug。
2. **TTL 淘汰时机缺失（-2）**：TTL 淘汰也会导致节点股票变化，也会触发级联。但 TTL 什么时候执行？每条边后？所有边后？独立 tick？完全没说。
3. **无条件边触发机制模糊（-2）**："无条件边：源节点股票变了 → 立即 propagate"——"立即"是同 tick 内立即还是跨 tick？无条件边要不要走时间触发检查？自相矛盾。
4. **循环依赖问题未提及（-1）**：用户可以定义执行顺序，如果边1: A→B，边2: B→A，流式级联会不会导致同 tick 内死循环？没讨论。

### 4.2 表驱动深度（17/25）

**做得好的（+17分）：**

1. **timing 的正交分解（+7）**：8 种 starttype + 3 种 cxtype = 24 种组合，而不是 24 个 if。这是真表驱动的范式。
2. **filter 的求值器/比较器分离（+6）**：6 个求值器 × 10 个比较器 = 60 种组合，思路是对的。
3. **核心表收敛到 8 张（+4）**：从 50+ 张收敛到 8 张核心表，这个减法做得不错。

**扣分项（-8分）：**

1. **大部分表是 dispatch 表（-3）**：propagate_modes、node_roles 等表本质是"用 key 选函数"，逻辑还是在代码里。加一种新模式还是要改代码。
2. **表的 schema 定义不完整（-2）**：只说了表名和作用，没说每条记录有什么字段、什么类型、约束是什么。照着做会发现很多细节没定义。
3. **表驱动的层次单一（-2）**：只有"函数选择"这一层表驱动，没有上升到"流程编排"和"状态机"层面的表驱动。
4. **配置表 vs 驱动表混淆（-1）**：把 16 张配置表都说成"表驱动"，其实大部分是纯配置，任何系统都有。

### 4.3 事件驱动纯度（11/20）

**做得好的（+11分）：**

1. **事件发射流式化（+5）**：每条边执行完立即发事件，事件顺序 = 执行顺序，这是对的。
2. **脏标记驱动触发（+4）**：用脏标记来决定要不要执行边，而不是每 tick 全量计算——虽然还是遍历，但至少有触发条件。
3. **水位线作为全局触发源（+2）**：水位线不涨就不进入核心循环，这个设计是事件驱动思路。

**扣分项（-9分）：**

1. **边触发本质是轮询（-5）**：`for eid in compiled.edge_order:` 遍历所有边，然后检查脏标记。这就是加了条件的轮询，不是事件驱动。真正的事件驱动应该是：节点变脏时，把它的出边加入待执行队列，然后处理队列。
2. **run_once 是"拉"不是"推"（-2）**：外部调用 `run_once()` 来"拉取"一次执行，而不是事件"推送"触发执行。这是轮询架构的典型特征。
3. **时间触发不是事件驱动（-2）**：时间触发是通过每 tick 检查实现的，不是定时器事件驱动。虽然对于股票池这个场景可以接受，但从"事件驱动纯度"角度要扣分。

**做得好的（+13分）：**

3. **核心循环极薄的目标（+3）**：engine.py ≤ 800 行，核心循环 ≤ 150 行——这个目标感很好。
4. **三模式统一（+2）**：实盘/回放/仿真的差异归结为三个插件，核心引擎统一——这个抽象是对的。

**扣分项（-2分）：**

1. **核心循环职责还是偏重（-1）**：run_once 里既要遍历边、检查脏、执行边、发事件、清脏——虽然代码量可能不大，但职责不止一个。

## 五、15 条具体改进建议（按优先级排序）

### P0 级（不做就会卡壳）

**1. 彻底分离"数据脏"和"股票脏"两种脏标记**

两种脏的性质、传播方式、清除时机完全不同：
- **数据脏**（data_dirty）：水位线涨了导致的，全局的，影响所有条件边的 filter 结果。清除时机：tick 结束时统一清。
- **股票脏**（stock_dirty）：节点股票变化导致的，局部的，沿边传播。清除时机：边的出边都处理完后清（或者 tick 结束统一清，取决于级联策略）。

不能用一个 `_is_node_dirty()` 混着检查。建议每个节点维护两个时间戳：`data_ts` 和 `stock_ts`，分别对应两种脏。

**2. TTL 淘汰的执行时机必须明确**

TTL 淘汰也会改变节点股票列表，也会触发级联。建议：
- TTL 检查放在**每条边执行之前**（作为源节点的"预处理"），这样淘汰导致的变化能被同 tick 内后续边感知到
- 或者放在 tick 最开头，作为独立的一步
- 不能含糊其辞

**3. 无条件边的触发机制重新定义**

当前描述自相矛盾：一会儿说"无条件边不需要时间条件"，一会儿三要素里又有时间触发。建议明确定义：
- 无条件边：源节点股票脏 → 立即 propagate（不检查时间条件，也不检查数据脏）
- 条件边：源节点脏（股票脏或数据脏）**且**时间到 → filter + propagate
- 无条件边的"立即"是同 tick 内立即，通过流式级联实现

**4. 循环依赖的防护机制**

用户定义的执行顺序可能形成 A→B→A 的级联环。流式执行下，同一次 tick 内会不会无限循环？
- 方案A：每条边同 tick 内最多执行一次（用 `_executed_edges` 集合记录）
- 方案B：级联深度设上限（比如最多 10 层）
- 方案C：完全信任用户，不做防护（不推荐）

建议选方案A，简单可靠。

### P1 级（影响架构质量）

**5. 边触发从"遍历检查"改为"脏节点出边队列"，实现真正的事件驱动**

当前：
```python
for eid in compiled.edge_order:    # 遍历所有边
    if not _is_node_dirty(sid):    # 检查脏不脏
        continue
    # 执行边
```

建议：
```python
# 节点变脏时，把它的出边加入待执行队列
def _on_node_dirty(nid):
    for eid in compiled.out_edges[nid]:
        if eid not in pending_edges:
            pending_edges.append(eid)  # 按执行顺序插入

# 然后处理队列（按执行顺序）
while pending_edges:
    eid = pending_edges.pop(0)  # 按执行顺序取
    # 执行边
    # 如果目标节点变脏，自动触发 _on_node_dirty
```

这样才是真正的事件驱动——节点变脏是事件，事件驱动边的执行。不需要遍历所有边。

**6. 明确事件的结构和去重规则**

同一只股票同 tick 内可能多次入池出池：
- 发多条事件？还是合并成一条最终状态？
- 入池事件包含哪些字段？（code、node_id、timestamp、reason/edge_id？）
- 出池事件包含哪些字段？
- 交易信号和事件是什么关系？

这些不定义清楚，事件驱动就是空中楼阁。

**7. 水位线粒度从全局改为 per-code 或 per-node**

当前全局水位线的问题：一只股票更新了，所有源节点都变脏，所有条件边都要重新 filter。
建议：
- `latest_tick` 维护 per-code 的时间戳
- 节点的"数据脏"判定：节点内是否有股票的 tick 时间 > 上次处理时间
- 这样大部分时候只有少数节点变脏，性能更好

当然这会增加复杂度，需要权衡。但至少要讨论这个选项，而不是直接默认全局。

**8. filter 结果缓存机制**

同一条边、同一个源节点、数据没变（水位线没涨），filter 结果应该一样。
建议增加 `filter_cache[edge_id][node_snapshot_hash]` 缓存。
水位线没涨时，直接命中缓存，跳过 filter 计算。

这和水位线优化是互补的——水位线优化是"数据没变就不算"，filter 缓存是"同样的数据输入结果不变"。

**9. 节点股票的数据结构从 List 改为 Set/Dict**

股票池操作大量使用：
- 判断某只股票是否在节点中（O(1) vs O(n)）
- 差集/并集计算（入池出池事件）
- 去重

用 List 效率太低，应该用 `Dict[code → stock_info]` 或者至少 `Set[code]`。
而且"stock"到底是什么？是字符串代码还是包含字段的对象？必须明确定义。

**10. 表驱动从"函数选择"上升到"流程编排"**

当前表驱动只在"选哪个函数"层面。建议更进一步：
- 边的执行流程本身也可以表驱动：步骤1检查脏、步骤2检查时间、步骤3 filter、步骤4 propagate、步骤5发事件
- 不同类型的边（条件/无条件/预警/...）有不同的流程步骤
- 用表来定义流程步骤，而不是用 if/else 硬编码

这样才是"逻辑在表结构里"。

### P2 级（锦上添花）

**11. 增加边执行的幂等性保证**

同一条边、同样的输入，多次执行结果应该一样。
这是分布式系统和可测试性的基础。
建议：每条边的执行是纯函数，输入是（源节点状态、tick数据），输出是（目标节点变化、事件）。

**12. 定义 CompiledPool 的完整 schema**

当前 CompiledPool 的定义太随意，像随手写的注释。
建议用类型定义或者 JSON Schema 正式定义每个字段的类型、含义、约束。
这是编译器和运行时的契约，不能含糊。

**13. 事件的顺序保证和因果关系**

流式事件的顺序很重要。需要明确：
- 同 tick 内的事件顺序 = 边的执行顺序
- 不同 tick 的事件顺序 = tick 顺序
- 事件之间的因果关系怎么表达（比如事件B是事件A的后续）

**14. 增加"执行轨迹"的可观测性设计**

流式执行、级联触发，调试起来会很痛苦。
建议在架构层面就考虑可观测性：
- 每条边的执行日志（触发原因、执行结果、变化量）
- 脏标记传播轨迹
- 事件生成链路

没有好的可观测性，流式级联就是黑盒，出问题查不出来。

**15. 表驱动的测试策略**

表驱动的好处是可以用数据来测试。
建议：为每张核心表设计"表驱动测试"——输入一组表数据，验证输出行为。
而不是为每种场景写单独的测试用例。

## 六、3 条最深刻的洞见

### 洞见1：水位线是整个系统的灵魂

> "最新 tick 时间不变 → 所有 K 线数据不变 → 不需重新计算"

这不是一个简单的性能优化技巧，这是对股票池计算本质的深刻理解。
股票池的所有计算最终都依赖行情数据，而行情数据的变化是单调递增的（时间只往前走）。
抓住了水位线，就抓住了整个系统的性能支点和逻辑简化支点。

这个洞见的价值，怎么强调都不过分。v1.1 把它放在最开头，是对的。

### 洞见2：执行顺序 = 综合设置表格行顺序，而不是拓扑序

大部分人会想当然地认为"DAG 的执行顺序就是拓扑序"。
但这份设计意识到：
- 拓扑是结构，执行顺序是行为
- 用户拖拽调整行顺序，就是在调整执行顺序
- 不同顺序结果不同（因为流式级联），所以必须让用户控制

这个洞见说明设计者真的去理解了用户交互和系统行为的关系，不是从教科书出发，而是从实际出发。

### 洞见3：流式级联——同 tick 内前边影响后边

"批处理"思维下，所有边的输入是同一个状态，输出是另一个状态，中间过程不可见。
但这份设计意识到，股票池的实际运行是流式的：
- 边1把股票从A移到B
- 边2从B里选股票
- 边2能看到边1的执行结果

这是对"股票池到底怎么运行"的更精细认知。
不是 DAG 分层计算，而是串行流水线。
这个认知直接导致了执行顺序必须用户可控的结论——因为顺序影响结果。

## 七、3 条最肤浅的理解

### 肤浅1：事件驱动 = 流式发射事件

文档通篇说"事件驱动"，但核心循环还是 `for eid in compiled.edge_order:` 遍历所有边。
事件发射是流式的没错，但边的触发本身还是轮询。

**真正的事件驱动是：事件源产生事件，事件驱动计算，计算产生新的事件。**
不是"定时遍历一下，有活就干，没活就歇着"。

脏标记已经是事件的雏形了（节点变脏是事件），但没有贯彻到底——
节点变脏应该触发"把出边加入待执行队列"，而不是"下一次遍历的时候检查到"。

### 肤浅2：表驱动 = 把配置放 JSON 里

文档自己也说了"表驱动不是把 if 搬进 JSON"，但实际大部分表就是这么做的。

propagate_modes 有 3 条记录 = 3 个 if，换了个存储方式而已。
node_roles 有 5 种角色 = 5 套行为，逻辑还是在代码里。

**真表驱动的检验标准：加一种新行为，要不要改代码？**
如果还是要改代码，那就是 dispatch 表，不是表驱动。

timing.json 是真表驱动的范例——加一种新的 starttype 组合？不需要改代码，只要加一条规则（如果规则引擎够通用的话）。
但这个范式没有推广到其他地方。

### 肤浅3：两种脏标记混为一谈

"数据脏"和"股票脏"是完全不同性质的东西：
- 数据脏：全局的、由外部输入引起的、影响所有依赖数据的计算
- 股票脏：局部的、由内部传播引起的、只影响出边的触发

混在一个 `_is_node_dirty()` 里，看似简化了，实则埋了坑。
比如：一个节点数据脏了，它的无条件边要不要触发？按文档说"无条件边不需要数据更新"，
但数据脏也是脏，`_is_node_dirty()` 返回 true，那无条件边也会触发——这就不对了。

把不同性质的东西混在一起，用同一个概念表达，是思考不深入的典型表现。

## 九、总结评价

**这份设计的优点：方向对、味道正、有几个亮眼的洞见。**

- 水位线、执行顺序=行顺序、流式级联——这三个洞见说明设计者真的在思考股票池的本质，不是在做表面文章。
- 运行前/运行时分离、数据层/计算层分离、核心极薄的目标——这些架构原则都是对的。
- v1.1 对流式执行的修正是有进步的，至少事件发射和脏传播改对了。

**这份设计的问题：深度不够、细节缺失、名不副实。**

- "事件驱动"喊得响，但边触发还是轮询——换皮不换骨。
- "表驱动"喊得响，但大部分表只是 dispatch 表——换个存储方式而已。
- 关键行为（TTL、无条件边、循环依赖）要么没定义，要么定义模糊。
- 两种脏标记混为一谈——核心概念没理清楚。

**71 分的含义**：及格了，方向对，有亮点，但离"可以照着做的架构设计"还差一到两层深度。
如果下一轮能把 P0 的三个问题解决掉，分数可以提到 85+。
如果还是只改表面文字不改核心机制，那就是原地踏步。
