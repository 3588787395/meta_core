## 二、3个最严重的问题（P0级，不解决不能开工）

### 🔴 问题1：伪事件驱动 —— 核心循环本质仍是轮询

**问题描述**：
设计声称"事件驱动而非轮询包装"，但从 §2.2 事件流和 §3.1 完整事件链看，核心执行路径是：

```
TimerTickEvent → 按 execution_order 遍历所有边 → 检查触发条件 → 满足则执行
```

这**不是事件驱动**，这是**带条件门控的轮询**。真正的事件驱动应该是：
- 源节点股票变化 → 直接触发下游边 → 级联传播
- 数据变化 → 标记所有依赖行情的条件节点为脏 → 仅这些节点重新计算

**当前设计的问题**：
- 每 tick 都要遍历所有边（O(n) 检查），这是轮询的典型特征
- `NodeStockChangedEvent` 发布后，下游不是立即被触发，而是要等到下一次 `TimerTickEvent` 遍历到它
- 事件只是"置标记"，真正的驱动还是时钟 tick

**风险**：
- 性能天花板低（边数多了每 tick 开销线性增长）
- 延迟高（股票入池要等到下一个 tick 才往下游传）
- 架构名不副实，后续维护者会困惑

---

### 🔴 问题2：执行顺序与拓扑关系混乱 —— "一次遍历即可"是错误结论

**问题描述**：
§5.4 第4点说："因为 execution_order 是按拓扑深度排序的（默认情况），上游先执行，下游后执行，一次遍历即可完成所有级联更新。"

**这是根本性错误**。理由：

1. **execution_order 是边的顺序，不是节点的顺序**。一条边的目标节点变脏后，该节点的出边可能在 execution_order 中排在当前边之前。一次遍历必然漏掉。

2. **设计自相矛盾**：§4.2 说"脏标记沿拓扑向下传播，直到没有下游"，但 §5.4 又说"一次遍历即可"。如果一次遍历就行，何来"传播"？

3. **用户自定义顺序更危险**：如果用户把下游边排在上游边前面，一次遍历必然导致上游变化当 tick 不生效，要等下一个 tick。这叫"一 tick 延迟"，但设计文档只字未提。

**风险**：
- 行为与旧引擎不一致（旧引擎是多轮传播直到稳定）
- 级联更新场景下数据不一致
- 调试困难（某些边执行了某些没执行，原因是顺序问题）

---

### 🔴 问题3：等价性保证只有口号 —— 没有系统的验证策略

**问题描述**：
§7.3 第三层"行为等价"只说了三句话：
- 编写行为等价性测试（已有 test_event_driven_equivalence.py）
- 同一 pool_config + 同一输入数据 → 同一输出结果
- 所有现有 simtests / tests 必须全部通过

**问题在于**：
1. **测试粒度太粗**：现有测试只测"最终股票列表是否一致"，不测中间状态、不测时序、不测事件顺序。
2. **等价维度缺失**：
   - 时序等价：同一股票在同一时间点入池/出池吗？
   - 事件等价：事件的顺序、数量、内容完全一致吗？
   - 边界等价：空池、满池、单股票、多分支汇合等边界情况一致吗？
   - 性能等价：最坏情况性能不劣化吗？
3. **迁移路径过于乐观**：v1.0 就要"新架构并行运行"，但没有灰度策略、没有回滚机制、没有监控指标。
4. **"行为等价"定义不清**：是严格等价（每一行输出都一样）还是可接受差异（功能一致但事件顺序可能不同）？

**风险**：
- 重构完发现行为不一致，回滚成本极高
- 线上出问题无法快速定位是新架构还是旧架构的问题
- 用户的股票池迁移过来结果不一样，引发信任危机

## 三、3个最好的地方（亮点，值得肯定）

### ✅ 亮点1：面向对象拆分方向正确，上帝类拆解思路清晰

从 3500+ 行的 `MetaEngine` 上帝类拆分为 Node/Edge/EventBus/Topology/DirtyManager 等协作类，方向完全正确。类层次控制在 2 层以内，符合设计原则。继承关系（SourceNode/StatePoolNode/ConditionNode 继承 Node）合理，是真正的"is-a"关系。

### ✅ 亮点2：数据驱动增量计算思路对，三级跳过机制有价值

L1（数据哈希）→ L2（节点脏）→ L3（边触发）→ L4（公式缓存）的四级跳过机制，思路清晰且分层合理。特别是 L1 的 `data_hash` 检查，能在数据未变化时直接跳过所有计算，这是真正的性能优化点。

### ✅ 亮点3：向后兼容策略务实，三层兼容框架合理

API 兼容（Facade 模式）+ 数据结构兼容（pool_config 不变）+ 行为等价（测试保证）的三层兼容框架，思路正确。特别是保留 `MetaEngine` 类名作 Facade、内部委托给 `EventDrivenEngine` 的方案，风险可控。迁移路径（v1.0 并行 → v1.1 默认 → v1.2 移除）也符合渐进式重构的最佳实践。

## 四、15条具体改进建议（按优先级排序）

### P0 级（不解决不能开工）

#### 1. 【事件驱动】实现真正的级联触发，消除核心循环的全量遍历

**现状**：每 tick 遍历所有边检查条件（轮询）。  
**改进**：改为"事件级联 + 待处理队列"模式：

```python
# 核心循环
event_queue = deque()

def on_node_stock_changed(event):
    # 源节点变了，把它的所有出边加入待执行队列
    for edge in topology.get_out_edges(event.node_id):
        if edge.should_trigger(now_ts):
            event_queue.append(edge)

def process_queue():
    while event_queue:
        edge = event_queue.popleft()
        result = edge.execute()
        # 如果目标节点变了，继续把目标的出边加入队列
        if result.target_changed:
            for out_edge in topology.get_out_edges(result.target_id):
                if out_edge.should_trigger(now_ts):
                    event_queue.append(out_edge)
```

**好处**：
- 只有变化的路径才会被执行（真正的事件驱动）
- 不需要遍历所有边
- 级联传播自动完成（不需要"一次遍历"的错误假设）

---

#### 2. 【执行顺序】明确 execution_order 的语义，放弃"一次遍历"

**现状**：execution_order 既是用户期望顺序，又要满足拓扑，还要一次遍历搞定，三者不可兼得。  
**改进**：

- **编译期**：验证用户指定的执行顺序，检查是否满足拓扑依赖。如果不满足，**强制重排为拓扑序**并告警，而不是"尽量贴近用户顺序"。
- **运行期**：采用"拓扑序 + 待执行队列"模式，execution_order 只影响**同一深度边的相对顺序**，不影响整体传播路径。
- **文档中明确**：级联更新是多轮的，直到没有新的变化为止。execution_order 保证的是"当多条边都可执行时，先执行哪条"，而不是"每条边只检查一次"。

---

#### 3. 【等价性】定义严格的等价性标准，建立对比测试框架

**改进**：
- **等价维度清单**：列出 10+ 个等价维度（最终状态、事件序列、时序、边界行为、错误处理等），每个维度有明确的通过标准。
- **Oracle 测试框架**：用旧引擎作为 Oracle，新引擎作为待测，对同一输入逐 tick 对比输出。
- **模糊测试**：随机生成 1000+ 个 pool_config + 行情序列，自动对比新旧引擎输出。
- **性能基准**：建立性能基线，新架构在 100 条边、1000 只股票的场景下，性能必须 ≥ 旧引擎的 90%。

---

### P1 级（严重影响质量，开工前应明确）

#### 4. 【面向对象】ConditionNode 的职责过重，应拆分

**现状**：ConditionNode 既要做公式计算、又要做缓存、还要做结果对比。  
**改进**：
- 抽出 `FilterEvaluator` 类负责过滤计算
- 抽出 `FilterCache` 类负责缓存管理
- ConditionNode 只做"协调"：接收输入 → 调用 evaluator → 更新输出 → 发布事件

理由：单一职责原则。公式计算逻辑本身就很复杂（nset 分派、双引擎切换、公式路由），塞在 Node 类里会变成新的上帝类。

---

#### 5. 【面向对象】Edge 的职责模糊，"时机门控"和"执行逻辑"应分离

**现状**：Edge 既要管时机门控（should_trigger），又要管执行逻辑（execute），还要管触发条件判断（is_data_triggered / is_node_triggered）。  
**改进**：
- 抽出 `TimingGate` 类专门负责时机门控（starttype × cxtype 的 24 种组合）
- Edge 只负责"连接 + 触发判定 + 执行流转"
- `TimingGate` 是 Edge 的一个组件（组合优于继承）

理由：时机门控本身就是一个独立的复杂度源，24 种组合的逻辑 deserve 自己的类。

---

#### 6. 【数据驱动】脏标记粒度太粗，应支持"哪些股票变了"的增量

**现状**：脏标记只有布尔值（脏/不脏），计算时要拿全部股票重新算。  
**改进**：
- `NodeStockChangedEvent` 已经带了 `added` 和 `removed`，但 ConditionNode 没用上
- ConditionNode 应该支持**增量过滤**：只对新增的股票执行过滤，对移除的股票直接从输出中移除
- 公式计算支持单只股票的增量评估（如果公式引擎支持的话）

理由：对于 1000 只股票的备选池，每次只有 1-2 只变化时，全量重算浪费 99% 的算力。

---

#### 7. 【事件驱动】事件同步发布的死循环风险未提及

**现状**：§2.3 说"事件同步发布"，但没说怎么防止循环。  
**改进**：
- 增加**循环检测机制**：在事件传播路径中记录已访问的节点/边，如果再次遇到则终止
- 或者采用**深度标记**：每个事件带一个传播深度，超过阈值（如 100）就报错
- 编译期必须检测环，运行期也要有兜底防护

理由：如果拓扑有环（比如 A→B→C→A），同步事件发布直接栈溢出。

---

#### 8. 【表驱动】12张表还是太多，应进一步收敛为"元数据表"

**现状**：从 50+ 砍到 12 张，但很多表的内容其实可以合并。  
**改进**：
- `edge_semantics.json` + `edge_strategies.json` → 合并为 `edge_types.json`（边类型定义）
- `timing.json` → 直接编译成代码（24种组合是固定的，不需要运行时查表）
- `pool_roles.json` + `tdx_psatt.json` → 合并为 `node_types.json`（节点类型定义）
- 目标：核心配置表 ≤ 5 张，其他都是"编译期用一次"的配置

理由：表驱动的精髓是"用数据表达变化"，不是"什么都塞到 JSON 里"。固定不变的东西直接写代码更清晰。

---

#### 9. 【等价性】明确"行为等价"的精确定义 —— 是严格等价还是功能等价？

**改进**：
- 如果是**严格等价**：事件顺序、股票顺序、时间戳都必须完全一致（难度极高，可能做不到）
- 如果是**功能等价**：最终状态一致，中间过程可以有差异（合理目标）
- 建议定义为**功能等价 + 关键时序等价**：
  - 最终股票列表一致（必须）
  - 股票入池/出池的 tick 级时序一致（必须）
  - 同一 tick 内的事件顺序可以不同（可接受）

---

### P2 级（重要但可以迭代完善）

#### 10. 【面向对象】SinkNode 是多余的类，直接用 StatePoolNode 加标记即可

**现状**：SinkNode 继承 Node，但没有任何新增属性和方法。  
**改进**：删除 SinkNode 类，用 `StatePoolNode(is_sink=True)` 或角色标记替代。

理由：继承的代价是增加类层次复杂度。如果没有差异化行为，就不值得一个子类。

---

#### 11. 【事件驱动】事件类型太多，很多可以合并

**现状**：设计了 10+ 种事件类型，但很多事件的携带数据高度重叠。  
**改进**：
- `PoolEnterEvent` + `PoolExitEvent` → 合并为 `PoolChangedEvent`（带 direction 字段）
- `EdgeFiredEvent` + `EdgeExecutedEvent` → 考虑合并（或者只保留 Executed，Fired 只是内部状态）
- `DataUpdatedEvent` + `BarDataUpdatedEvent` → 统一为 `DataEvent`（带 data_type 字段）

理由：事件类型越多，订阅/发布的管理成本越高。够用就好，不是越多越清晰。

---

#### 12. 【数据驱动】公式缓存的键设计有问题 —— 股票列表不应该直接进哈希

**现状**：cache_key = md5(formula_id + symbols + period + bar_data_hash)  
**问题**：
- symbols 是列表，顺序不同但内容相同会导致缓存不命中
- 1000 只股票的列表做 md5 本身就有开销
- 股票列表变化频繁的话，缓存基本无用

**改进**：
- symbols 用 frozenset 或排序后的 tuple，保证顺序不影响哈希
- 考虑按单只股票缓存（如果公式是逐股票计算的）
- 明确缓存的适用场景：适合大股票池 + 少量变化 + 计算昂贵的公式

---

#### 13. 【可实施性】缺少错误处理和异常恢复策略

**现状**：整个设计文档没有提到异常处理。  
**改进**：
- 单条边执行失败怎么办？终止整个 tick 还是跳过继续？
- 公式计算抛出异常怎么处理？（当前引擎是跳过该股票还是整个边失败？）
- 事件总线的异常传播策略？（一个订阅者抛异常，其他还执行吗？）
- 引擎启动失败的降级策略？

理由：生产系统的 80% 代码是处理异常情况的。设计文档不提，开发时就会各写各的。

---

#### 14. 【可实施性】缺少可观测性设计 —— 怎么调试和监控？

**现状**：没有提到日志、指标、追踪。  
**改进**：
- 日志策略：每个关键路径打什么日志？日志级别？
- 性能指标：tick 耗时、边执行次数、缓存命中率、事件队列长度
- 调试工具：怎么 dump 当前所有节点状态？怎么跟踪某只股票的流动路径？
- 事件溯源：能不能重放某段时间的事件序列来复现问题？

理由：事件驱动系统的调试难度远高于过程式系统。没有可观测性，出问题就是黑盒。

---

#### 15. 【向后兼容】`__getattr__` 代理属性是危险的，应明确列出兼容属性清单

**现状**：§7.3 说"所有现有属性通过 `__getattr__` 代理到新对象"。  
**问题**：
- `__getattr__` 是黑魔法，会掩盖真正的 AttributeError
- 不知道哪些属性是外部依赖的，哪些可以安全删除
- 性能开销（每次属性访问都走一遍 `__getattr__`）

**改进**：
- 做一次全面的属性使用审计（搜索所有调用点）
- 明确列出需要兼容的属性清单（白名单）
- 用 `@property` 显式代理，而不是 `__getattr__` 全量代理
- 给被代理的属性加 deprecation warning

## 五、总体评价

### 这个设计达到什么水平？

**结论：方向正确，细节不足，处于"有想法但还没想透"的阶段。**

打个比方：就像画了一张建筑的效果图，外立面看着挺漂亮，但结构图、水电图、消防图都还没画。施工队拿着这张图没法开工——或者说，硬开工的话，盖到一半肯定要返工。

**具体来说**：

| 方面 | 水平 | 说明 |
|------|------|------|
| 愿景/方向 | ★★★★☆ | 面向对象、事件驱动、数据驱动、表驱动，这四个方向都对 |
| 核心机制设计 | ★★☆☆☆ | 伪事件驱动、执行顺序逻辑错误、脏标记传播不严谨 |
| 细节完备度 | ★★☆☆☆ | 错误处理、可观测性、边界情况，大量留白 |
| 可落地性 | ★★☆☆☆ | 开发拿到这个设计会有 100 个问题要问 |
| 风险可控性 | ★★☆☆☆ | 等价性保证薄弱，向后兼容靠黑魔法 |

**与现有代码的关系**：
现有代码（`engine.py`）虽然是过程式的，但**经过了大量测试和实战验证，细节是完备的**。新设计如果只是"结构好看了但细节没跟上"，最终结果可能是：代码更优雅了，但 bug 更多了、性能更差了、行为不一致了。

**重构的正确顺序应该是**：
1. 先把现有逻辑的所有细节摸清楚（包括边界情况、异常处理、历史包袱）
2. 再考虑怎么用新架构重写
3. 最后才是类怎么分、事件怎么发

目前的设计给人的感觉是：**第1步（理解现状）做得不够，第2步（架构设计）跳得太快**。

## 七、给设计者的几句话

1. **不要为了"模式"而模式**。事件驱动不是目的，解决问题才是。如果轮询更简单更高效，就用轮询。关键是要诚实，不要把轮询包装成事件驱动。

2. **细节里有魔鬼**。3500 行的 `MetaEngine` 之所以有 3500 行，不是因为前人不会写面向对象，而是因为**业务本身就有 3500 行的复杂度**。重构不是把 3500 行分成 10 个文件就完事了，而是要真正理解这 3500 行里每一行存在的理由。

3. **先写测试，再写代码**。建议 v1.1 先把等价性测试框架搭起来，用测试驱动重构。这样每改一步都有反馈，不用等到最后才发现"哎，行为不一样"。

4. **小步快跑，不要一口吃成胖子**。四个"驱动"（面向对象、事件驱动、数据驱动、表驱动）不要同时上。建议先做面向对象拆分（验证等价），再做数据驱动优化（验证性能），最后再考虑是不是真的需要事件驱动。
