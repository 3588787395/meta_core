## 二、3个最严重的问题（P0级，开工前必须修复）

### 🔴 问题1：Pending 合并方案有致命逻辑漏洞 — 处理后未清空变更集

**问题描述**：

文档 §2.5 给出了 Pending 合并的完整方案，但出队处理逻辑存在严重 bug。

**当前设计的处理流程**：
```
事件出队 → 从 pending 取 added/removed → 处理下游边 → clear_dirty() → info.has_event_in_queue = False
```

**问题**：处理完后，`info.added` 和 `info.removed` **没有被清空**。

这意味着什么？假设以下序列：
1. 变化1：added={1,2} → 创建 pending，事件入队
2. 事件出队，开始处理（从 pending 取 added={1,2}）
3. 变化2：added={3} → 合并到 pending，此时 pending.added = {1,2,3}
4. 事件处理完成，has_event_in_queue = False，但 added/removed 不清空
5. 变化3：added={4} → 合并到 pending，此时 pending.added = {1,2,3,4}（因为基准还是 {1,2,3}）
6. 因为 has_event_in_queue=False，变化3触发新事件入队
7. 新事件处理时，取 added={1,2,3,4} → **{1,2,3} 被重复处理了！**

**更严重的场景**：如果变化2是 removed={1}，那么合并后 pending.added = {2,3}，pending.removed = {}。但步骤7处理时，下游边看到的是"新增了 {2,3}"，但实际上 1 已经在之前被处理过了（作为新增）。这次应该是"移除1，新增3"，而不是"新增2,3"。

**根本原因**：pending 中的 added/removed 应该是"自上次处理以来的累计变更"，处理完后必须清空，作为下一轮的起点。当前设计只重置了 has_event_in_queue，没有重置 added/removed。

**正确的逻辑应该是**：
```python
# 事件出队时，"消费" pending 中的变更
def dequeue_node_change(node_id):
    info = _pending_node_changes[node_id]
    added = info.added.copy()
    removed = info.removed.copy()
    version = info.version
    # 清空，为下一轮累计做准备
    info.added.clear()
    info.removed.clear()
    info.has_event_in_queue = False
    return version, added, removed
```

**影响**：如果不修，会导致股票被重复添加/移除，状态不一致，等价性测试必然失败。这是**阻断性 bug**。

### 🔴 问题2：SourceNode / 外部数据更新的事件触发流程完全缺失

**问题描述**：

文档详细描述了 Edge.execute() 如何调用 `enqueue_node_changed()`，但对于**源节点（SourceNode）如何被外部数据触发更新**，完全没有说明。

**缺失的关键环节**：

1. **谁调用 SourceNode.update_stocks()？**
   - 是 Engine.on_data() 直接调用吗？
   - 还是 SourceNode 自己订阅数据更新？
   - MarketSourceNode 和 CandidatePoolNode 的触发方式一样吗？

2. **谁调用 enqueue_node_changed()？**
   - Node.update_stocks() 本身不发布事件（§1.1 明确说"不直接发布事件，由调用方发布"）
   - 那 SourceNode 更新后，谁负责把 NodeStockChangedEvent 入队？
   - 是 Engine.on_data() 调用 update_stocks 后，再手动调用 enqueue_node_changed？

3. **DataUpdatedEvent 的处理逻辑不完整**：
   - §2.2 说 DataUpdatedEvent 的处理动作是"更新全局 bar_data；置 data_dirty=True；把所有依赖行情的条件边加入执行队列"
   - 但是！**源节点（MarketSourceNode）的数据也更新了，为什么不需要触发源节点的 NodeStockChangedEvent？**
   - 还是说源节点的股票集是不变的，变化的只是股票的价格数据？

**这里有一个根本性的概念混淆**：

- Node.stocks 是"股票代码集合"（哪些股票在池子里）
- 行情数据更新（价格、成交量等）是"股票的属性变化"，不是"股票集合变化"

如果 SourceNode 的股票集合（备选池）是固定的，那它确实不需要 NodeStockChangedEvent。但如果备选池会动态变化（比如根据指数成分股调整），那它也需要触发事件。

**文档没有澄清这一点**，导致整个"数据到达 → 源节点 → 下游传播"的链条是断的。

**更严重的是**：FilterEvaluator.evaluate() 需要行情数据来计算过滤条件。数据更新后，即使股票集合没变，过滤结果也可能变。那数据更新后，是怎么触发条件边重新执行的？

文档 §2.2 说 DataUpdatedHandler 会"把所有依赖行情的条件边加入执行队列"——这个是对的。但这条路径和 NodeStockChangedEvent 的路径是什么关系？两条路径会重复触发吗？

**影响**：开工后，开发人员不知道数据更新的完整链路，各写各的，必然导致数据流混乱。

### 🔴 问题3：EngineContext 职责边界模糊，有上帝对象膨胀风险

**问题描述**：

文档 §1.5 定义了 EngineContext 的属性，数一下有 9 个：
```
now_ts, bar_time, bar_data, data_dirty,  // per-tick 状态（4个）
formula_router, data_query, config_store, event_queue, metrics  // 稳定服务（5个）
```

**问题**：把"每 tick 变化的状态"和"稳定的服务依赖"混在一个对象里，会导致：

1. **生命周期不一致**：
   - event_queue、formula_router 是引擎级的，和引擎同生命周期
   - now_ts、bar_data 是 tick 级的，每个 tick 都变
   - 混在一起，谁来更新 tick 级状态？什么时候更新？更新时需要同步吗？

2. **可测试性下降**：
   - 测试一个只需要 formula_router 的方法，也得构造一个完整的 EngineContext，填 9 个属性
   - 虽然 Python 的 mock 灵活，但设计上是有问题的

3. **违反接口隔离原则**：
   - Node.update_stocks() 只需要 event_queue，但拿到的是整个 context
   - FilterEvaluator.evaluate() 需要 formula_router 和 data_query，但也拿到了 event_queue
   - 等于每个组件都拿到了它不应该拿到的东西

4. **膨胀风险**：
   - 现在 9 个，未来可能 15 个、20 个
   - 什么东西都往 context 里塞，最后变成垃圾筐

**建议的拆分方式**：
```
EngineServices（引擎级，稳定）:
  - event_queue
  - formula_router
  - data_query
  - config_store
  - metrics

TickContext（tick 级，每 tick 重建）:
  - now_ts
  - bar_time
  - bar_data
  - data_dirty
```

或者用组合模式：`EngineContext.services` 和 `EngineContext.tick`。

**文档的辩解**：§10.2 说方案 B 的缺点是"有上帝对象的风险"，但认为"通过约定可以避免"。

**我的评价**：约定是靠不住的。如果架构上不做隔离，代码写着写着 context 就会膨胀。这不是人的问题，是系统的自然演化趋势。

**影响**：现在可能还能接受，但 v2.0 之前必须拆分，否则代码会越来越难维护。

## 三、3个最大的进步（亮点，值得肯定）

### ✅ 亮点1：扇入去重机制设计完整，思考深度足够

上一轮 P0-1 提的 NodeStockChangedEvent 去重问题，这一轮给出了非常完整的方案。

**值得肯定的点**：

1. **方案对比充分**：§2.4 对比了事件合并、脏标记去重、时间戳版本号三种方案，分析了各自的优缺点，不是拍脑袋选的。

2. **自我推翻的勇气**：文档中能看到思考的轨迹——从"墓碑标记"到"变更集合并"到"pending 中维护总变更集"，作者不断推翻自己的初稿，逐步逼近最优解。这种**迭代式思考**是架构师的核心能力。

3. **变更集合并的数学推导**：§2.5 中推导了合并公式：
   ```
   merged_added = (info.added - new_removed) | (new_added - info.removed)
   merged_removed = (info.removed - new_added) | (new_removed - info.added)
   ```
   并且用具体例子验证了正确性。这个严谨性在很多设计文档中是看不到的。

4. **正确性论证意识**：§2.5 最后有"正确性论证"一节，尝试证明合并方案与逐次处理等价。虽然论证还有漏洞（见问题6），但有这个意识就很好。

5. **极端场景考虑**：§2.6 考虑了并发乱序、变更集抵消、大扇入等极端场景，说明作者不是只考虑 happy path。

**美中不足**：有逻辑 bug（见问题1），但整体思路是对的，修一下就能用。

### ✅ 亮点2：增量过滤 No-Go 决策理性，懂得克制

上一轮 P0-2 提的增量过滤问题，这一轮没有硬着头皮上，而是做出了"v1.x 不做，v2.0 再优化"的决策。

**为什么这是进步？**

1. **正确性优先于性能**：对于金融交易系统，正确性是底线。性能优化可以以后做，但 correctness bug 可能导致真金白银的损失。

2. **懂得做减法**：很多设计师的通病是"什么都想做，什么都想做好"，结果哪个都做不好。v1.2 主动砍掉增量过滤，把精力集中在核心功能的正确性上，这是**架构克制力**的体现。

3. **分析深度到位**：虽然决定不做，但 §4.2 还是深入分析了增量过滤的适用边界、判断标准、甚至给出了正确性证明。这说明不是"因为难所以不做"，而是"想清楚了，现在不做更合适"。

4. **为 v2.0 铺路**：§4.2 的分析不是白费的，v2.0 做增量过滤时可以直接用。

这种"先做对，再做快"的思路，比那种"一步到位"的冒进方案靠谱得多。

### ✅ 亮点3：依赖注入方案明确，责任边界更清晰

上一轮 P0-3 提的事件发布依赖传递问题，这一轮也给出了明确方案。

**进步体现在**：

1. **四种方案对比**：§10.2 对比了构造函数注入、上下文对象、全局单例、回调注册四种方案，每个方案都从耦合度、可测试性、性能、复杂度、灵活性五个维度评价。分析框架很完整。

2. **选择理由充分**：不是因为"上下文对象最流行"而选，而是从依赖集中管理、构造函数简洁、易于扩展、可测试性好等角度论证。

3. **责任边界明确**：§10.5 用表格列出了每个组件可以发布哪些事件，谁可以发、谁不可以发，一目了然。

4. **方法签名约定**：§10.6 约定了"纯计算方法不需要 context，有副作用的方法才需要 context"，并且 context 统一放在最后一个参数。这个约定很重要，能避免 context 滥用。

5. **Node 移除 _event_queue**：Node 不再直接持有 EventQueue，改为通过方法参数传递，职责更单一了。

虽然 EngineContext 有膨胀风险（见问题3），但方案选择本身是合理的，比 v1.1 的混乱局面强太多。

### P1 级（严重影响质量，开发前应明确）

#### 4. 【等价性】扇入合并的等价性论证需要更严谨

§2.5 的正确性论证只考虑了"无状态过滤 + 复制式流转"的情况，但没有考虑：

- **状态性过滤**：如果 FilterEvaluator 有内部状态（比如历史值、累计值），合并后只执行一次 vs 执行多次，状态更新次数不一样，结果可能不同
- **移动式流转**：如果边的逻辑是"移动"而非"复制"（股票从源节点移到目标节点），合并后结果一样吗？
- **入池/出池事件**：同一 tick 内先入后出，旧引擎产生两个事件，新引擎合并后可能不产生事件，这等价吗？

建议：
- 明确等价性的定义是"状态级等价"还是"事件级等价"
- 如果是状态级，确认外部系统都不依赖"同一 tick 内的事件数量"
- 如果有依赖，要么保证事件级等价，要么修改外部系统

### P2 级（重要但可以迭代完善）

#### 9. 【等价性】明确"变更集抵消"场景的等价性

§2.6 场景2提到"变更集抵消后，事件还是会出队，处理时发现没有净变化，下游边不会执行"。

但问题是：**旧引擎在这种情况下会执行下游边吗？**

如果旧引擎是"每次变化都触发"，那：
- 旧引擎：变化1 → 下游执行 → 变化2 → 下游再执行

如果下游边有副作用（比如触发告警、写入日志），那行为不一致。

建议明确：这种情况算不算等价？如果算，为什么？如果不算，怎么处理？

#### 11. 【可观测性】补充 metrics 的具体指标清单

建议列出：
- 事件队列相关：入队数、出队数、去重数、队列长度峰值
- 节点相关：变化次数、脏标记时间
- 边相关：执行次数、过滤通过率
- 性能相关：每 tick 处理时间、事件平均处理时间

#### 12. 【设计文档】减少"同 v1.1"的省略，保持文档自包含

v1.2 文档中有大量"同 v1.1，本节不重复"的省略（§2.1、§4.4、第5章、第6章、第7章、8.2~8.6、第9章）。

这样做的问题是：
- 读者需要同时打开 v1.1 和 v1.2 两个文档才能看到完整设计
- 如果 v1.1 和 v1.2 有不一致的地方，读者会困惑
- 不利于新人上手

建议：
- 至少每个章节保留一个**摘要**，说明这一章的核心内容
- 或者 v1.2 是一个完整的文档，v1.1 的内容也包含进来，用变更标记标注
- 设计文档应该是自包含的，不应该让读者去翻旧版本

**我的建议：可以开工，但不是"全面开工"，而是"先搭骨架，边搭边验证"。**

具体的开工策略：

## 七、给设计者的几句话

1. **进步稳，继续保持**。从 55.7 → 78.4 → 82.25，每次都有实打实的进步，不是靠嘴炮提升的。三大 P0 问题都有了深入的思考和方案，这非常好。

2. **细节决定成败**。整体框架都对了，但 Pending 合并的那个 bug 是真的致命——如果不修，整个系统的正确性就没保障。架构设计不能只看大方向，关键路径上的每个细节都要抠到位。

3. **不要怕写"笨办法"**。全量扫描不是什么丢人的事，Pending 合并搞复杂了反而容易出 bug。有时候最笨的办法反而是最可靠的。v1.x 的目标是"正确、可验证"，不是"最优雅"。

4. **文档要自包含**。"同 v1.x，本节不重复"看似高效，实则增加了读者的认知负担。设计文档是给人看的，不是给自己备忘的。每个版本都应该是完整可读的。

5. **可以开始写代码了**。不用等 v1.3 评审。先把 P0 bug 修了，然后从 EventQueue 和 EventLoop 开始写，写一行测一行。代码和设计应该是共振的——写代码会反过来帮你完善设计。
