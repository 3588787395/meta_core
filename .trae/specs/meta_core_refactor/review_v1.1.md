## 二、3个最严重的问题（P0/P1级，开工前应明确）

### 🔴 问题1：NodeStockChangedEvent 缺少去重机制，重复事件可能导致级联放大

**问题描述**：
文档 §1.4 明确了 `EdgeExecuteEvent` 通过 `_pending_edges` 集合去重，但 **NodeStockChangedEvent 没有任何去重机制**。

考虑以下场景：
```
拓扑：A → edge1 → B
      A → edge2 → B
      B → edge3 → C
```

如果 A 节点变化，edge1 和 edge2 都会执行，且都可能导致 B 节点变化。这样会产生 **两个 NodeStockChangedEvent(B)** 先后入队。

后果：
1. **性能浪费**：B 的出边（edge3）被重复加入队列（虽然 EdgeExecuteEvent 有去重不会重复执行，但 NodeStockChangedEvent 的处理本身有开销）
2. **脏标记清除时机错误**：第一个 NodeChanged(B) 处理完后会清除 B 的脏标记，但此时 B 可能又被第二条边更新了（取决于执行顺序），脏标记状态不一致
3. **调试困难**：事件日志中大量重复事件，难以追踪真实变化

**更严重的场景**：扇入（10个上游→1个下游），一个 tick 内可能产生10个相同的 NodeStockChangedEvent。

**建议**：
- 增加 `_dirty_nodes` 集合（类似 `_pending_edges`），NodeStockChangedEvent 入队前去重
- 或者在 Node 内部维护"变更集"（added/removed），多次变更合并为一次事件
- 明确脏标记的语义：是"有变化待处理"还是"当前数据是脏的"

---

### 🔴 问题2：增量过滤的正确性没有严格论证，适用边界模糊

**问题描述**：
§4.3 提出了 L5 增量过滤："只有少数股票变化时，只计算变化的部分"。思路很好，但文档存在以下漏洞：

1. **适用条件判断缺失**：怎么判断一个公式是"逐股票计算的"？`nset=0/1/2` 是公式型，`nset=5` 是集合运算型——这个可以通过 dispatch.json 判断。但 `nset=3/4` 标量型呢？排名类公式（"涨幅前10"）呢？文档只说了"排名类、集合运算类不适用"，但没有给出**可执行的判断算法**。

2. **正确性论证缺失**：增量过滤（新增的算一下，移除的直接删）和全量过滤结果严格一致吗？考虑以下情况：
   - 公式引用了"池内股票数量"等聚合属性 → 增量计算错误
   - 公式有状态（比如历史值） → 增量计算可能漏更新状态
   - 股票从 A 池移到 B 池，同时触发两条边 → 增量和全量的中间状态是否一致？

3. **10%阈值拍脑袋**："变化股票占比 < 10% 时用增量"，这个 10% 没有任何依据。是性能拐点吗？是正确性边界吗？都没说。

**风险**：
- 增量过滤在某些边界情况下与全量计算结果不一致 → 等价性测试不通过
- 开发时不知道什么时候该用增量、什么时候该用全量 → 各写各的

**建议**：
- 给出**精确的增量过滤适用条件**（基于公式类型的可执行判断）
- 给出**正确性证明**或至少**不变量论证**：在什么条件下，增量计算 ≡ 全量计算
- 初始版本可以**先只做全量过滤**，增量过滤作为 v1.2 的优化项，不要在 v1.1 就上

---

### 🟠 问题3：事件发布的依赖传递不清晰，Node/Edge 如何拿到 EventQueue 引用？

**问题描述**：
文档中 Node 类有 `_event_queue` 属性（§1.1），但 Edge 类没有。然而：
- `Node.update_stocks()` 需要产生 `NodeStockChangedEvent` 并入队 → 需要 EventQueue 引用
- `Edge.execute()` 导致目标节点变化后，也需要产生事件 → 是 Edge 自己入队，还是通过 Node 的 update_stocks 间接入队？
- `TimingGate`、`FilterEvaluator` 这些组件需要发布事件吗？

更根本的问题是：**事件发布的责任边界在哪里？**

选项 A：Node 持有 EventQueue，所有事件通过 Node 发布
选项 B：EventLoop 持有 EventQueue，所有组件通过 EventLoop 发布
选项 C：EngineContext 持有 EventQueue，通过上下文传递

文档没有明确说明，开发时很可能出现"每个对象都传一份 event_queue"的混乱局面。

**建议**：
- 明确事件发布的统一入口（建议通过 EngineContext 传递，或采用 Mediator 模式）
- 画出事件发布的调用链图：谁产生事件 → 谁入队 → 谁消费
- Node 类中的 `_event_queue` 可以去掉，改为通过方法参数或上下文传递

## 三、3个最大的进步（亮点，值得肯定）

### ✅ 亮点1：真·事件驱动核心循环，从轮询到级联传播的质变

上一轮最核心的批评——"披着事件外衣的轮询"——在 v1.1 中得到了彻底解决。

**进步体现在**：
1. **EventQueue 成为心脏**：优先级队列 + 级联传播，事件驱动不再是口号
2. **级联传播模型正确**：节点变化 → 下游边入队 → 执行边 → 目标节点变化 → 继续传播，形成完整的闭环
3. **去重机制到位**：`_pending_edges` 集合防止同一条边重复入队
4. **正确性论证充分**：§3.3 用数学归纳法论证了级联传播的完整性和终止性（DAG 前提下）

特别是 §2.4 中对"NodeStockChangedEvent 优先级为什么比 EdgeExecuteEvent 低"的思考过程——作者自己提出疑问、自己推翻、自己重新论证——这种**自我质疑的严谨态度**非常值得肯定。虽然最终结论还可以再推敲，但这种思考方式是架构师必备的素质。

---

### ✅ 亮点2：执行顺序与拓扑的关系彻底澄清，两种方案对比后理性选择

上一轮第二大问题——"执行顺序与拓扑关系混乱，一次遍历是错误结论"——在 v1.1 中也得到了彻底解决。

**进步体现在**：
1. **概念清晰分离**："拓扑决定谁能影响谁，执行顺序决定同时都满足时先算谁"——一句话总结到位
2. **两种方案充分对比**：方案A（事件队列+优先级）vs 方案B（分轮次全量遍历），各有优缺点都列出来了
3. **选择理由充分**：不是因为"事件驱动更酷"而选A，而是从性能、可扩展性、优雅性三个维度论证
4. **编译期验证算法**：§5.6 给出了执行顺序验证的具体算法步骤

§5.4 用一个反例（用户把下游边排前面）证明了"一次遍历"的错误，论证过程清晰、有说服力。这才是设计文档应有的深度。

---

### ✅ 亮点3：等价性验证框架完整可操作，从口号到系统工程

上一轮第三大问题——"等价性只有口号"——在 v1.1 中变成了一套完整的方法论。

**进步体现在**：
1. **等价性定义精确**：明确了哪些必须一致（最终状态、tick级时序）、哪些可以不同（同tick内顺序），不是模糊的"行为一致"
2. **Oracle 对比框架**：旧引擎作基准、逐 tick 对比、多维度对比，可直接落地
3. **测试金字塔**：单元(100+) → 集成(50+) → E2E(1000+)，数量级合理
4. **模糊测试**：随机生成 + 自动最小化，思路正确
5. **四阶段迁移**：影子模式 → 小流量 → 大流量 → 全量替换，每个阶段有明确的准出标准
6. **回滚机制**：有触发条件、有回滚方式、有日志记录

特别是 §8.1 对"为什么这样定义等价性"的解释——"同一tick内的顺序不影响策略结果"——是经过业务思考的，不是拍脑袋的。

## 四、12条具体改进建议（按优先级排序）

### P0 级（开工前必须明确）

#### 1. 【事件驱动】补充 NodeStockChangedEvent 的去重机制

同"问题1"。明确：
- NodeStockChangedEvent 是否需要去重
- 去重的粒度（按 node_id 去重，还是按变化内容去重）
- 多次变化是合并为一次事件，还是保留多次但标记脏状态

#### 2. 【数据驱动】v1.1 先不上增量过滤，作为 v1.2 优化项

增量过滤看起来美好，但正确性边界模糊、实现复杂度高。建议：
- v1.1 只做全量过滤 + L1~L4 跳过机制
- 把增量过滤推迟到 v1.2，先保证功能正确，再做性能优化
- 如果一定要做，先给出严格的适用条件判断和正确性证明

#### 3. 【架构】明确事件发布的依赖传递方式

同"问题3"。明确：
- EventQueue 的引用从哪里来（构造注入？方法参数？全局上下文？）
- 哪些对象可以直接发布事件，哪些需要通过中间层
- 画出事件发布的调用链图

---

### P1 级（严重影响质量，开发前应明确）

#### 4. 【事件驱动】诚实面对"时钟/数据触发仍是全量扫描"的事实

文档声称"真·事件驱动"，但 §2.3 的流2（时钟tick）和流1（数据到达）本质上还是全量扫描：
- TimerTickHandler：遍历**所有** ConditionalEdge 的 TimingGate
- DataUpdatedHandler：把**所有**条件边加入执行队列

这不是"假"，但也不是"纯"事件驱动。建议：
- 文档中诚实说明这一点，不要过度营销"真·事件驱动"
- 可以考虑优化：TimingGate 自己注册到时间轮（Time Wheel），只有时机状态可能变化的 gate 才被检查

#### 5. 【执行顺序】明确"execution_order 违反拓扑约束"时的处理策略

§5.3 说"用户指定的顺序优先，但必须满足源节点深度 <= 目标节点深度，否则强制调整"。但：
- "强制调整"是怎么调整的？整体重排还是局部调整？
- 调整后的 execution_order 还和用户预期一致吗？
- 为什么不直接禁止用户指定违反拓扑的顺序？

建议：编译期如果检测到用户顺序违反拓扑依赖，**直接报错**，而不是"强制调整+警告"。强制调整可能导致用户预期之外的行为，报错更安全。

#### 6. 【等价性】讨论"事件顺序不一致"的外部风险

§8.1 说"同一 tick 内的事件顺序不要求"，但没有讨论风险：
- 外部系统（UI、交易信号处理器）是否依赖事件顺序？
- 如果旧引擎的事件顺序是 A→B→C，新引擎是 C→B→A，外部系统会不会出问题？
- 事件回调中如果有副作用（比如修改全局状态），顺序不同会不会导致结果不同？

建议：做一次外部调用点审计，检查是否有代码依赖事件顺序。如果有，要么保证顺序一致，要么修改外部代码。

#### 7. 【等价性】模糊测试的"自动最小化"说得太轻松

§8.4 说"如果发现差异，自动最小化复现用例"。但自动最小化（delta debugging）的实现复杂度很高，特别是对于 pool_config 这种结构化数据。

建议：
- v1.1 先不要求"自动最小化"，能记录失败用例就行
- 把"自动最小化"列为 v1.2 的优化项
- 或者用更简单的策略：二分法减少 tick 数、二分法减少边数

#### 8. 【面向对象】Node 类的 stocks 属性类型不一致

§1.1 中 Node.stocks 的类型是 `list[dict]`，但 §4.2 又用了 `frozenset` 做快照、§4.4 用 `frozenset(symbols)` 做缓存键。

问题：
- stocks 到底是 list 还是 set？
- 如果是 list，顺序有意义吗？
- 每次比较都要转 frozenset，性能开销考虑过吗？

建议：明确 stocks 的数据结构。如果顺序不重要，内部用 set/frozenset 存储，需要输出时再转 list。

---

### P2 级（重要但可以迭代完善）

#### 9. 【表驱动】dispatch.json 也可以考虑编译成代码

§6.2 保留了 dispatch.json 作为核心表，理由是"公式分派逻辑复杂且经常调整"。

但实际上，nset 的分派规则（0/1/2公式型，3/4标量型，5集合运算型）是 TDX 的固有属性，**不会经常变化**。经常调整的可能是"某个公式用哪个引擎"，那是 engines.json 的事。

建议：dispatch.json 的分派逻辑可以硬编码到 FormulaRouter 中，减少一张核心表。

#### 10. 【可观测性】调试工具只有功能列表，没有接口定义

§9.2 列出了5个调试工具（状态快照、单步执行、股票追踪、事件溯源、性能分析），但只有功能描述，没有接口定义。

建议：至少给出每个工具的方法签名和返回值结构，比如：
```python
def dump_state(self) -> dict:
    """返回所有节点、边、队列的状态快照"""

def step(self) -> Event:
    """执行一个事件，返回被处理的事件"""

def track_stock(self, code: str) -> List[TrackRecord]:
    """开启股票追踪，返回追踪记录列表"""
```

#### 11. 【错误处理】缺少"部分失败"的状态一致性保证

§9.1 说"单条边失败不影响整个 tick"，但没有讨论**部分失败后的状态一致性**：
- 一条边执行了一半（过滤做完了，流转没做完）失败了，目标节点是脏的还是干净的？
- 失败的边在下一个 tick 会重试吗？
- 怎么避免"部分成功部分失败"导致的状态不一致？

建议：明确边执行的原子性保证——要么全成功，要么全失败（目标节点状态回滚）。

#### 12. 【迁移策略】四阶段迁移的时间安排过于乐观

§8.6 中阶段0只要"连续运行7天无差异"，阶段1只要"连续运行3天"。对于金融交易系统来说，这个时间太短了：
- 7天可能连一个完整的交易周都覆盖不了（遇到节假日更少）
- 至少要覆盖一个完整的月度周期，最好覆盖一个季度
- 还要考虑特殊日子：财报季、交割日、极端行情日

建议：把各阶段的时间拉长，或者用"覆盖的场景数"而不是"天数"作为准出标准。

## 六、下一轮 P0 重点（v1.2 或开发过程中必须明确的问题）

### 🔥 P0-1：NodeStockChangedEvent 去重与脏标记语义

开工前必须明确的第一个问题。不解决的话，开发时每个人对脏标记的理解不一样，后期会有很多隐蔽 bug。

**交付物**：
- NodeStockChangedEvent 的去重策略

## 七、给设计者的几句话

1. **进步很大，继续保持**。从 55.7 到 78.4，这是实打实的进步。三大 P0 问题都不是敷衍了事，而是真正深入思考了。特别是能在文档中展示自己的思考过程（甚至自我推翻），这种能力比写出"完美设计"更重要。

2. **不要追求一步到位**。增量过滤、自动最小化、100% 事件驱动——这些都是好东西，但不用都塞在 v1.1 里。先把核心做对，再逐步优化。v1.1 的目标应该是"功能正确、可验证、可回滚"，而不是"所有优化都做完"。

3. **诚实是最好的架构**。时钟 tick 和数据到达时的全量扫描，不是什么丢人的事。系统中本来就有全局事件和局部事件之分。诚实地说清楚"哪些是事件驱动、哪些还是全量扫描"，比强行包装成"纯事件驱动"更能赢得信任。

4. **设计是迭代的，不是一次性的**。v1.0 → v1.1 是一次迭代，开发过程中还会有 v1.1.1、v1.1.2。不要试图在设计阶段把所有问题都想清楚——有些问题只有写了代码才会暴露。关键是要有快速反馈的机制（比如等价性测试）。

5. **下一轮可以开始写代码了**。不用等 v1.2 评审。先把测试框架搭起来，再实现核心骨架，边写边验证，遇到不清楚的地方再回头更新设计。设计和代码应该是共振的，而不是串行的。
