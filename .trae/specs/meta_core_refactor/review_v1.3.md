## 三、3个最严重的问题（P0）

### P0-1：Pending 消费时的版本号验证可能导致变化丢失

**位置**：§2.6 事件处理逻辑，第 661-663 行

**问题描述**：
```python
# 消费 pending 后
info.added.clear()
info.removed.clear()
info.has_pending_event = False

# ... 获取节点 ...

# 版本号验证
if version != node.version:
    logger.warning(...)
    return  # ← 直接返回，本次变化被丢弃！
```

**触发场景**：
在单线程事件循环中，这个问题可能不明显。但在以下场景会触发：
1. **数据推送在另一个线程**：on_node_stock_changed 执行过程中，数据线程推送了新数据，SourceNode.update_stocks() 被调用，node.version +1
2. **重入调用**：处理下游边时，某种回调导致源节点再次变化（虽然不常见，但防御性编程要考虑）

**后果**：本次事件的 added/removed 已经从 pending 中清空了，但因为版本号验证失败，业务逻辑没执行，变化永久丢失。

**为什么严重**：
- 这是一个"消费了但不处理"的问题，比重复处理更严重（重复处理最多浪费性能，丢数据是正确性问题）
- 并发场景下必现
- 文档没有说明并发模型，让人不知道这个问题会不会发生

**修复建议**：
```python
# 方案A：先验证版本号，再消费 pending（更安全）
node = context.services.topology.get_node(node_id)
if version != node.version:
    # 版本不一致，说明有更新的事件在队列中，跳过本次
    # 但 pending 不要清空，让更新的事件处理
    return

# 验证通过后再消费
added = info.added.copy()
removed = info.removed.copy()
info.added.clear()
info.removed.clear()
info.has_pending_event = False

# 方案B：去掉版本号验证，因为 dequeue 时已经验证过了
# （dequeue 时 event.version == info.version，而 info.version == node.version）
# 除非有并发修改，否则这个验证是多余的
```

**推荐方案A**，更安全。而且需要明确并发模型：事件队列的所有操作是否都在同一个线程？

### P0-2：FormulaCache 生命周期矛盾（引擎级 vs Tick 级）

**位置**：§4 公式结果缓存设计 + §1.2 EngineServices

**问题描述**：
- §4.2 说 FormulaCache 在 `formula_router.cache` 里
- §1.2 说 formula_router 是 EngineServices 的属性（引擎级生命周期）
- §4.3 又说 "tick 结束时清空所有缓存"（tick 级生命周期）

**矛盾**：引擎级的对象（EngineServices）持有 tick 级的状态（FormulaCache）。

**为什么是 P0**：
- 这是架构级的生命周期错误
- 会导致：测试时构造 EngineServices 也得考虑 FormulaCache 的重置、多 tick 状态混乱、职责不清晰
- 与 v1.3 新增的"生命周期匹配"原则（§0 第22行）直接矛盾

**修复建议**：
```
方案A（推荐）：FormulaCache 放到 TickContext 里
  - 因为它就是 tick 级的
  - 每个 tick 创建新的 TickContext，缓存自然就是新的
  - 不需要手动 clear

方案B：FormulaCache 独立出来，由 Engine 在 tick 开始/结束时管理
  - EngineServices 不持有 FormulaCache
  - Engine 在 tick 开始时创建 FormulaCache，挂到 TickContext 上
  - tick 结束后丢弃
```

**同时需要在 TickContext 属性列表中补上 `data_version` 字段**（§4.6 用到了，但 §1.3 没列）。

### P0-3：EventLoop / TimingGate / FilterEvaluator 完全没有详细设计

**问题描述**：
这三个是引擎的核心组件，但文档中只有名字，没有：
- 类的属性列表
- 类的方法签名
- 核心逻辑的伪代码
- 状态管理

**具体缺失**：

| 类 | 缺失内容 | 影响 |
|----|---------|------|
| **EventLoop** | 主循环逻辑、事件处理器注册机制、异常处理、停止机制 | 开发人员不知道怎么实现事件循环 |
| **TimingGate** | 有哪些时机类型、is_open() 的判断逻辑、状态变化检测、时间轮设计 | 时机门控是核心功能，没有设计等于没设计 |
| **FilterEvaluator** | 公式怎么执行、怎么调用 FormulaRouter、输入输出是什么、错误处理 | 过滤条件是股票池的核心，没有设计等于空壳 |

**为什么是 P0**：
- 这三个类加起来占引擎代码量的 40% 以上
- 没有详细设计，开发人员拿到文档后全靠脑补
- 脑补出来的东西大概率不符合架构预期，后期返工成本高
- 等价性论证的基础（"过滤函数是确定性的"）依赖于 FilterEvaluator 的设计

**修复要求**：
- EventLoop：主循环伪代码、事件处理器注册方式、与 Engine 的关系
- TimingGate：支持的时机类型、状态机、is_open() 逻辑、状态变化检测
- FilterEvaluator：evaluate() 方法签名、公式调用方式、输入输出约定

## 四、其他严重问题（P1）

### P1-1：EdgeExecuteEvent 的去重逻辑缺失

**位置**：§2.3 EventQueue 数据结构

**问题**：EventQueue 有 `_pending_edges: set[str]`，说明边执行事件有去重，但文档完全没讲去重逻辑。

**需要明确**：
1. 同一条边已经在队列中，再次入队时忽略？
2. 边正在执行时，又有触发，需要再次入队吗？
3. 去重是在 enqueue_edge_execute 里做的吗？伪代码呢？

### P1-2：并发模型完全没说明

**问题**：
整个文档没有一句话说明：
- 引擎是单线程还是多线程？
- 事件队列的操作是否线程安全？
- 数据推送在哪个线程？
- 回调在哪个线程执行？

**影响**：
- 不知道 P0-1 会不会触发
- 不知道 EventQueue 需不需要加锁
- 不知道 SourceNode.update_stocks 是不是线程安全的

### P1-3：等价性的关键假设未验证

**位置**：§5.3 + §5.4

**问题**：
等价性论证基于两个假设：
1. "旧引擎也是每个 tick 只计算一次"
2. "过滤函数是确定性的"

但这两个假设都没有验证：
- 旧引擎到底是 tick 级还是变化时立即计算？文档说"需要确认"但没确认
- 所有公式都是确定性的吗？有没有随机数、有没有时间依赖、有没有外部状态？

**影响**：如果假设不成立，整个设计的正确性就不成立。

### P1-4：TickContext 的创建/销毁时机不明确

**问题**：
- §1.3 说"每个 tick 开始时创建新的 TickContext"
- 但 §3.6 路径2中，_on_tick_data 直接修改 `self.context.tick.current_data_ts`
- 这说明 TickContext 是复用的，不是每个 tick 创建新的

**矛盾**：到底是"每个 tick 创建新的"还是"复用并重置"？

**影响**：生命周期不清晰，容易有状态残留问题。

### P1-5：DataProvider 是现有系统的还是新设计的？

**位置**：§3.4 + §3.6

**问题**：
文档中大量使用 DataProvider，但：
- 它是现有系统中已有的，还是新设计的？
- 如果已有的，接口是什么样的？需要改多少？
- EventBus 是 DataProvider 自带的，还是新加的？

**影响**：与现有系统的对接成本完全不可评估。
